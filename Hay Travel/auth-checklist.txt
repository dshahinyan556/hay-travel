1. Схема БД (LocalDB "ATTours", НЕ Azure):
   - User: + IsEmailVerified (bool, default false).
   - PasswordRecovery ПЕРЕИМЕНОВАНА в UserToken (+ поле Type: EmailVerification=1/
     PasswordReset=2), unique index (UserId,Type) вместо unique(UserId).
   - Новая RefreshToken (Id/UserId/TokenHash-unique(SHA256)/ExpiresAtUtc/CreatedAtUtc/
     CreatedByIp/RevokedAtUtc/ReplacedByTokenHash).
   - Миграции применены к LocalDB: AddAuthTokensAndEmailVerification, SeedAdminUser.
   - Azure SQL НЕ трогали (осознанно, по решению Давида — сначала локальный тест).

2. Сид админа (данные УЖЕ переданы Давиду в чате, пароль сохранён им в password
   manager — здесь НЕ дублирую пароль):
   Username: admin
   Email:    admin@haytravel.local
   (пароль — см. чат / password manager Давида, не хранить plaintext в файлах)

3. JWT: access 15 мин (в теле ответа), refresh 14 дней (httpOnly Secure SameSite=Lax
   cookie, Path=/api/Auth — РЕГИСТРОЗАВИСИМО, фронт обязан ходить ровно на /api/Auth,
   не /api/auth). Ротация refresh с reuse-detection (повторное предъявление отозванного
   токена гасит ВСЕ refresh-токены юзера). BCrypt для паролей.

4. Email: IEmailSender с DevEmailSender (сейчас активен — токен возвращается в поле
   DevToken ответа, реальных писем не шлёт) и SendGridEmailSender (код готов, но
   SendGridApiKey пуст — не используется, пока Давид не даст ключ; провайдер выбирается
   в DI автоматически по наличию ключа).

5. Эндпоинты AuthController (api/Auth, все AllowAnonymous кроме ChangePassword):
   POST Register {FirstName,LastName?,Username,Email,PhoneNumber,Password}
        -> MessageResultModel{Message,DevToken?}. Email уже занят -> generic 200
        (без утечки инфы), если юзер неверифицирован - письмо шлётся повторно (это и
        есть "resend", отдельного эндпоинта нет и не нужно).
        Username занят -> 400 UsernameTaken.
   POST VerifyEmail {Token} -> MessageResultModel. Невалиден/просрочен -> 400
        VerificationTokenInvalid.
   POST Login {UsernameOrEmail,Password} -> LoginResultModel{AccessToken,
        ExpiresInSeconds,User(UserInfoModel),ForceChangePassword}.
        401 InvalidCredentials / 401 AccountLocked / 403 EmailNotVerified.
        Lockout: 5 неудачных попыток -> блок 15 мин (UTC).
   POST RefreshToken (читает cookie) -> AccessTokenModel. Теперь ТАКЖЕ перепроверяет
        LockedUntil/IsEmailVerified при каждом refresh (ужесточено по просьбе Давида) -
        если юзера заблокировали/деверифицировали после логина, refresh отклонится
        (401) и текущий (только текущий, не все) токен отзовётся.
   POST Logout (cookie) -> 204, отзывает refresh на сервере, идемпотентно.
   POST ForgotPassword {Email} -> MessageResultModel, ВСЕГДА generic 200.
   POST ResetPassword {Token,NewPassword} -> MessageResultModel. Успех: новый пароль +
        погашение токена + сброс FailedLoginAttempts/LockedUntil/ForceToChangePass +
        отзыв ВСЕХ refresh-токенов юзера. Невалиден -> 400 ResetTokenInvalid.
   POST ChangePassword {CurrentPassword,NewPassword} - [Authorize] (добавлено доп. по
        просьбе Давида, в исходном контракте не было). Неверный текущий -> 401
        InvalidCredentials.

6. UsersController (api/Users, [Authorize(Roles="Admin")] на весь контроллер):
   GET -> List<UserInfoModel>. PATCH ChangeRole {UserId,RoleId} -> UserInfoModel.
   Guard: нельзя снять роль Admin у последнего админа / у самого себя.

ОТКЛОНЕНИЯ ОТ ПЛАНА АРХИТЕКТОРА (все обоснованы, зафиксировано в отчёте
frontend-developer'а):
  - authFetch рефрешит токен только на 401 БЕЗ errorCode (bodyless-challenge JWT-мидлвари),
    а не на любой 401 - иначе ChangePassword с неверным текущим паролем (тоже 401,
    но С errorCode InvalidCredentials) разлогинивал бы юзера вместо показа ошибки.
  - sessionEpoch-гард в store - защита от гонки "login во время фонового refresh".
  - Роль в JWT приходит НЕ как claim "role", а как длинный WS-URI claims-namespace
    (`http://schemas.microsoft.com/ws/2008/06/identity/claims/role`) - план архитектора
    предполагал короткое имя, это единственное непроверенное допущение плана, оно не
    подтвердилось на практике. decodeAccessToken читает оба варианта.
  - Ошибки бэкенда - PascalCase {Message,ErrorCode}, не camelCase как в плане (§0.4
    архитектора был неточен). Обработано (читает оба регистра, как уже делал
    catalogErrors.ts).
  - Backend email-ссылки (Email:VerifyUrlBase/ResetUrlBase в appsettings) указывают на
    /verify-email и /reset-password, а не /auth/* - добавлены 2 redirect-роута вместо
    правки backend-конфига (dev и prod appsettings трогать не стали).
