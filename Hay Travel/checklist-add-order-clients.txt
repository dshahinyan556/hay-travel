ЗАДАЧА A — Заморозка заказа по статусу (Rejected/Completed) + "Возобновить"
════════════════════════════════════════════════════════════════════════════
ДОПУЩЕНИЯ (подтверждены Давидом):
- При статусах Rejected и Completed заказ становится ПОЛНОСТЬЮ нередактируемым: строки,
  оплаты, назначение исполнителя, pickup/навигатор, причина отказа — всё read-only.
- Единственное действие, доступное в этот момент — кнопка "Возобновить" (замещает собой
  Approve/Reject/"..." меню целиком, а не добавляется к ним). Возвращает заказ в Open.
- Технически Reopen = уже существующий `SetStatus(Open)` — новый бэкенд-эндпоинт НЕ нужен,
  OrderStatusService и так принимает любой переход (осознанно нестрогий автомат).
- Без бэкенд-работы вообще — это чисто фронтенд-гейтинг. Делаю сам, без сабагентов (мелкая
  задача, [[feedback_delegate_to_subagents]]).
- Допущение (не переспрошено явно, поправить если не так): при Reopen причина отказа
  (rejectReason) очищается — заказ возвращается в чистое Open-состояние.
- Допущение: кнопка "Удалить" в тулбаре остаётся доступна даже на замороженном заказе —
  удаление это не редактирование содержимого, а его снятие целиком.

[ ] A.1 `OrderContextActions.tsx` / `OrderDetailPage.tsx`: `frozen = status===Rejected ||
        status===Completed`. При frozen — рендерить ТОЛЬКО кнопку "Возобновить" (новый
        `onReopen` → `setOrderStatus({id, status: Open, rejectReason: null})`), скрыть
        Approve/Reject и весь `AdminActionsMenu` ("..." — Назначить/Отправить клиенту/
        Отправить исполнителям).
[ ] A.2 `OrderLinesGrid.tsx`: Select исполнителя, чекбокс/сумма предоплаты, "+"/"×" — все
        disabled при frozen (расширить существующий `pending`-проп или завести отдельный).
[ ] A.3 `OrderPaymentTab.tsx`: форма "+ Добавить проводку" disabled при frozen.
[ ] A.4 `OrderFulfillmentTab.tsx`: pickup/навигатор + "Назначить и отправить" disabled при frozen.
[ ] A.5 `OrderHeader.tsx`: Textarea причины отказа — read-only при frozen (сейчас она и так
        показывается только при Rejected, но была редактируемой).
[ ] A.6 AdminToolbar: Save/Add — disabled при frozen (редактировать/добавлять строки нельзя).

ЗАДАЧА B — Ручное создание заказа админом + приглашение клиента (User без пароля)
════════════════════════════════════════════════════════════════════════════
Схема выполнения: архитектуру (контракт ниже) собираю сам, КОДЯТ сабагенты — backend-developer
(бэкенд-часть целиком) и frontend-developer (фронтенд-часть целиком), каждый ОДИН раз, без
повторных раундов ([[feedback_subagent_single_round_use]]). Спрашиваю разрешение перед каждым
вызовом Agent отдельно ([[feedback_subagent_permission_required]]).

════════════════════════════════════════════════════════════════════════════
ДОПУЩЕНИЯ (подтверждены Давидом в этой сессии, не переспрашивать)
════════════════════════════════════════════════════════════════════════════
- "Клиент" — НЕ отдельная сущность. Это тот же User (та же таблица), которого админ создаёт
  вручную БЕЗ пароля. Экран создания — не отдельный раздел "Клиенты", а прямо в существующем
  разделе "Пользователи" (UsersPage).
- Приглашение: админ может "пригласить" такого юзера — он переходит по ссылке, вводит
  new password/confirm password и становится обычным пользователем сайта. Технически — то же
  самое, что уже существующий флоу ForgotPassword→ResetPassword (UserToken/email), просто
  инициируется админом, а не самим юзером с формы "забыли пароль".
- IsEmailVerified у юзера, созданного админом = false до активации (тот же смысл, что при
  обычной саморегистрации) — подтверждается, когда юзер реально ставит пароль.
- Роль нового юзера — всегда Regular, без выбора в форме. Меняется потом обычным Select роли
  на UsersPage, как у любого другого юзера.
- Password (хэш) в БД NOT NULL — для админ-созданного юзера нужен непроходимый плейсхолдер-хэш
  (например хэш от случайного GUID), который не совпадёт ни с одним реальным паролем.
- Заказ, который вручную создаёт админ: СНАЧАЛА пустой (без строк, без клиента ещё не может
  быть — клиент выбирается сразу), строки добавляются потом уже готовым "+"/AddLineModal в
  OrderDetailPage. Email клиенту НЕ уходит автоматически при создании — только по существующей
  кнопке "Отправить заказ клиенту" в "..." меню.
- Точка входа "Добавить заказ" должна быть В ОБОИХ местах:
  (а) на списке заказов (/admin/orders) — сейчас там вообще нет тулбара/кнопки добавления;
  (б) внутри уже открытого заказа (OrderDetailPage) — там кнопка уже есть, но сейчас это
  visual-заглушка (`newDraftMode`/`blankDraftOrder` в OrderDetailPage.tsx, см. комментарий в
  коде "never sent anywhere") — Save для неё задизейблен, реального создания не происходит.
  Обе точки входа ведут к одному и тому же реальному сценарию создания.
- Публичный клиентский чекаут НЕ меняется: `OrderController.CreateAsync` продолжает брать
  UserId строго из JWT (анти-IDOR, см. комментарий в контроллере) — это осознанно ДРУГОЙ,
  новый endpoint для админского создания, с явным UserId в теле, доступный только роли Admin.

БЭКЕНД-КОНТРАКТ (собран мной по факту существующего кода, для backend-developer)
════════════════════════════════════════════════════════════════════════════
[ ] 1. UsersController — новый `POST Users/CreateByAdmin`, `[Authorize(Roles=ApiRoles.Admin)]`.
       Model: `AdminCreateUserModel { FirstName, LastName, Username, Email, PhoneNumber? }`.
       Новый сервис (по образцу `AuthService.RegisterAsync`, ATTours.Service/Services/
       AuthServices или рядом с остальными User-сервисами):
       - Уникальность Username/Email — переиспользовать `UserRegistrationValidationService`
         (тот же класс, что и RegisterAsync, конструктор принимает `Context` — см.
         AuthService.cs:90).
       - `RoleId` — Regular-роль (тот же `UserRoleRepository...SingleOrDefaultAsync(role =>
         role.Type == RoleType.Regular)`, см. AuthService.cs:107-110).
       - `Password` — хэш случайного непроходимого значения: `passwordHasher.Hash(Guid.NewGuid()
         .ToString())` (IPasswordHasher уже в DI, см. BCryptPasswordHasher).
       - `IsEmailVerified=false`, `FailedLoginAttempts=0`, `LockedUntil=null`,
         `ForceToChangePass=false`, `IsDeleted=false`, `RegisteredAtUtc=UtcNow`,
         `RegisteredIp=null` (это не саморегистрация, IP админа тут не смысловое поле).
       - PhoneNumber: "" → null (тот же паттерн, AuthService.cs:114).
       - НЕ шлёт никакого письма сама (приглашение — отдельное явное действие, п.2). НЕ пишет
         OrderEvent (это User, не Order).
       - Возвращает UserInfoModel (существующий маппинг, как у остальных User-эндпоинтов).
[ ] 2. "Пригласить" — БЕЗ нового бэкенд-кода. Фронт напрямую дёргает уже существующий ПУБЛИЧНЫЙ
       `POST Auth/ForgotPassword` (AllowAnonymous, `authApi.ts:forgotPasswordRequest`) с email
       созданного юзера — тот же механизм, что "Забыли пароль" на сайте.
[ ] 3. ВАЖНАЯ НАХОДКА, обязательна к фиксу: `AuthService.ResetPasswordAsync` (AuthService.cs:385)
       сейчас НЕ трогает `IsEmailVerified`. Если оставить как есть — приглашённый юзер поставит
       пароль через ResetPassword, но всё равно не сможет войти (гейт "IsEmailVerified=false →
       403 EmailNotVerified" в LoginAsync). Фикс: `ResetPasswordAsync` должен выставлять
       `user.IsEmailVerified = true`, если было false — обоснование: раз юзер прошёл по
       одноразовой ссылке, присланной на его email, владение email тем самым доказано, это
       эквивалентно верификации. Поведение корректно для ЛЮБОГО юзера через reset-flow, не
       только для админ-приглашённых — не костыль, общее исправление.
[ ] 4. OrderController — новый `POST Order/CreateByAdmin`, `[Authorize(Roles=ApiRoles.Admin)]`.
       Model: `OrderAdminCreateModel { UserId }`. Новый сервис (рядом с `OrderCreationService`,
       но БЕЗ строки — тур/дата/гости туда не передаются): создаёт `Order{ UserId, Number =
       OrderNumberGenerator (переиспользовать как есть), Status = OrderStatus.Open, Currency =
       <тот же дефолт, что берёт публичный OrderCreationService>, Lines = [] }`. НЕ шлёт письмо
       админу о новой брони (это его собственное действие, не бронь с сайта) — в отличие от
       публичного `CreateAsync`. Пишет `OrderEvent.Created` (тот же лог-вызов, что у публичного
       Create — контракт уже есть, см. docs/specs/007-order-event-log-backend.md).
       Проверить перед сдачей: ничего в OrderInfo/мапере/агрегатах (DiscountTotal/Total над
       пустым Lines) не падает на 0 строк — защита "нельзя удалить последнюю строку" относится
       только к RemoveLine, на создание пустого заказа не распространяется.
