3. RichTextEditor («профессиональный» редактор) — расширяем существующий TipTap-компонент
   (`features/admin/ui/RichTextEditor`), не пишем новый. Реальный аудит текущего кода
   (`RichTextToolbar.tsx`, `ColorPicker.tsx`, `useRichTextEditorInstance.ts`) — что уже есть и

   УЖЕ ЕСТЬ (не переделываем): bold/italic/underline/strike, blockquote, bullet/ordered list,
   align left/center/right, ссылка (`LinkDialog`), изображение (`RichImage`+`ImageDialog`),
   undo/redo, вставка Data Field (`PlaceholderMenu`).

   ОТСУТСТВУЕТ/НЕДОСТАТОЧНО — делаем:
   - Заголовки: сейчас только H1–H3 (`HEADING_LEVELS = [1,2,3]`, `heading: { levels: [1,2,3] }`).
     Расширить до H1–H6 (это HTML-максимум, выше H6 не бывает — Давид говорил «1-7», уточняю:
     стандартный потолок H6, дальше идёт просто Paragraph/Preformatted/Quote как отдельные
     стили, не заголовки).

     нормальный диапазон в pt (не px), как в Word/Google Docs: 8, 9, 10, 10.5, 11, 12, 14, 16,
     18, 20, 24, 28, 36, 48, 60, 72pt — курируемый список в Select (не произвольный ввод, чтобы
     не сломать рендер письма), значения хранятся как CSS `pt` (HTML/CSS его поддерживает
     нативно, конвертация не нужна).
   - Font family — отсутствует полностью. Добавить `@tiptap/extension-font-family` + toolbar

     New, Verdana, Tahoma и т.п. — то, что реально доживает до email-клиента, не системные
     экзотические шрифты типа Comic Sans/Impact из ERP-скрина).
   - Highlight/заливка текста — отсутствует полностью (сейчас только text color). Добавить
     background-color мark (аналогично уже существующему `TextStyleAttributes` для color) +
     отдельная кнопка-палитра в тулбаре.
   - Нормальная палитра цветов — заменить/дополнить нынешние 5 quick-swatches + нативный
     OS-пикер настоящим грид-пикером (несколько рядов оттенков + серая шкала + произвольный

   - Переключатель режимов Visual / HTML / Plain text / Preview — отсутствует полностью,

   - Санитайзер (ADR 026, `RichHtmlSanitizer.cs`) — добавить профиль для Telegram (жёсткий
     allow-list) + расширить Email-профиль под table/pre/code/font-family/background-color,

   - «Previous Data Field» из ERP-скрина — НЕ делаем: в проекте нет сценария сравнения
     до/после значения, для которого это нужно. Если появится — отдельная задача.
   - Выравнивание работает на уровне paragraph/heading (`TextAlign.configure({ types:

     (Word/Google Docs/Gmail): выравнивание — свойство блока, а не отдельной визуальной

   полностью редактируемая, имя/канал/сущность не залочены).
   - Для того чтобы код (`AuthService`) знал, какой именно шаблон использовать для какого
     триггера — на `NotificationTemplate` заводится необязательное поле `TriggerKey`
     (VerifyEmail/ResetPassword/EmailChangeCode/EmailChangeConfirm/None), доступное как обычное
     поле формы (не скрытое, не спец-режим).
   - Защита от поломки продакшена: удаление шаблона с непустым `TriggerKey` блокируется, пока

     «системным», просто обычная защита от случайного удаления используемой записи, снять

НАЙДЕН И ПОЧИНЕН критический баг при живой проверке: сохранение ЛЮБОГО Telegram-шаблона
СТИРАЛО ВСЁ ТЕЛО ЦЕЛИКОМ — `<p>` (TipTap оборачивает им любой текст безусловно) не входил в
Telegram-whitelist санитайзера, и запрещённый тег вырезается вместе с содержимым. Починено:
`p`/`br` разрешены в `TelegramEntry` для ХРАНЕНИЯ, конвертируются в `\n` непосредственно перед
отправкой (`OrderNotificationService.Telegram.cs`, `ParagraphsToNewlines`). Заодно добавлена
вторая линия защиты — валидация проверяет тело ПОСЛЕ санитизации, не только до.

Также попутно найден и починен баг с фантомным "есть несохранённые изменения" сразу после
открытия карточки (RichTextEditor перевыставляет HTML при монтировании, из-за чего draft
расходился с baseline без единого действия пользователя) — `useNotificationTemplateForm`
сворачивает патчи первого тика в baseline тоже.

Миграция `AddNotificationTemplates` написана руками поверх scaffold (EF сам данные не
переносит) — прогнана на локальной dev-БД успешно (данные перенесены, `EmailTemplate`
удалена). НА КОПИИ ПРОД-БД НЕ ТЕСТИРОВАЛАСЬ — проверить на стейджинге перед деплоем, миграция
необратимо дропает таблицу EmailTemplate (Down() восстанавливает Email-шаблоны частично, но
не Telegram/auth-шаблоны, которых в старой схеме не было).

Известное ограничение: подстановка {{Token}} внутри `href` (напр. кликабельная ссылка вместо
голого URL в auth-письмах) не проверена — санитайзер валидирует href ДО подстановки токена,
поэтому `{{VerifyUrl}}` внутри href может быть вырезан как невалидный URI; сейчас auth-ссылки —
просто текст в теле, как было раньше (поведение не изменилось, просто не улучшено).
