ДОПУЩЕНИЯ (не переспрашивать, но если Давид поправит — обновить здесь же)
════════════════════════════════════════════════════════════════════════════
- Order model: полная переделка текущей клиентской Order в мульти-строчную (подтверждено).
- Статусы: 7 новых (Open/Hold/Approved/Rejected/ReadyForAssignment/PendingPayment/Completed)
  ПОЛНОСТЬЮ заменяют текущие 3 (подтверждено) + необязательное поле "причина отклонения".
- Employee назначается на КАЖДУЮ строку заказа отдельно; на уровне заказа есть кнопка
  "назначить на все строки" — bulk-действие, заполняет все строки одним значением, каждую
  можно потом переопределить (подтверждено).
- Нумерация: ДДММГГ + 4-значный счётчик, СБРОС каждый день (подтверждено). Это отдельное
  "человеческое" поле Order.Number, внутренний Id в БД остаётся обычным техническим полем —
  НЕ подтверждено явно, но иначе ломается FK/сортировка. Если важно иначе — сказать.
- Клиентский сайт (публичный чекаут брони тура) НЕ меняется — по-прежнему создаёт заказ с
  ОДНОЙ строкой. Многострочность — это то, что админ добавляет вручную открытым заказом
  (кнопка "+" в гриде). Это МОЁ предположение, не подтверждённое явно Давидом — если бронь с
  сайта тоже должна стать мульти-товарной (корзина), сказать до Фазы 1.
- PDF из заказа прикладывается: (а) к письму "Отправить заказ" клиенту — весь заказ,
  (б) к письму сотруднику при "Назначить" — только его строка(и). Тоже моё предположение,
  не подтверждено явно — поправить, если не так.
- Email сейчас — простой текст (без шаблонов), т.к. Давид сказал что шаблонами будем
  заниматься отдельно позже. Не проектировать шаблонизацию сейчас, только сам факт отправки +
  PDF-вложение.
- Скидка на тур: ОДНО активное правило на тур (не список), с датой окончания, само перестаёт
  применяться после даты (не нужно вручную снимать).
- UI: никаких нативных <select>/window.confirm — только переиспользуемые shared/ui компоненты
  (Select/Popover/Checkbox/Button/Modal/Sheet). Экшн-кнопки заказа — через новый выпадающий
  ActionsMenu (строится на shared/ui/Popover, по образцу Select). Ссылки (клиент/продукт в
  строке) — без иконки-стрелки, обычная ссылочная стилизация (цвет/подчёркивание), везде
  target="_blank".
- Правки от 2026-08-16 (второй раунд, после мокапа): клиент — тоже ссылка на страницу
  пользователя в админке (не только продукт). 3-я вкладка называется "Детали для выполнения"
  (не "Выполнение"). Кнопка добавить строку — текст "+", кнопка удалить строку(и) — символ "×"
  (обычный крестик закрытия, не буква x). "Требуется предоплата" в гриде — Checkbox, не текст
  Да/Нет. Новое: парсер/генератор PDF из заказа для email-вложений (Фаза 4) — уже было в
  чек-листе, подтверждено явно. Email-шаблонами Давид займётся отдельно позже — сейчас просто
  текст письма, без шаблонизации.
- Архитектурное решение по деньгам (2026-08-16, зафиксировано как ADR 019, супersедит ADR 014):
  OrderPayment был 1:1 снапшот денег заказа (ADR 014) — теперь список ПРОВОДОК
  (Type/Number-автономер/Amount/OrderLineId), снапшоты цены/скидки уехали на OrderLine.
  См. docs/adr/019-order-becomes-multi-line-orderpayment-becomes-ledger.md.
- Прод не работает, реальных заказов ещё нет (Давид, 2026-08-16) — миграция может быть
  drop/create, без сохранения существующих данных Order/OrderPayment. Упрощает Фазу 1.5.
- SMTP-инфраструктура УЖЕ ЕСТЬ в проекте (IEmailSender/SendGridEmailSender/BrevoEmailSender/
  DevEmailSender) — Фаза 5.3 закрыта простой находкой, отдельный setup провайдера не нужен.
