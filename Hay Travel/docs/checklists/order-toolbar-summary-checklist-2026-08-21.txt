Чек-лист: Order Toolbar + Summary + Action-панель + История заказа (Acumatica-style, ч/б)
Заведено: 2026-08-21. Полностью переписан в этот же день после нескольких раундов уточнений —
ниже ФИНАЛЬНОЕ состояние договорённостей, а не история правок.

===============================================================================
ОБЩИЙ КОНТЕКСТ
===============================================================================
Референс — 2 скрина Acumatica Sales Order (тулбар с иконками + summary-панель справа +
"..." сгруппированное меню действий) + Hay Travel/brand/button.txt (ТОЛЬКО статика чёрной
кнопки: чёрный фон/белый текст/форма — БЕЗ shimmer-анимации, компонент как есть не ставим).
Цель — перенести уровень функционала Acumatica на наш ч/б современный стиль, как
переиспользуемые примитивы админки, обкатанные на странице заказа.

Правила выполнения (agents.md/team.md), важное для этой задачи:
- Архитекторов (architect / backend-architect) больше НЕ вызывать — контракт по OrderEvent уже
  получен и утверждён, архитектурных развилок не осталось.
- Тестировщиков (tester / backend-tester) НЕ вызывать — Давид тестирует сам.
- Реализацию фронтенда (переписывание OrderDetailPage) делает ГЛАВНЫЙ АГЕНТ САМ, не через
  агента frontend-developer. ui-ux-engineer делает только переиспользуемые примитивы в shared/ui.
- backend-developer делает всю бэкенд-часть (OrderEvent + notify-флаг у назначения).

===============================================================================
СКОУП: ЧТО ИМЕННО ДЕЛАЕМ
===============================================================================

1) AdminToolbar (переиспользуемый примитив, shared/ui)
   Кнопки строго в этом порядке: Cancel, Save, Add, Delete.
   - Стиль — ч/б, статика из button.txt (без анимации), см. утверждённый мокап.
   - Save — иконка нормальной "дискеты" (добавить в shared/ui/icons.tsx, геометрия как у
     остального набора: 24x24, stroke 1.5, round caps/joins).
   - Delete — строго ч/б (инверсия в чёрный на hover), БЕЗ красного акцента. Красная кнопка
     подтверждения ВНУТРИ модалки удаления остаётся как есть в коде (variant="danger") — не трогать.
   - Prev/Next — ОТМЕНЕНЫ Давидом, не делать вообще.

2) Save/Cancel — страница заказа переходит на модель черновика
   - Локальный буфер правок; Save коммитит на сервер, Cancel откатывает МГНОВЕННО (без запроса,
     из последнего загруженного/сохранённого снапшота).
   - Под черновик идут ПОЛЯ: статус — НЕТ (см. п.4, статус вообще не редактируется через Select),
     reject-reason, requiresPrepayment/prepaymentAmount, pickupDetails/navigatorLink.
   - НЕ уходят в черновик (остаются мгновенными операциями со своим сохранением): Approve/Reject,
     Assign (весь попап), AddPayment, AddLine/RemoveLine, SendToClient, SendToEmployees.
   - Оптимизация количества запросов на Save — на усмотрение реализации (батчить, что можно).

3) Add — ТОЛЬКО визуальное состояние "новый черновик"
   - Открывает страницу в пустом клиентском состоянии (без сохранения в БД, без пикера клиента).
   - Save в этом режиме — задизейблен, с подсказкой, что полноценное создание (пикер клиента +
     расширение бэкенда POST /Order — сейчас он всегда берёт владельца из токена и делает 1
     строку) появится в отдельной будущей задаче.

4) Статус — read-only бейдж
   - Никакого Select. Статичная пилюля (как "Back Order" у Acumatica), БЕЗ hover/focus/стрелки.
   - Показывается ТОЛЬКО в шапке карточки заказа (у номера/клиента) — НЕ дублировать в тулбаре.
   - Меняется ИСКЛЮЧИТЕЛЬНО через кнопки Approve/Reject (см. п.5) — никакого прямого редактирования.

5) Contextual action-кнопки (у тулбара, рядом с "...", НЕ спрятаны в выпадающем меню)
   Именно эти 5 действий и их поведение — финальные названия и семантика от Давида:
   - "Одобрить" — мгновенный сейв. Просто вызывает СУЩЕСТВУЮЩИЙ SetStatus(Approved).
     Никакой переделки flow (Assigned/Готов к выполнению/В процессе и т.д. НЕ вводим).
   - "Отклонить" — мгновенный сейв. Вызывает существующий SetStatus(Rejected).
   - "Назначить исполнителя/ей" — открывает попап. Один исполнитель на строку/на все строки
     сразу — КАК СЕЙЧАС (AssignAllModal/per-line select), просто новый вид под новый дизайн.
     НЕ вводим множественных исполнителей с ролями (водитель/гид/гид-водитель) — это отдельная
     будущая задача (many-to-many модель).
     В попапе РОВНО 3 кнопки: "Отмена", "Назначить" (тихо, БЕЗ письма), "Назначить и отправить
     письмо" (как сейчас AssignEmployee — назначает и шлёт письмо+PDF атомарно).
     Бэкенд: нужно завести у назначения флаг "слать письмо или нет" (сейчас AssignEmployee всегда
     шлёт письмо) — небольшое расширение существующего OrderAssignEmployeeService/эндпоинта,
     backend-developer делает без нового похода к архитектору.
   - "Отправить заказ клиенту" — НЕ сейвит. Если в черновике есть несохранённые изменения —
     сначала спрашивает сохранить (диалог "Сохранить перед отправкой?" → Сохранить и отправить /
     Отмена). Переиспользует существующий SendToClient.
   - "Отправить заказ исполнителям/ю" — запасное/ручное действие: ПОВТОРНО отправляет письмо+PDF
     ТЕМ, кто УЖЕ назначен на заказ, БЕЗ создания нового назначения (на случай сбоя автоматической
     отправки или по требованию). Технически — переиспользует существующий AssignEmployee-эндпоинт
     по каждой уже назначенной строке с ТЕМ ЖЕ employeeId (тот же паттерн, что уже делает кнопка
     "Назначить и отправить" на табе "Детали для выполнения", просто на весь заказ разом).
     Тоже НЕ сейвит черновик — если есть несохранённое, сначала спрашивает сохранить.
   - Видимость: Approve/Reject показывать, пока заказ ещё не Approved/Rejected; после — вместо
     них показывать Assign/SendToEmployees. Это просто условный рендеринг по текущему статусу,
     БЕЗ серверных guard-проверок (флоу остаётся плоским, как и весь текущий OrderStatus).

6) Action-панель ("...", сгруппированное выпадающее меню)
   - Группы-колонки в ч/б стиле (см. утверждённый мокап). Содержимое ПОСЛЕ пересмотра:
     действия из п.5 (Одобрить/Отклонить/Назначить/Отправить клиенту/Отправить исполнителям)
     теперь ПРОМИНЕНТНЫЕ кнопки у тулбара, а не пункты меню — см. п.5.
   - Placeholder-пункты "скоро" ("Печать ваучера", "Дублировать заказ") — ИСКЛЮЧИТЬ из разработки
     полностью, не делать даже как задизейбленные заглушки.
   - Итог: если после переноса п.5 в контекстные кнопки у "..." не остаётся реальных пунктов —
     меню можно не показывать вообще на этом этапе (пусто = скрыть триггер), либо оставить как
     пустую заготовку под будущие "Recalculate Prices"-подобные действия — на усмотрение реализации.

7) Activity log / таб "История" (ПОЛНОСТЬЮ в этой задаче, не отложено)
   - Бэкенд-контракт УЖЕ утверждён backend-architect:
     Hay Travel/docs/specs/007-order-event-log-backend.md
     Hay Travel/docs/adr/020-order-event-log-outside-mutation-transaction.md
   - Сущность OrderEvent, пишется вне транзакции мутации (не роняет операцию при сбое лога),
     логируются: Created, StatusChanged (в т.ч. Approve/Reject), Updated, LineAdded/Removed/
     Updated, EmployeeAssigned, SentToClient, PaymentAdded. Delete заказа НЕ логируем (каскад).
   - СОЗДАНИЕ ЗАКАЗА — тоже событие (Created) — уже учтено в контракте, отдельно делать не нужно.
   - Чтение — отдельный `GET api/Order/{id}/Events`, НЕ поле в OrderInfoModel.
   - Новый таб "История" на странице заказа (после "Детали для выполнения") — чистый readonly
     таймлайн (дата/автор/описание/тип), без интерактивных элементов. Показать и пустое состояние.

8) "Тяжёлые" операции (Approve/Reject/Assign-и-письмо/SendToClient/SendToEmployees)
   - На время выполнения блокируется ВСЯ страница заказа (не только кнопка) — уже есть паттерн
     `pending`, который OrderDetailView прокидывает во все дочерние компоненты через run().
   - Дополнительно нужен ВИДИМЫЙ индикатор "идёт тяжёлый процесс" (генерация PDF + отправка) —
     не просто disabled-состояние: спиннер/оверлей с поясняющим текстом поверх заблокированной
     страницы, а не только спиннер на самой кнопке.
