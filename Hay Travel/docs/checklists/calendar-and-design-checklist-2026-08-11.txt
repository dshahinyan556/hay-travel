ФИЧА №1 — Календарь занятости + бронирования
---------------------------------------------------------------------

Зафиксированные решения:
- Объём: A — полноценный Booking (Order-сущность) + Calendar/Closure сразу
  (не заглушка, реальные заказы считаются в календаре).
- Бронирование — только для залогиненных пользователей (JWT), гостевого
  чекаута нет.
- Оплата — БЕЗ онлайн-шлюза сейчас: заказ фиксирует сумму/предоплату как
  число, оплата идёт вне сайта (звонок/перевод). Архитектура ОБЯЗАНА
  закладывать точку расширения под будущий платёжный шлюз, чтобы позже
  не переписывать Order с нуля.
- Подтверждение заказа — сейчас автоматическое при отправке. В будущем
  (после внедрения предоплаты) часть продуктов потребует РУЧНОГО
  подтверждения администратором/командой, а часть — останется авто; это
  будет настройкой на уровне продукта (тура/экскурсии), не глобальным
  переключателем. Статус-модель должна быть расширяемой под это заранее.
- Закрытие дней: точечные даты + повторяющиеся правила (день недели),
  применимые глобально (все туры) или к конкретному туру, + массовые
  действия (например «закрыть все понедельники для тура Гарни-Гегард»).
- Календарь: месячная сетка (grid), навигация на год вперёд, клик по дню —
  панель/модалка с деталями и действиями (кол-во заказов по турам,
  открыть/закрыть).
- Изменения доступности в админке обязаны быть видны на публичном сайте
  при бронировании (закрытые даты недоступны в BookingCard).

ФИЧА №2 — Дизайн (шрифт / палитра / тема / логин-регистрация)
---------------------------------------------------------------------

Зафиксированные решения:
- Палитра — кураторские пресеты (3–5 готовых вариантов), НЕ свободный
  цветовой конструктор. Текущая тёмно-люксовая палитра остаётся одним из
  пресетов, добавляется минимум одна новая «главная».
  Выбор активной палитры — из админки (раздел «Настройки»).
- Dark/Light дефолт — мягкий: админ задаёт дефолтный режим для новых
  посетителей, переключатель у пользователя остаётся как есть.
- Референса конкурента нет — дизайнер предлагает шрифт и палитру сам,
  на уровне премиум-туристических сайтов.
- Редизайн логина/регистрации — в ЭТОМ ЖЕ пакете, до уровня
  интерактивности разделов Туры/Экскурсии (moзейн-эффекты, `.reveal`,
  `card-lift`, full-bleed паттерны текущего сайта).

Подзадачи:
[ ] 1. designer (+ design-mockup) — варианты шрифта + минимум одна новая
       «главная» палитра (плюс текущая как пресет) — мокапы на утверждение
[ ] 2. designer — мокап редизайна логина/регистрации под визуальный язык
       остального сайта — на утверждение
[ ] 3. Утверждение Давидом шрифта/палитры/мокапов логина — БЛОКИРУЮЩИЙ шаг,
       дальше архитекторы/разработка не начинаются
[ ] 4. architect (frontend) — спецификация палитр-пресетов как
       data-driven набора (не хардкод в index.css), переключение через
       data-theme/data-palette, спецификация редизайна логина/регистрации
[ ] 5. backend-architect — контракт под хранение активной палитры/дефолт-
       темы (вероятно расширение SiteSetting) — только если нужно хранение

[ ] 6. ui-ux-engineer / frontend-developer — реализация шрифта, палитр-

[ ] 7. backend-developer — новый SiteSetting-ключ/эндпоинт при
       необходимости (см. п.5)
[ ] 8. tester — проверка всех палитр × обеих тем, ОБЯЗАТЕЛЬНО мобильная
