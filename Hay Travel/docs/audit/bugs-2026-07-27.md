## 1. Баг A — на `/excursions` нельзя выбрать «Туры»

### 1.1. Как устроены маршруты (вопрос 1)

Это **один компонент с разными пропсами**, не две страницы и не редирект.

`src/app/router.tsx`:
```
34:        path: 'tours',
35:        lazy: () =>
36:          import('@/features/tours').then((m) => ({ Component: m.ToursPage, loader: m.toursLoader })),
39:        path: 'excursions',
41:          import('@/features/tours').then((m) => ({
42:            Component: () => <m.ToursPage lockedKind="excursion" />,
43:            loader: m.toursLoader,
```

Факты:
- `/tours` (строка 36) вызывает `ToursPage` **без** `lockedKind`.
- `/excursions` (строка 42) оборачивает `ToursPage` в анонимный компонент и передаёт
  `lockedKind="excursion"`.
- Лоадер у обоих маршрутов **один и тот же** — `m.toursLoader`, он грузит ВСЕ туры
  (`ToursPage.tsx:10-12`), фильтрация по типу происходит только в рендере.
- Третий маршрут `tours/:slug` (`router.tsx:47`) — страница деталей, к каталогу отношения не имеет,
  но URL-пространством пересекается с `/tours`.

Побочный факт, важный для раздела 4: ветка `lockedKind === 'tour'` в коде **есть, но мертва** —
`ToursPage.tsx:27` и `ToursPage.tsx:31` готовят заголовок «Туры с ночёвкой», однако ни один
маршрут не передаёт `lockedKind="tour"` (проверено поиском по всему `src`: `lockedKind` встречается
только в `router.tsx:42` и внутри самого `ToursPage`).

Из этого следует уже сейчас существующая нестыковка: в меню пункт называется «Туры»
(`Header.tsx:9`), а страница `/tours` показывает заголовок **«Все маршруты»**
(`ToursPage.tsx:27`, ветка `else`) и выводит в списке **и туры, и экскурсии**. То есть
«Туры» и «Экскурсии» в навигации — это не два симметричных раздела, а «весь каталог» и
«каталог, зажатый на экскурсии».

### 1.2. Где живёт состояние вкладки (вопрос 2)

**В URL, в query-параметре `?kind=`.** Ни `useState`, ни контекста.

```
31:    if (value === 'all' || value === null) {

34:      next.set(key, String(value))

```

Решение осознанное и правильное само по себе (ссылка шарится, переживает reload, работает
back/forward) — это зафиксировано в комментарии `useTourFilters.ts:12-18`. Проблема не в том,
где живёт состояние, а в том, что его **перезаписывают на пути к UI**.

### 1.3. Почему нельзя переключиться — точный механизм (вопрос 3)

Вкладка **НЕ задизейблена**, состояние **НЕ теряется при ре-рендере**, `disabled` в
`ToursFilterBar.tsx` вообще нет. Механизм — **двойное затирание значения пропсом маршрута**.

Ключевые две строки, `src/features/tours/ToursPage.tsx`:
```
24:  const scoped = lockedKind ? tours.filter((t) => t.kind === lockedKind) : tours
25:  const visible = applyTourFilters(scoped, lockedKind ? { ...filters, kind: 'all' } : filters)
...
45:          filters={lockedKind ? { ...filters, kind: 'all' } : filters}
```

Пошагово, что происходит при клике на «Туры» на странице `/excursions`:

1. `ToursFilterBar.tsx:44` — `onClick={() => setFilter('kind', value)}`. Обработчик срабатывает,
   ничего не блокирует.
2. `useTourFilters.ts:34,36` — в URL пишется `?kind=tour`. URL **реально меняется** на
   `/excursions?kind=tour`.
3. `ToursPage.tsx:21` — `useTourFilters()` читает обратно `filters.kind === 'tour'`. Значение
   доехало корректно.
4. **`ToursPage.tsx:45`** — в `ToursFilterBar` уходит не `filters`, а `{ ...filters, kind: 'all' }`.
   Выбор пользователя выбрасывается ровно здесь.
5. `ToursFilterBar.tsx:39` — `const active = filters.kind === value`. Так как пришло `'all'`,
   `aria-pressed=true` навсегда остаётся у кнопки «Всё». **Кнопка «Туры» никогда не подсветится**,
   сколько по ней ни щёлкай.
6. **`ToursPage.tsx:24`** — независимо от шага 4 список уже сужен маршрутом:
   `tours.filter((t) => t.kind === 'excursion')`. Даже если бы вкладка подсветилась, содержимое
   не поменялось бы.
7. `ToursPage.tsx:25` — здесь `kind` тоже нейтрализуется в `'all'`, чтобы фильтр не дал пустое
   пересечение. Пустого пересечения нет — но и эффекта от выбора нет.

Итог: **пункт 3 из твоего вопроса — «тип жёстко зашит из маршрута и перекрывает выбор
пользователя»**, причём перекрывает в двух местах сразу (`:24` для данных, `:45` для вида
контрола). Двойного применения фильтра, дающего пустоту, нет.

### 1.4. Почему это выглядит как «сломано», а не как «так задумано»

Замысел автора был другим. Комментарий `ToursPage.tsx:14-18` буквально пишет:

> `lockedKind`, which pre-filters the list and **hides the kind switch**

Но **скрытия нет**: у `ToursFilterBarProps` (`ToursFilterBar.tsx:6-13`) вообще отсутствует проп,
которым можно было бы спрятать группу кнопок. Группа `KIND_OPTIONS` (`ToursFilterBar.tsx:15-19`)
рендерится всегда — все три кнопки, все кликабельные. То есть баг = **задуманное поведение
(«скрыть») не реализовано, а вместо него оставлен видимый неработающий контрол**.

Дополнительный симптом, подтверждающий, что URL всё-таки меняется: `isFiltered`
(`useTourFilters.ts:43`) считается по «сырым» фильтрам, а не по нейтрализованным. Поэтому после
клика по «Туры» на `/excursions` **появляется кнопка «Сбросить»** (`ToursFilterBar.tsx:98-107`),
хотя визуально в списке и во вкладках не изменилось ничего. Это надёжный способ проверить диагноз
руками: клик по «Туры» → в адресной строке появился `?kind=tour`, справа возникло «Сбросить»,
подсветка осталась на «Всё», карточки те же.

### 1.5. Мелкая заметка по консистентности (не баг, но рядом)

Публичный переключатель типа сделан как группа toggle-кнопок: `role="group"` +
`aria-pressed` (`ToursFilterBar.tsx:35-36, 45`). Аналогичный контрол в админке сделан как
радиогруппа: `role="radiogroup"` / `role="radio"` / `aria-checked`
(`TourTypeToggle.tsx:21-22, 33-35`). Для одного и того же смысла («выбери ровно один из N»)
корректнее второй вариант. Если группу типов будут переделывать в рамках объединения разделов —
имеет смысл заодно привести к одному паттерну.

## 2. Баг B — ползунок цены не обновляется в реальном времени

### 2.1. Что это физически (вопрос 1)

**Нативный `<input type="range">`.** Самописных pointer-компонентов здесь нет.

`src/features/tours/components/ToursFilterBar.tsx`:
```
74:        <label className="flex min-w-[210px] flex-1 items-center gap-3 text-sm">
75:          <span className="whitespace-nowrap text-ink-muted">
76:            До {formatPrice(filters.maxPrice ?? priceCeiling, 'USD')}
77:          </span>
78:          <input
79:            type="range"
80:            min={50}
81:            max={priceCeiling}
82:            step={10}
83:            value={filters.maxPrice ?? priceCeiling}
84:            onChange={(e) => {
85:              const value = Number(e.target.value)
87:              setFilter('maxPrice', value >= priceCeiling ? null : value)
88:            }}
89:            className="flex-1 accent-[var(--accent-base)]"
90:            aria-label="Максимальная цена"
91:          />
```

Стилизации ползунка в проекте практически нет: во всём `index.css` `input[type='range']`
встречается только в правилах курсора (`index.css:460` и `index.css:471`). Ни
`::-webkit-slider-thumb`, ни `::-moz-range-track` не переопределены — вид трека и бегунка целиком
браузерный, задан только цвет через `accent-color`. Так что визуально он тоже «старый», как
dropdown из бага C.

### 2.2. Почему значение приходит только на отпускании (вопрос 2)

Ни одного из перечисленных тобой подозреваемых в коде **нет**. Проверено поиском по всему `src`:
`debounce`, `throttle`, `useDeferredValue`, `useTransition`, `flushSync`, `onPointerUp`, `onMouseUp`,
`shouldRevalidate` — **не встречаются ни разу**. Значение контролируемое (`value` на строке 83),
обработчик — `onChange` (строка 84), что для `input[type=range]` в React означает непрерывный
поток на каждое движение. То есть «в лоб» код написан правильно.

Тормоз находится не в контроле, а в **цепочке, по которой значение возвращается обратно в UI**.
Подпись «До $300» (строка 76) и `value` ползунка (строка 83) читаются из **одного и того же
источника** — `filters.maxPrice`, то есть из URL. А запись в URL идёт через полноценную
навигацию React Router:

1. `useTourFilters.ts:36` — `setParams(next, { preventScrollReset: true })`.
2. `node_modules/react-router/.../lib/dom/lib.js:762` — `setSearchParams` внутри делает
   `navigate("?" + newSearchParams, navigateOptions)`. Это **не локальный setState, а навигация**.
3. `node_modules/react-router/.../lib/router/router.js:1965` —
   `else if (currentUrl.search !== nextUrl.search) defaultShouldRevalidate = true;`
   Изменение query-строки по умолчанию **заставляет лоадеры маршрута перезапуститься**.
   Своего `shouldRevalidate`, который бы это отменил, в проекте нет.
4. `ToursPage.tsx:10-12` — `toursLoader` делает `await getTours()`.
5. `shared/api/tours.ts:263-265` — `getTours()` возвращает `delay(TOURS)`;
   `shared/api/tours.ts:20` — `const LATENCY_MS = 260`;
   `shared/api/tours.ts:22-24` — `setTimeout` на эти 260 мс.
   **Каждое движение ползунка стоит 260 мс искусственной задержки.**
6. `node_modules/react-router/.../lib/router/router.js:490` — в начале `startNavigation`:
   `pendingNavigationController && pendingNavigationController.abort();`
   **Новая навигация отменяет предыдущую незавершённую.**
7. `node_modules/react-router/.../lib/components.js:287` — `RouterProvider` отдаёт вниз
   `location: state.location`, то есть **уже закоммиченный** location. Пока навигация в полёте,
   `useSearchParams` возвращает СТАРЫЕ параметры.
8. `node_modules/react-router/.../lib/components.js:145-149` — коммит состояния роутера обёрнут в
   `React.startTransition(...)`, если проп `useTransitions` не равен `false`.
   `App.tsx:10` передаёт в `RouterProvider` только `router`, `useTransitions` не задан → ветка
   `startTransition` активна. Это добавочный слой неприоритетности к уже описанной задержке.
   Обрати внимание: у React Router v8 есть режим `useTransitions={true}`, который включает
   **оптимистичный location** (`components.js:147`, `getOptimisticRouterState`) — сейчас он НЕ
   включён, поэтому оптимистичного обновления URL нет.

**Итоговый механизм.** Пока палец двигается, события идут чаще, чем раз в 260 мс. Каждое новое
событие через `navigate` отменяет предыдущую навигацию (шаг 6), поэтому ни одна не доходит до
коммита. `state.location` не меняется (шаг 7) → `filters.maxPrice` не меняется → подпись «До $…»
и счётчик «Найдено» **стоят на месте**. Бегунок при этом визуально ползёт, потому что его тащит
сам браузер, а React ничего не перерисовывает и не возвращает `value` назад. Как только палец
отпущен, последняя навигация проживает свои 260 мс без отмены, коммитится — и подпись «прыгает»
в новое значение. Это ровно то, что описал Давид.

Уровень уверенности: механизм установлен по исходникам react-router (строки указаны выше) и по
коду проекта. **НЕ ЗАМЕРЕНО** в браузере — профилировщик я не запускал, доступа к браузеру в этой
задаче не было. Проверяется за минуту: временно поставить `LATENCY_MS = 0` в `shared/api/tours.ts:20`
— если ползунок начал обновляться непрерывно, диагноз подтверждён на 100%.

### 2.3. Более тяжёлая проблема в этом же месте (вопрос 3) — да, есть, и не одна

**(а) Полный список туров пересчитывается на каждое движение — причём через сеть/лоадер, а не в
памяти.** Это главное. `applyTourFilters` (`useTourFilters.ts:48-55`) сам по себе дешёвый —
`Array.filter` по 7 элементам. Дорого другое: изменение `?maxPrice` считается навигацией и
перезапускает `toursLoader` (шаги 3–5 выше), который заново «ходит за данными». На моках это
искусственные 260 мс; **когда моки заменят на реальный API — это станет реальным HTTP-запросом
на каждое движение ползунка**. То есть баг сейчас косметический, а после подключения бэкенда
превратится в шквал запросов. Лечить надо до перехода на API.

**(б) Framer Motion на каждый коммит.** `ToursPage.tsx:72-74` — сетка карточек обёрнута в
`<motion.div layout>`, а каждая карточка — `motion.article` с `whileHover`
(`TourCard.tsx:38-41`). `layout` заставляет framer измерять геометрию контейнера на каждом
коммите. При 7 карточках это терпимо, при 50+ из реального API — заметно. Это **вторичная**
причина, не основная: даже с идеальным рендером задержка из п. (а) осталась бы.

**(в) История браузера засоряется.** `useTourFilters.ts:36` вызывает `setParams` **без
`replace: true`**, а дефолт `setSearchParams` — `push` (`lib/dom/lib.js:762` → `navigate(...)` без
`replace`). При перетаскивании большинство навигаций отменяется и в историю не попадает, но
**управление с клавиатуры коммитит каждое нажатие**: 10 нажатий стрелки = 10 записей в истории,
и кнопка «Назад» перестаёт возвращать на предыдущую страницу. Это отдельный, уже сейчас
воспроизводимый дефект.

Отсюда прямая рекомендация по реализации, которую ты и предполагал: **разделить два потока** —
визуальная часть (позиция бегунка + подпись «До $…») обновляется мгновенно из локального
`useState`, а запись в URL/фильтрацию списка делать с задержкой либо на `onPointerUp`/`onChangeEnd`,
и обязательно с `replace: true`, чтобы не плодить историю.

**(г) Отдельный, независимый баг того же контрола: `min={50}` захардкожен.**
`ToursFilterBar.tsx:80` — `min={50}`, при том что потолок выводится из данных
(`ToursFilterBar.tsx:81` + `usePriceCeiling`, `useTourFilters.ts:58-63`). В моках есть позиции
дешевле 50: `shared/api/tours.ts:214` — `priceFrom: 35`, `shared/api/tours.ts:87` —
`priceFrom: 45`. **Эти две экскурсии ползунком не отсекаются в принципе** — минимум фильтра
выше их цены, поэтому «показать только то, что дешевле $40» невозможно. Нижнюю границу надо
выводить из данных так же, как верхнюю.

### 2.4. Клавиатура и `aria-*` (вопрос 4)

- **Клавиатура: работает**, потому что контрол нативный — стрелки/Home/End обрабатывает браузер,
  `tabIndex` не переопределён, `disabled` нет. НО: из-за механизма §2.2 **каждое нажатие стрелки
  стоит ~260 мс до отклика** и добавляет запись в историю (§2.3в). Формально доступно,
  практически — неприятно.
- **`aria-label="Максимальная цена"` есть** (`ToursFilterBar.tsx:90`). Роль `slider`,
  `aria-valuemin/max/now` браузер выводит из `min`/`max`/`value` сам — вручную их дублировать не
  нужно и не нужно.
- **Чего не хватает:**
  1. `aria-valuetext` — скринридер озвучит «300», а не «до 300 долларов». Для ценового фильтра
     это существенно, потому что визуальная подпись `formatPrice` (строка 76) в дерево
     доступности не попадает.
  2. Связи «подпись ↔ контрол» нет. Текст «До $300» лежит в том же `<label>` (строки 74-77), но
     `aria-label` на строке 90 **перекрывает** текст обёртки при вычислении имени, поэтому
     значение из подписи для AT теряется. Правильнее: `<output>` + `aria-describedby`, либо
     `aria-valuetext`.
  3. Живого объявления результата нет: счётчик «Найдено: N» (`ToursFilterBar.tsx:94-96`) не
     обёрнут в `aria-live`, поэтому пользователь скринридера не узнаёт, что список изменился.

## 3. Баг C — нативные dropdown и календарь

### 3.1. Все `<select>` (вопрос 1) — полный список

1. **Мест мало — 5 инстансов в 4 файлах** (4 дропдауна + 1 календарь, §3.1–3.2). Radix/HeadlessUI

2. **Две несовместимые темы.** Публичный сайт — тёмная золото/вино палитра на токенах

   зависимость и её breaking changes останутся.
3. **Инфраструктура уже написана и лучше типового качества** (§3.3): focus trap, scroll lock,
   media query на `useSyncExternalStore`, портал в `Modal`, drag-шторка в `RegionSheet`. Основную
   сложность (a11y-оверлеи и мобильные жесты) проект уже решил — брать библиотеку значит
   выбросить это и получить дублирование.
4. **Требование статической сборки под Netlify и минимума зависимостей.** Каждая новая
   зависимость — это ещё один источник обновлений, который владелец проекта не сможет обслуживать.

Оговорки, которые нужно проговорить честно:
- **Позиционирование попапа у якоря** — единственное место, где своя реализация объективно
  проигрывает. Нужно: переворот при нехватке места снизу, зажатие в границы вьюпорта, поведение
  при скролле. На десктопе это ~60-80 строк. Обходной путь, снижающий риск почти до нуля:
  **на мобильном (`useIsCompactViewport`) открывать шторку снизу, а не попап** — там
  позиционирование не нужно вовсе, а именно на мобиле нативные контролы выглядят хуже всего.
  Ещё вариант — использовать CSS Anchor Positioning / `popover` API, но их поддержка на момент
  реализации **должна быть проверена исполнителем** (я её не проверял — **НЕ ЗАМЕРЕНО**).
- **Календарь.** Сейчас требований нет (§3.2: одно поле, значение никуда не уходит), поэтому
  своя сетка месяца — дешевле и достаточно. Если позже появится бронирование с диапазонами,
  занятыми датами и локалями — **вот тогда** единственный оправданный кандидат
  `react-day-picker`; но его размер и API надо смотреть на момент установки, я их не проверял.
  `date-fns`/`dayjs` для одного поля даты не нужны: формат `YYYY-MM-DD` и арифметика месяца

- **`framer-motion` уже есть** — анимацию открытия/закрытия попапа и шторки брать оттуда, ничего
  доустанавливать не надо. Но учесть предупреждение из прошлого аудита: в `RegionSheet` от framer

### 4.2. Можно ли сохранить старые URL — да, и это дешевле, чем кажется

**Рекомендация: да, сохранить оба URL, реализовав их как редирект на новый раздел с
предустановленным `?kind=`.**

Схема:
```
/<новый-раздел>                  — каноническая страница каталога, фильтр из ?kind
/tours        → redirect → /<новый-раздел>?kind=tour
/excursions   → redirect → /<новый-раздел>?kind=excursion
/tours/:slug                     — НЕ ТРОГАТЬ, остаётся как есть
```

Почему именно редирект, а не «два пути, рендерящих один компонент»:
1. **Одна каноническая страница.** Иначе один и тот же список доступен по трём URL — это и
   SEO-дубликаты, и повод для той же ошибки, что в баге A (страница знает про себя из маршрута и
   спорит с фильтром).
2. Редирект в React Router data-mode делается **лоадером маршрута** (`redirect()` из
   `react-router`) — это ~3 строки на маршрут, никакой серверной конфигурации не требуется,
   работает на статике Netlify как есть. Существующий `netlify.toml` уже даёт SPA-fallback
   (`router.tsx:19-20`), поэтому прямой заход на `/excursions` попадёт в приложение и там
   отработает редирект.
3. Старые ссылки, которые Давид уже отправлял, продолжат работать и приведут человека на список
   с уже выбранным нужным типом.

**Важное следствие про `/tours`:** сегодня `/tours` показывает **весь каталог**, а не только туры
(§1.1). Если сделать `/tours → ?kind=tour`, поведение этого URL изменится. Два варианта, нужен
выбор Давида:
- **(а)** `/tours → ?kind=tour` — семантично, соответствует названию, но люди, у которых
  `/tours` в закладке как «весь каталог», увидят сузившийся список.
- **(б)** `/tours → без фильтра` (весь каталог), `/excursions → ?kind=excursion` — сохраняет
  сегодняшнее фактическое поведение обеих ссылок один в один. Асимметрично, зато нулевой риск
  для уже отправленных ссылок.

Я рекомендую **(б)** — потому что она не меняет наблюдаемое поведение ни одного существующего
URL, а вся асимметрия остаётся в двух строках лоадеров-редиректов и наружу не протекает.

**Про имя нового раздела.** Имя выбирает Давид. С архитектурной стороны есть только одно
ограничение: **новый путь не должен быть `tours`**, иначе он столкнётся с уже существующим
`tours/:slug` (`router.tsx:47`) и потребует их вложения друг в друга — лишнее усложнение. Любое
другое слово (`/catalog`, `/routes`, `/travel`, `/marshruty`, …) конфликтов не даёт. Если Давид
всё-таки захочет `tours` как имя объединённого раздела — это делается вложенными маршрутами
(`path: 'tours'` с `index` для каталога и `:slug` для деталей), но тогда `/excursions` остаётся
единственным редиректом, а «предустановленный фильтр для /tours» теряет смысл (вариант (а)
становится невозможен).

### 4.3. Меню: 2 пункта или 1

При объединении пункты `Header.tsx:9-10` и `Footer.tsx:30-35` сворачиваются в один. Есть
компромиссный вариант: **один пункт в меню, но с двумя быстрыми ссылками** (`?kind=tour` /
`?kind=excursion`) — на десктопе как подменю, на мобиле как два вложенных пункта. Стоит ли —
решает Давид: с точки зрения архитектуры оба варианта одинаково дешёвы, потому что фильтр уже
в URL и ссылка с `?kind=` — это готовый deep-link без единой строки нового кода.

Два решения из этого раздела значимые и не читаются из кода — их место в

## 6. Развилки — нужно решение Давида

1. **Имя объединённого раздела.** Единственное ограничение — не `tours` (конфликт с
   `tours/:slug`, §4.2).
2. **Поведение старого `/tours`:** вариант (а) `?kind=tour` (семантично) или (б) без фильтра
   (сохраняет сегодняшнее поведение). Рекомендация — (б), §4.2.
3. **Меню: один пункт или один пункт + два быстрых фильтра** (§4.3). Оба варианта одинаково дешёвы.
4. **Ползунок: «непрерывно, но список с задержкой» или «непрерывно всё»?** Второе возможно, если
   фильтровать в памяти и не гонять через лоадер, — но это уже изменение того, как каталог
   получает данные (§2.3а), и его лучше делать одновременно с переходом с моков на реальный API.
5. **Календарь: своя сетка месяца или `react-day-picker`?** Рекомендация — своя, потому что
   требований к дате сейчас нет вообще и она никуда не отправляется (§3.2). Пересмотреть, когда
   появится реальное бронирование.
6. **Шторка (`Sheet`) в `shared/ui/`** — это рефактор уже работающего кода региона. Делать сразу
   вместе с задачей C или отложить и временно продублировать? Рекомендация — сразу: дублировать
   200+ строк drag-логики дороже.
