# Модель продукта (тур / экскурсия / трансфер)

Продукт — это тур, экскурсия или трансфер. Все три хранятся как `Tour` с полем `Type`
(`TourType { Tour = 1, Excursion = 2, Transfer = 3 }`), отдельных сущностей нет.

## Домен: тур vs экскурсия vs трансфер
- **Экскурсия** — ровно 1 день (без ночёвки).
- **Тур** — 2 дня и более (минимум 1 ночёвка).
- **Трансфер** (2026-08-29) — перевозка из точки A в точку B, дней у него нет вовсе; см.
  «Трансфер — третий тип продукта».
- Тип **неизменяем после создания** (тур нельзя превратить в экскурсию и наоборот). В форме редактирования тумблер типа заблокирован; бэкенд тоже отклоняет смену типа (400).

## Форма (`src/features/admin/tour-form/`)
Состоит из всегда видимой шапки (`TourFormHeader`) и карточки с вкладками. Состояние — `useReducer` (`useTourForm`), без form-библиотек. Конвертация wire ↔ view-model только в `lib/tourMapper.ts`.

**Шапка**: тип, главная картинка (URL), заголовок/краткое описание/описание/длительность (RU+EN), публикация, цена.

**Вкладки**:
- **Тур**: `Дни` (аккордеон дней) + `Организационные детали` + `Ограничения` + `Доп. расходы`.
- **Экскурсия**: вкладки `Дни` **нет**. Единственный день = сам тур, поэтому:
  - цена — редактируемый инпут прямо в шапке;
  - точки маршрута и галерея единственного дня — секциями под шапкой;
  - заголовок/описания шапки автоматически становятся текстами дня (унификация при отправке — `dayTexts()` в `tourMapper`), чтобы не заполнять дважды.

## Цена
- **Тур**: цена в шапке — read-only сумма цен всех дней (цена вводится в каждом дне).
- **Экскурсия**: цена вводится в шапке и пишется в единственный день.
- На бэке `TotalPrice` считается на запись (Σ цен дней) при create/update. Хранится и
  редактируется в администрации **только в AMD** — мультивалютность и тирная наценка по
  кол-ву гостей (1-4/5-6/7+) существуют только на публичном сайте как отображение поверх
  этой базовой цены, не как отдельное поле в БД (см. `client-site.md#мультивалютность`).

## Валидации (фронт + бэк)
Обязательные/блокирующие:
- заголовок продукта (RU) и главная картинка;
- для тура — минимум 2 дня; заголовок RU каждого дня (у экскурсии день наследует шапку — не проверяется отдельно);
- **цена не может быть отрицательной** (каждый день);
- **минимум 1 точка маршрута** в каждом дне (в т.ч. в единственном дне экскурсии);
- **тип неизменяем** при редактировании.

Фронт: ошибки скрыты до первой попытки сохранения (`hasAttemptedSubmit`), затем показываются вживую (`lib/validation.ts`). Бэк дублирует правила в `TourValidationService` (работает и на create, и на update) + запрет смены типа в `TourUpdateService`.

## Архив
Мягкое удаление (soft-delete) через флаг `IsArchived` — отдельно от `IsActive` (публикация на сайте):
- **В архив**: `SetArchived(id, true)` — тур исчезает из основного списка (`GetAll`), появляется в `GetArchived`.
- **Восстановить**: `SetArchived(id, false)`.
- **Удалить окончательно**: `DeleteTour(id)` — безвозвратно, только из архива, с подтверждением в UI.

## Избранное (2026-08-02)
Отдельно от `IsActive`/`IsArchived`: `Tour.IsFeatured`(bool) + `FeaturedSortOrder`(int) — показ в секции «избранное» на главной публичного сайта. Управляется только через `PATCH SetFeatured`/`PATCH ReorderFeatured` (`api/Tour`), не через `UpdateTour`. Не более **9** продуктов одновременно (было 6, расширено 2026-08-29 вместе с трансферами — они тоже участвуют в избранном, решение 0.5 батча) — сервер отклоняет лишний (`TooManyFeaturedTours`/2011, лимит в `TourFeaturedService`), админка (`Продукты → Избранные`, `MAX_FEATURED = 9` в `ProductsPage.tsx`) дизейблит сердечко на остальных продуктах, когда лимит достигнут. Публичная секция показывает **ровно то, что отмечено**, в заданном порядке — без «первых N туров» как фолбэка и без плейсхолдеров при пустом наборе (секция целиком скрыта, если ничего не отмечено).

## Предоплата (2026-08-13)
`Tour.RequiresPrepayment` (bool, `HasDefaultValue(true)` + `ValueGeneratedNever()` — см. `backend-api.md`) — показывать ли на публичной странице тура (`BookingCard`) блок «Предоплата 20%». Сумма предоплаты по-прежнему единая глобальная константа (`PREPAYMENT_SHARE` во фронтовом `useTierPrice.ts`) — это поле только видимость блока, не per-tour процент. Редактируется прямо через `UpdateTour` (в отличие от `IsActive`/`IsFeatured`, которые он игнорирует) — чекбокс «Требуется предоплата» в `TourFormHeader.tsx`. Новый тур создаётся с `true` (задаётся в `TourInitializationService`), сохраняя прежнее поведение «предоплата всегда» по умолчанию.

## Теги продукта (2026-08-16, скидка выведена из тегов 2026-08-16 Фаза 3)
Мерч-теги на карточке ("Хит сезона", …) — отдельная сущность `Tag` (каталог, управляется в Справочниках), назначается тур-продукту через join `TourTag`. До 3 тегов на продукт — правило живёт и на фронте, и на бэке (`TourValidationService`, окончательный источник правды).

Один тип тега (`TagType`): **Regular** — чисто декоративный, никак не влияет на цену. Тип `Discount` **удалён из enum** (`checklist-orders-redesign.txt`, Фаза 3) — скидка тура больше не тег, см. «Скидка тура» ниже. `Tag.DiscountPercent`, ограничение «максимум 1 Discount-тег» и код ошибки `MultipleDiscountTags` тоже убраны вместе с типом.

**Текст тега — то, что ввёл админ, без изменений.** Цвет — один из 5 preset-токенов сайтовой палитры, не свободный hex.

## Скидка тура (2026-08-16, диапазон дат добавлен 2026-08-18)
`Tour.DiscountPercent` (decimal? 1–100) + `Tour.DiscountStartDate` (DateOnly?) + `Tour.DiscountValidUntil` (DateOnly?) — три поля напрямую на туре, не через тег. Все три обязательны вместе или все три `null` (`TourValidationService`, `InvalidTourDiscount`/2025), плюс `DiscountStartDate <= DiscountValidUntil` (равенство разрешено — однодневная акция).

Скидка активна на дату D, если `DiscountStartDate <= D <= DiscountValidUntil` включительно (`TourDiscountExtensions.IsDiscountActive`). Два разных «сегодня»:
- **Витрина** (карточка/детальная тура, `DiscountedPrice`) — резолвится на СЕГОДНЯШНЮЮ дату.
- **Бронирование** (`OrderLine.DiscountPercent`/`LineTotal`, `OrderCreationService`/`OrderLineService`) — резолвится на дату САМОГО ТУРА (`OrderLine.TourDate`), не на дату оформления заказа. До 2026-08-18 оба места по ошибке использовали дату оформления заказа — бронь на день вне диапазона скидки всё равно получала скидку; исправлено.

`TourDiscountExtensions.ApplyDiscount` возвращает `null` (не исходную цену), когда скидка не активна — контракт «`DiscountedPrice == null` значит скидки нет» соблюдается строго с 2026-08-18 (до этого баг: возвращалась обычная цена, и фронт по ошибке рисовал скидочную вёрстку на турах без скидки).

Скидка снапшотится в момент бронирования (`OrderLine.DiscountPercent`/`PriceSnapshot`/`LineTotal`) — последующая правка/удаление скидки тура не меняет задним числом уже оформленные брони, тот же принцип, что у `TourPriceSnapshot`.

Календарь бронирования (`shared/ui/DatePicker.tsx`) показывает красную ленту с процентом («-15%») на днях внутри диапазона скидки — см. `client-site.md#скидка-тура-и-календарь-2026-08-18`.

## Переводы
Каждое текстовое поле двуязычное (RU+EN). На бэке — плоский список `{Type, LanguageCode, Value}` (2 строки на поле). В форме — `Localized {ru, en}`. Разворот/сборку делает только `tourMapper.ts`.

Двуязычные упорядоченные списки (точки маршрута дня, орг.детали, ограничения тура) используют общий тип `LocalizedListItem` и общий компонент `LocalizedListEditor`. Реордер — drag-and-drop мышью/тачем/клавиатурой через общий примитив `shared/ui/SortableList.tsx` (+`DragHandle`, на `@dnd-kit`), не кнопки ▲▼ (убраны 2026-08-01). Дни тура (`TourDaysEditor`/`TourDayCard`) и галерея дня (`GalleryImagesEditor`) используют тот же примитив. Редьюсер адресует реордер по индексам (`{fromIndex, toIndex}` → `arrayMove`), а не по направлению — единственное намеренное исключение из правила «списки адресуются по `key`, не по индексу» (см. `tourFormReducer.ts`).

**Автодополнение из справочников (2026-08-01).** Точки маршрута, орг.детали, ограничения
(`LocalizedListEditor`) и доп.расходы (`AdditionalExpensesEditor`) подсказывают существующие
записи справочника, пока печатаешь — это не `Select` (значение не ограничено списком): свободный
текст остаётся всегда, подсказка — только ускоряющий шорткат. Компонент `shared/ui/SuggestInput.tsx`
(текстовый `Input` + `Popover`-панель, тот же паттерн наведения-и-клика, что у листбокса `Select`)
подключён к RU- и EN-полю по отдельности, список кандидатов — по подстроке (`includes`,
регистронезависимо), пустой ввод при фокусе показывает все варианты (до 20). Выбор подсказки
заполняет **сразу оба языка** через `onChangeText`/`onChangeDescription` — поле остаётся
редактируемым дальше. Источник подсказок — три каталога (`Place`/`ExpenseTemplate`/
`TourNoteTemplate`, последний фильтруется по `TourNoteType` для орг.деталей и ограничений
раздельно), грузятся в лоадере `tourCreateLoader`/`tourEditLoader` параллельно с самим туром
(`CatalogSuggestions` в `types/form.ts`), маппинг — `placesToSuggestions`/
`expenseTemplatesToSuggestions`/`noteTemplatesToSuggestions` в `lib/tourMapper.ts` (переиспользует
`readLocalized(translations, 0)` — каталоги всегда кодируют название переводом `type: 0`).

## Формат продукта: индивидуальный / групповой / оба (2026-08-29)
`Tour.Format` (`TourFormat { Individual = 1, Group = 2, Both = 3 }`, nullable) — **обязателен у
тура/экскурсии и запрещён у трансфера** (`InvalidTourFormat`/2050, оба нарушения одним кодом:
это «формат не соответствует типу продукта»). Существующим продуктам миграция проставила
`Individual` — фиксация того, как цена считалась до батча, а не смена поведения.

- **Individual** — прежняя схема: `TotalPrice` это фикс за группу, поверх него тирная наценка по
  числу гостей 1-4 / 5-6 / 7+ (на 7+ цена скрыта, «по запросу»).
- **Group** — `Tour.GroupPricePerPerson` × количество гостей, **без тиров и без скрытия цены**.
  Ограничитель — свободные места, а не тир.
- **Both** — продукт продаётся в обоих; какой применить, выбирает клиент при бронировании, и
  выбор снапшотится в `OrderLine.Format`. Строка без формата у такого продукта отбивается
  (`OrderLineFormatRequired`/2046) — молча посчитать по индивидуальному нельзя.

`GroupPricePerPerson` (decimal?) и `GroupCapacity` (int?) обязательны вместе при `Group`/`Both`
и обязаны быть `null` при `Individual` и у трансфера (`InvalidGroupPricing`/2051).
`GroupCapacity` — «мест на выезд», **одно число на весь продукт**; занятость же считается на пару
(дата + время старта), см. ниже. Две цены на одной форме не выводятся друг из друга: «цена за
группу» (`TotalPrice`, сумма цен дней) и «цена за человека» — независимые поля.

Расчёт строки живёт в одном месте на бэке (`OrderLinePricing`, `ATTours.Service/Services/Shared/`)
и продублирован на фронте (`shared/booking/format.ts`) — порядок операций одинаковый и
переставлять его нельзя: **базовая цена по формату → скидка на дату поездки → формат/тир**.

## Время начала — коллекция слотов (2026-08-29)
`TourStartTime { TourId, Time (TimeOnly), SortOrder }` — предопределённые времена начала, которые
задаёт админ. Клиент на сайте выбирает **одно из них** и изменить не может; выбор снапшотится в
`OrderLine.StartTime` (снапшот, а не FK: правка расписания продукта не должна менять уже
оформленную бронь).

- **Минимум одно время обязательно** у тура/экскурсии и **ни одного** у трансфера — там время
  подачи вводит сам клиент (`InvalidTourStartTimes`/2052). Правило строгое и на фронте, и на бэке.
- Выбор вне списка отбивается (`InvalidStartTimeSelection`/2045); исключение только для старых
  строк заказа с `StartTime == null`, чтобы уже оформленные брони остались редактируемыми.
- `SortOrder` задаёт порядок показа — сортировка по самому времени не подразумевается.
- Для группового формата пара (дата + время старта) — тот ключ, по которому считается остаток
  мест из `GroupCapacity`: один продукт 12-го в 09:00 и 12-го в 14:00 это два независимых выезда.
- `TimeOnly` без даты и таймзоны (тот же выбор, что `DateOnly` у `OrderLine.TourDate`). На фронте
  единственная каноничная форма — `HH:mm` (`shared/booking/startTime.ts`), на проводе `HH:mm:ss`.

Миграция `AddTransfersProductFormatAndStartTimes` посеяла существующим продуктам одно время
`09:00`, чтобы они не стали нередактируемыми на полпути; следующая миграции
`RemoveSeededDefaultStartTimes` этот сид удалила ровно одним `DELETE FROM [TourStartTime] WHERE
[Time] = '09:00:00'` — решение 0.28 (продукты и заказы не тронуты, реальное расписание админ
заводит руками).

## Трансфер — третий тип продукта (2026-08-29)
`TourType.Transfer = 3`. Отдельной сущности нет: трансфер живёт в том же экране «Продукты» и в
той же форме, тип выбирается **только при создании** (как и у тура/экскурсии — тип неизменяем).

Из «богатства» тура у трансфера остаётся **только главная картинка** (`TransferMainImageRequired`
/2056 — она обязательна) **и участие в «Избранном»**. Нет: дней, галереи, регионов, тегов, скидки,
орг.деталей, ограничений, доп.расходов, формата, времён старта — попытка прислать любое из них
отбивается `TransferFieldNotAllowed`/2055.

**Маршрут** — `TransferRoutePoint { TourId, Kind (TransferRoutePointKind { From = 1, Stop = 2,
To = 3 }), SortOrder }` + `TransferRoutePointTranslation` (RU/EN). Ровно одна точка `From` и ровно
одна `To`, между ними сколько угодно `Stop` (`InvalidTransferRoute`/2053). Отдельно от `RoutePoint`
дня тура: та висит на `TourDayId` и ссылается на каталог `Place`, эта — прямо на продукте и знает
роль точки. **FK на `Place` нет намеренно** (решение 0.8): текст свободный, каталог даёт только
подсказки в `SuggestInput`, а не строгий выбор.

**Цена** — `TransferPrice { TourId, VehicleClassId, OneWayPrice, RoundTripPrice }`, то есть на
связке «трансфер × класс авто», а не в `Tour.TotalPrice`: у одного трансфера столько цен, сколько
на нём заведено классов. **Две цены — независимые поля**: `RoundTripPrice` задаёт админ, это НЕ
`OneWayPrice × 2` (обратный рейс обычно продаётся дешевле двух отдельных). Минимум один класс,
обе цены строго положительные (`InvalidTransferPrices`/2054).

**Классы авто** — новый общий справочник `VehicleClass { Capacity, LuggageCapacity, SortOrder,
IsActive }` + `VehicleClassTranslation` (RU/EN), по образцу `Tag`. `Capacity` — мест без водителя,
`LuggageCapacity` — лимит багажа в «единицах» (средний чемодан = 3, большой = 5). Класс, который
уже участвует в `TransferPrice` или в строке заказа, удалить нельзя (`CatalogEntryInUse`/2010 +
FK `Restrict`) — такой класс скрывают флагом `IsActive`.

Публично трансферы видны только на `/transfers` (+ секция «Избранное» на главной): из
`GetToursClient` они исключены фильтром по типу, а `GetTourInfo` отвечает на трансфер 404 — см.
`backend-api.md`, `client-site.md`.
