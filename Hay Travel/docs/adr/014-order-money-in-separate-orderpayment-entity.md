# ADR 014 — Денежная часть заказа вынесена в отдельную сущность `OrderPayment` (1:1), не owned-type и не плоские колонки

Автор: `backend-architect`. Дата: 2026-08-11.
Статус: принято. Реализацию делает `backend-developer` по спецификации
`docs/specs/001-booking-calendar-backend.md`.

## Контекст

`Order` хранит снапшот цены на момент заказа и сумму предоплаты. Платёжного шлюза сейчас нет —
предоплата это просто число, ничего не списывается. Требование Давида: архитектура обязана
оставить чистую точку расширения, чтобы позже подключить реальный шлюз **без переделки `Order`
с нуля**.

## Развилка

**A. Плоские колонки в `Order`.** `TourPriceSnapshot`, `TotalAmount`, `PrepaidAmount`, `Currency`
лежат прямо в таблице `Order` вперемешку с `UserId`, `TourDate`, `GuestCount`, `Status`.

**B. EF Owned Type.** Отдельный C#-тип `OrderMoney` через `builder.OwnsOne(...)` — колонки всё
равно в таблице `Order`, но сгруппированы в объекте.

**C. Отдельная сущность `OrderPayment` (1:1, свой `Id`, FK `OrderId`) — выбрано.**

## Решение — C

`OrderPayment : EntityBase` с собственным `Id`, `OrderId` (unique, 1:1), навигация
`Order.Payment`. Каскадное удаление от `Order`. Все денежные поля — здесь:
`TourPriceSnapshot`, `TotalAmount`, `PrepaidAmount`, `Currency`.

## Почему C, а не B и не A

1. **Точка расширения под шлюз.** Подключение реального провайдера добавляет платёжные атрибуты
   (`ProviderName`, `ProviderTransactionId`, `PaymentStatus`, `PaidAtUtc`, при необходимости —
   дочерняя коллекция `PaymentTransaction` под retry/refund). С отдельной таблицей это рост
   `OrderPayment`, **без единого изменения `Order`** и без раздувания его строки редко нужными
   колонками. Именно этого требует задача.
2. **Owned-type в проекте нет ни одного (B отпадает).** `grep OwnsOne/OwnsMany` по
   `ATTours.Common` — пусто. Вводить owned-type ради одной сущности — новый, не проверенный
   в проекте механизм со своими ловушками (nullable owned, трекинг, split-таблицы). Проект
   вместо этого последовательно использует **сущности со своим `Id`**: даже join `TourRegion`
   сделан со своим `Id`, а не композитным ключом, именно чтобы работать с общей инфраструктурой
   (`ReconcileCollection<T> where T : IEntity`) — см. `backend-stage3-architecture.md` §3.2.1.
   `OrderPayment` ложится в ровно тот же паттерн.
3. **Граница «деньги ≠ остальной заказ» (A отпадает).** Плоские колонки смешивают коммерческие
   термины с операционными полями бронирования; при появлении шлюза таблица `Order` начинает
   расти платёжными деталями, к которым логика бронирования отношения не имеет. Отдельная
   таблица держит границу явной.

## Цена решения

- Чтение заказа требует `Include(o => o.Payment)` — одна ветка графа. Дёшево.
- 1:1 обеспечивается unique-индексом на `OrderPayment.OrderId`; создаётся всегда вместе с
  `Order` в одной транзакции (`OrderCreationService`), «заказа без денег» не существует.

## Что сознательно НЕ делаем сейчас

- Никаких платёжных статусов/транзакций/полей провайдера — их добавит будущая волна вместе с
  интеграцией шлюза. Сейчас `OrderPayment` — только снапшот суммы и предоплаты.
- `PrepaidAmount` вычисляется в `OrderCreationService` (сейчас — по умолчанию `0`, реальная
  политика предоплаты — будущий seam там же); поле уже существует и готово принять значение.
- `Currency` хранится строкой ISO-4217 со значением по умолчанию `"AMD"` (базовая цена на бэке
  всегда в AMD — см. `product-model.md#цена`). Мультивалютность остаётся отображением на фронте.
