# ADR 022 — Корзина публичного сайта: клиентский накопитель

- Дата: 2026-08-22
- Статус: Принято, **частично отменён [ADR 025](025-cart-checkout-single-multiline-order.md)**
  (2026-08-22, в тот же день)
- Связанные: ADR 007 (module-level auth store), ADR 009 (module-level currency store),
  ADR 019 (Order стал мультистрочным), ADR 025 (чекаут = один мультистрочный заказ),
  спецификации `docs/specs/008-cart-frontend.md`, `docs/specs/013-cart-checkout-backend.md`

> **Что из этого ADR отменено.** Первая редакция выбирала вариант «бэкенд не трогаем, а на
> чекауте фронт последовательно создаёт N одиночных заказов, по одному на позицию, и частичный
> успех — штатный исход». Давид развернул этот компромисс прямым решением: «всё, что in cart, в
> out становится одним order — 4 тура → 1 order», плюс жёсткая атомарность. Бэкенд-архитектор
> оформил новый контракт в ADR 025 / spec 013.
>
> **Остаётся в силе** (и это основная часть ADR): корзина — состояние фронтенда, а не сущность
> домена; module-level observable store + `useSyncExternalStore`; localStorage; `shared/cart` vs
> `features/cart`; переезд `useTierPrice`/`tourDiscount`/`bookingWindow` в `shared/booking`.
>
> **Заменено разделом «Чекаут» ниже**: способ отправки корзины на сервер.

## Контекст

Сегодня бронирование на публичном сайте одношаговое: `features/tours/components/BookingCard.tsx`
на странице тура собирает дату + число гостей и сразу вызывает `POST api/Order/Create`. Один тур —
один заказ, никакого промежуточного состояния.

Требование Давида: тур со страницы тура должен *добавляться в корзину*, а где-то на сайте должен
быть экран чекаута со списком всего выбранного и одной кнопкой отправки заявки. Дата и число
гостей задаются при добавлении, но должны оставаться редактируемыми в самой корзине. Корзина
работает у анонимного гостя; вход требуется только на шаге отправки. UI — отдельная страница
`/cart`, иконка в шапке — просто ссылка со счётчиком.

## Развилка 1 — где живёт корзина

Три варианта, которые реально рассматривались:

1. **Один мультистрочный заказ на всю корзину** — требует изменения бэкенда.
2. **Серверная корзина** (черновой `Order` в статусе «корзина», строки добавляются по одной).
   Требует новой сущности/статуса, авторизации при добавлении (то есть анонимной корзины не
   будет) и уборки брошенных черновиков.
3. **Клиентский накопитель** — корзина живёт только на устройстве (localStorage), а на чекауте
   уезжает на сервер одним действием.

## Решение 1 — клиентский накопитель (в силе)

**Корзина — это состояние фронтенда, а не сущность домена.** Никаких серверных черновиков, ничего
не уходит на бэкенд до нажатия «Отправить заявку».

Следствия:

- **Корзина работает у анонимного посетителя.** Вход требуется только на шаге отправки, и
  `?returnTo=/cart` не несёт никаких параметров выбора: корзина в localStorage переживает поход на
  `/auth` сама. Вся механика `?date=&guests=` из `BookingCard` перестаёт быть нужной для
  восстановления выбора — это самое крупное упрощение, которое даёт корзина.
- **Корзина не синхронизируется с аккаунтом** и не очищается при выходе: она привязана к
  устройству, персональных данных не содержит, серверного аналога у неё нет — мержить нечего.
- Корзина не переносится между устройствами. Для сайта, где заявка — это начало разговора с
  менеджером, а не оплата, это приемлемо.

## Решение 2 — чекаут (заменено ADR 025)

**Одна корзина = один мультистрочный заказ, атомарно, одним HTTP-запросом.**

`POST api/Order/Create` принимает `{ lines: [{ tourId, tourDate, guestCount }, …] }` и создаёт один
`Order` с N `OrderLine` одним `SaveChanges` (ADR 025, spec 013). Клиентские следствия:

- **Частичного успеха не существует.** Либо создан один заказ с одним номером, либо не создано
  ничего. Экран «часть принята, часть нет» из первой редакции этого ADR невалиден.
- **При отказе корзина остаётся нетронутой.** Ничего не удаляется, потому что ничего и не создано.
  Сервер возвращает пер-строчный список ошибок (`errorCode: 2031` + массив
  `lines: [{ index, tourId, tourDate, errorCode }]`), фронт раскладывает их по строкам корзины и
  показывает причину инлайн у каждой отклонённой позиции. Посетитель правит и жмёт «Отправить»
  снова.
- **При успехе корзина очищается целиком** (`clearCart()`), экран результата показывает один номер
  заказа.
- **401/сессия** больше не является особым случаем «посреди цикла»: единственный запрос просто
  падает, посетителя отправляют на `/auth?returnTo=/cart`, корзина как была цела в localStorage,
  так и остаётся.
- **Лимит 10 позиций сохраняется** и теперь зеркалится бэкендом (`OrderTooManyLines` 2032): это
  ограничение размера одного заказа, а не количества запросов.

Что это выкидывает из первой редакции: последовательный цикл `createOrder()`, поштучное удаление
позиции после её успешного создания как защиту от дублей, правило «созданный заказ не
откатывается», разделение исходов на `allCreated`/`partial`/`noneCreated`.

## Развилка 2 — чем хранить состояние корзины на клиенте

Стор корзины реализуется как **module-level observable + `useSyncExternalStore`** — тем же
идиомом, что `shared/auth/authStore.ts` (ADR 007) и `shared/currency/currencyStore.ts` (ADR 009).
Причины те же и здесь усиливаются:

- `cartLoader` (route loader React Router) обязан прочитать корзину **до рендера**, вне React —
  ровно ради этого ADR 009 и выбрал модуль вместо провайдера;
- корзину читают два независимых поддерева (`RootLayout` и страница `/cart`) и мутирует
  не-React код;
- один идиом стора на кодовую базу: третий способ хранить состояние — это цена, которую платят
  все последующие правки.

Zustand в зависимостях нет и добавляться не будет ради одного стора.

## Где живёт стор

`src/shared/cart/`, не `src/features/cart/`. `features/tours/BookingCard` кладёт позицию,
`features/cart/CartPage` читает и мутирует, `app/layout` рисует бейдж. Фичи не импортируют друг
друга — значит общее состояние обязано лежать в `shared`. Это в точности связка
`shared/auth` (стор) + `features/auth` (экраны), которая уже есть в проекте.

## Повышение `useTierPrice`/`tourDiscount`/`bookingWindow` до `shared/booking`

`features/tours/hooks/useTierPrice.ts` документирован как «feature-local, not shared: the group
tier only applies where a live guest counter exists, which is that one component». С появлением
корзины это утверждение становится фактически неверным — живой счётчик гостей есть в каждой
строке `/cart`. Дублировать правило тарифных ступеней и правило скидки по дате запрещено самим же
кодом (`shared/currency/pricing.ts`: «The group-tier rule lives HERE and nowhere else»).

Поэтому три модуля переезжают в новый лист `src/shared/booking/` без изменения содержимого:
`bookingWindow.ts`, `tourDiscount.ts`, `useTierPrice.ts` (+ новый `guests.ts` с границами 1..16,
которые сейчас — локальные константы `BookingCard`). Импортёров всего два файла, миграция
механическая.

`shared/api/booking.ts` (транспорт) остаётся на месте: перенос его под `shared/booking/` затронул
бы несвязанные вызовы ради симметрии имён и ничего не дал бы. Его сигнатура при этом меняется по
ADR 025 — `createOrder` начинает принимать список строк.
