# ADR 015 — Клиентская копия `ClosureRuleResolver` в админ-календаре

Дата: 2026-08-11. Автор: `frontend-architect`. Статус: принято.
Связанные: [ADR 012](012-closure-rules-stored-as-rules-not-materialized-dates.md),
[spec 001](../specs/001-booking-calendar-backend.md), [spec 003](../specs/003-calendar-frontend.md).

## Контекст

Закрытие дней хранится правилами (`ClosureRule`), а не материализованными датами (ADR 012).
Эффективное состояние дня вычисляет сервер: `GetCalendar` возвращает по каждому дню
`isClosedGlobally` + `closedTourIds`, `GetClosedDates` — плоский список закрытых дат тура.

Проблема появляется не при отображении, а при **мутации**. Админ в панели дня нажимает
«Открыть день». Что именно надо отправить на сервер — зависит от того, чем этот день закрыт:

- закрыт правилом `SpecificDate/Close` на эту дату → надо **удалить** это правило;
- закрыт правилом `Weekly/Close` (например «все понедельники») → удалять нечего, надо **создать
  исключение** `SpecificDate/Open` на эту дату;
- закрыт глобально, а закрывают конкретный тур → нужно правило другой области.

Бэкенд заморожен (spec 001, §8: редактирование правил не предусмотрено, только Create bulk и
Delete; эндпоинта «сделать день открытым» нет). То есть план мутации обязан построить клиент.

Чтобы построить план, нужно ответить на вопрос «если удалить правила `SpecificDate` на эту дату,
останется ли день закрытым?» — а это и есть precedence-логика резолвера
(`Tour+SpecificDate > Global+SpecificDate > Tour+Weekly > Global+Weekly`).

## Рассмотренные варианты

1. **Просить бэкенд добавить эндпоинт `SetDayClosed(date, tourId, isClosed)`.** Правильно по
   слоям, но бэкенд-спека уже зафиксирована и реализуется; фронт-задача блокируется на чужой
   волне. Отклонено по срокам, а не по существу.
2. **Оптимистичный «слепой» toggle: всегда создавать `SpecificDate` правило нужного действия.**
   Открыть день = создать `Open`-исключение, закрыть = создать `Close`. Не требует резолвера,
   но за месяц активного использования порождает мусорные правила-дубликаты (нажали «закрыть»,
   потом «открыть», потом снова «закрыть» — три правила на одну дату), и список «Правила»
   становится нечитаемым. Отклонено.
3. **После каждого нажатия перезапрашивать месяц и, если не сработало, отправлять второй
   запрос.** Две сетевые итерации на одно нажатие и видимое «мигание» состояния. Отклонено.
4. **Чистая клиентская копия резолвера, используемая ТОЛЬКО для планирования мутации.** Принято.

## Решение

В `features/admin/calendar/lib/closureResolver.ts` живёт чистая функция
`resolveClosure(rules, dateISO, tourId)` — построчный порт `ClosureRuleResolver.IsClosed`
(precedence из ADR 012). Поверх неё `lib/closureToggle.ts` строит план
`{ deleteIds: number[]; create: ClosureRuleCreateModel[] }`.

Границы использования зафиксированы жёстко:

- **Отображение** (бейдж «закрыто» в клетке, гашение дат в `BookingCard`) берётся ТОЛЬКО из
  ответа сервера (`CalendarMonthModel`, `GetClosedDates`). Клиентский резолвер в рендер не ходит.
- **Планирование мутации** — единственный потребитель клиентского резолвера.
- После применения плана состояние перечитывается с сервера (инвалидация кэша месяца), то есть
  сервер остаётся источником истины, даже если копия разойдётся с оригиналом.

## Последствия

- Логика продублирована в двух местах (C# и TS) — риск дрейфа. Смягчение: (а) копия изолирована
  в одном файле, в шапке которого стоит ссылка на `ClosureRuleResolver.cs` и ADR 012 с явным
  требованием менять оба файла вместе; (б) расхождение не может привести к неверному ОТОБРАЖЕНИЮ,
  максимум — к лишнему/недостающему правилу, которое сразу видно после перечитывания месяца;
  (в) серверная валидация брони (`TourDateUnavailable`) не зависит от клиента вообще.
- Функция чистая и покрывается юнит-тестами на четыре уровня precedence без сети и без DOM
  (зона `tester`).
- Если бэкенд когда-нибудь получит `SetDayClosed`, удаляются ровно два файла
  (`closureResolver.ts`, `closureToggle.ts`) и один вызов в `CalendarPage` — точка отката
  сохранена намеренно.
