# ADR 004. Общие для нескольких экранов админки form-примитивы живут в `features/admin/ui/`

- **Дата:** 2026-07-31
- **Статус:** Accepted
- **Контекст этапа:** 4.1 (раздел «Настройки»), но правило действует на всю админку
- **Слой:** фронтенд

## Контекст

До этапа 4 в админке был ровно один сложный экран формы — `features/admin/tour-form/`.
Все его составные части лежали в `tour-form/components/`, включая два компонента, которые
на деле не знают ничего про тур:

- `TranslationGroup` — пара полей RU|EN с подписью и флагом `multiline`;
- `MainImageField` — поле URL картинки с живым превью и фолбэком на плейсхолдер.

Экран «Настройки» (4.1) нуждается в обоих: 7 из 18 ключей каталога переводимые
(`IsTranslatable = true`), 3 ключа имеют `ValueType = ImageUrl`. Дальше по этапу 4 их же
попросят справочники (4.2) и selector-control (4.3) — там тоже билингвальные пары.

## Варианты

1. `settings/` импортирует компоненты напрямую из `tour-form/components/`.
2. `settings/` пишет свои `SettingTranslationPair` / `SettingImageField`.
3. Компоненты поднимаются в `features/admin/ui/` и оттуда используются обоими экранами.

## Решение

Вариант 3.

- `tour-form/components/TranslationGroup.tsx` → `features/admin/ui/TranslationGroup.tsx`
  (разметка и пропсы не меняются).
- `tour-form/components/MainImageField.tsx` → `features/admin/ui/ImageUrlField.tsx`:
  `label` и `hint` становятся пропсами, `id` берётся из `useId()` вместо литерала
  `"main-image-url"`. Логика превью не меняется.
- Билингвальные типы `Localized` и `LangKey` выносятся в
  `features/admin/types/localized.ts`; `types/form.ts` и `tour-form/reducer/tourFormReducer.ts`
  ре-экспортируют их по одной строке, чтобы существующие импорты не переписывались.

Правило на будущее: **презентационный компонент, который понадобился второму экрану админки,
переезжает в `features/admin/ui/`, а не импортируется из чужой подпапки и не дублируется.**
`features/admin/ui/` для этого и заведён (сегодня там `TourTableParts.tsx`).

## Обоснование

- Вариант 1 создаёт импорт `settings/` → `tour-form/`: соседние подобласти одной фичи
  начинают зависеть друг от друга, и через два-три экрана это гарантированно даёт
  цикл и «нельзя тронуть форму тура, не сломав настройки».
- Вариант 2 даёт второй способ работы с парой RU/EN. Дальше их станет три (4.2, 4.3), и
  переводы в админке будут выглядеть и вести себя по-разному на разных экранах. Единый
  визуальный контракт билингвального поля важнее экономии на переносе файла.
- Цена варианта 3 измерена, а не оценена на глаз: `TranslationGroup` импортируют два файла
  (`TourDayFields.tsx`, `TourFormHeader.tsx`), `MainImageField` — один
  (`TourFormHeader.tsx`). Итого правка трёх строк импорта.
- Обобщение `id` через `useId()` — не косметика, а необходимость: на экране настроек три
  поля `ImageUrl`, и захардкоженный `id="main-image-url"` дал бы три одинаковых `id` на одной
  странице (сломанная связь `label`↔`input`, некорректная доступность).

## Последствия

- `tour-form` теряет два файла и получает три изменённых импорта. **Визуально форма тура
  обязана остаться идентичной** — это отдельный пункт проверки для `tester`.
- Появляется правило, куда класть следующий общий примитив админки; экраны 4.2 и 4.3 уже не
  будут решать этот вопрос заново.
- `admin/ui/` перестаёт быть свалкой «мелких кусочков таблицы» и становится осознанным
  внутренним UI-слоем фичи `admin`. Компоненты, общие для админки **и** публичного сайта,
  по-прежнему живут в `shared/ui/` — это правило не меняется.
