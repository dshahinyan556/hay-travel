# ADR 017. Сплит-экран `/auth` — второй шелл рядом с `AuthShell`, а не переделка `AuthShell`

- **Дата:** 2026-08-11
- **Статус:** принято
- **Автор:** Frontend Architect
- **Связанная спецификация:** [Spec 005](../specs/005-auth-redesign.md)

## Контекст

Дизайнер предложил, а Давид утвердил редизайн `/auth`: вместо узкой центрированной колонки —
экран пополам, слева фотография Армении с затемнением, справа форма (`hay-auth.html`).

Сейчас у всей авторизации ровно одна оболочка — `features/auth/components/AuthShell.tsx`.
Её используют **семь** экранов плюс личный кабинет:

| Экран | Роль |
| --- | --- |
| `/auth` | вход + регистрация (`AuthPage`) |
| `/auth/check-email` | «письмо отправлено» |
| `/auth/verify` | обработка ссылки из письма |
| `/auth/forgot-password` | запрос ссылки на сброс |
| `/auth/reset-password` | новый пароль по токену |
| `/auth/change-password` | смена пароля (в т. ч. принудительная) |
| `/auth/confirm-email-change` | подтверждение смены email |
| `/account` | личный кабинет (`width="page"`) |

Развилка: расширить `AuthShell` до сплит-экрана (и тогда фото получают все восемь) или
сделать сплит отдельной оболочкой только для `/auth`.

## Рассмотренные варианты

**А. Переделать `AuthShell` в сплит-экран.**
Один шелл, «одинаковый вид у всей авторизации». Но:

- шесть из восьми экранов — это транзакционные подтверждения на 1–3 строки текста, куда
  приходят **по ссылке из письма**. Половина экрана под фотографию рядом с текстом «Проверяем
  ссылку…» — это не премиальность, а шум и лишние 300–800 КБ на экране, который живёт 2 секунды;
- `/account` — не форма, а несколько сворачиваемых секций на `max-w-2xl`; сплит его просто
  ломает;
- любая правка шелла — это риск для восьми экранов сразу, а проверять придётся все восемь
  (включая те, что достижимы только по токену из письма, т. е. дорогие в ручной проверке).

**Б. Параметризовать `AuthShell` пропом `variant: 'column' | 'split'`.**
Один файл, но внутри — два принципиально разных дерева разметки, две сетки, условная загрузка
картинки и условный список «доверия». Это не переиспользование, а `if` длиной в компонент:
любая правка «колонки» требует перечитать ветку «сплита» и наоборот. Классический случай,
когда общий компонент дороже двух отдельных.

**В. Отдельная оболочка `AuthSplitLayout` только для `/auth`; `AuthShell` не трогаем.**

## Решение

**Вариант В.** `features/auth/components/AuthSplitLayout.tsx` — новая оболочка, которую
использует только `AuthPage` (`/auth`). `AuthShell` остаётся ровно таким, какой есть, и
продолжает обслуживать шесть служебных экранов и `/account`.

Общими остаются **мелкие примитивы**, а не шелл: `AuthField`, `PhoneField`, `AuthError`,
`AuthNotice`, `AuthSubmitButton` живут там же, где живут сейчас, и используются обеими
оболочками. Именно на этом уровне переиспользование реально работает — там нет двух разных
деревьев, есть одно поле ввода и одна кнопка.

## Почему это правильная граница

- **Разная задача экрана.** `/auth` — витрина: это первое, что видит вернувшийся клиент, и
  единственный экран авторизации, на который приходят **с сайта**, а не из почты. Остальные —
  служебные шаги, у них задача «сообщить результат и не мешать».
- **Радиус изменений.** Правка `AuthSplitLayout` затрагивает один маршрут. Правка `AuthShell`
  затрагивает восемь, из них четыре проверяются только через реальное письмо/токен.
- **Стоимость отката.** Если сплит не приживётся, `AuthPage` возвращается на `AuthShell`
  одной строкой — старый шелл никуда не делся и не «эволюционировал».
- **Дублирование, которое мы принимаем.** Между двумя оболочками повторяются: заголовок,
  подзаголовок, панель-карточка и ссылка «Вернуться на сайт» — примерно 15 строк JSX. Это
  дешевле, чем условная ветка на весь компонент, и дублирование здесь не опасно: оболочки
  сознательно должны расходиться визуально, а не сходиться.

## Последствия

- В `features/auth/components/` становится два шелла. Чтобы это не читалось как «забыли
  удалить старый», в доккоментарии каждого прямо написано, кто его использует и почему их два.
- Новый экран авторизации, если такой появится, должен явно выбрать оболочку. По умолчанию —
  `AuthShell` (служебный шаг). `AuthSplitLayout` — только если экран является точкой входа с
  сайта.
- `AuthSubmitButton`/`AuthError` в этой задаче получают дополнительные **необязательные**
  пропы (загрузка/успех/иконка). Это осознанно распространяется на все восемь экранов: там
  улучшение бесплатное и без изменения существующих вызовов.
- Фото левой колонки берётся из `SiteSetting` (`branding.authImageUrl`), не хардкодом — по
  тому же принципу, что `hero.imageUrl` и `branding.logoUrl`. Это добавляет один ключ к уже
  готовой backend-спеке 002 (см. Spec 005, раздел «Требуется дополнение к Spec 002»).
