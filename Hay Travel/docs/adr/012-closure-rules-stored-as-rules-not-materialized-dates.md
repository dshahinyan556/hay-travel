# ADR 012 — Закрытые даты хранятся как правила (rule), а не материализуются в строки-даты

Автор: `backend-architect`. Дата: 2026-08-11.
Статус: принято. Реализацию делает `backend-developer` по спецификации
`docs/specs/001-booking-calendar-backend.md`.

## Контекст

Нужна модель «закрытых для бронирования дней», которая одинаково обслуживает:
- точечные даты («закрыть 25 августа»);
- повторяющиеся правила по дню недели («закрыть все понедельники»), с необязательной
  границей по времени (с/по дату);
- область действия «глобально» (все туры) или «конкретный тур»;
- массовые операции открытия/закрытия.

Модель должна кормить админ-календарь (per-day статус закрытия) и блокировать создание
`Order` на закрытую дату на уровне бэкенда.

## Развилка

**A. Материализация.** Recurring-правило раскладывается при сохранении в отдельные строки-даты
(например, «все понедельники» → строка на каждый понедельник в горизонте бронирования).
Таблица содержит только конкретные даты.

**B. Хранение правила (выбрано).** В БД лежит само правило: одна строка на «все понедельники»
с типом `Weekly` и `DayOfWeek`. Принадлежность конкретной даты к закрытию вычисляется во время
запроса резолвером в слое Service.

## Решение — B, хранить правило, резолвить на чтении

`ClosureRule` — одна таблица с дискриминатором `ClosureRuleType { SpecificDate = 1, Weekly = 2 }`:
- `SpecificDate` → заполнен `Date`;
- `Weekly` → заполнен `DayOfWeek` (+ необязательные `EffectiveFrom`/`EffectiveTo`).

Плюс поле действия `ClosureAction { Close = 1, Open = 2 }` — точечная дата с `Open` служит
исключением-переоткрытием поверх recurring-`Close` (иначе единственный понедельник нельзя
переоткрыть, не удаляя всё правило).

Разрешение «закрыт ли тур T в дату D» — чистая функция `ClosureRuleResolver` (без БД, в слое
Service), по убыванию специфичности:

1. Tour-scope `SpecificDate`
2. Global `SpecificDate`
3. Tour-scope `Weekly`
4. Global `Weekly`

> **Этот список устарел с 2026-08-29** — появилась третья область «тип продукта», рангов стало 6.
> Актуальный порядок — в разделе «Обновление 2026-08-29» в конце файла.

Побеждает самое специфичное применимое правило: его `Action == Open` → бронируемо,
`Close` → закрыто. Нет применимых правил → открыто (дефолт).

## Почему B, а не A

1. **Recurring без горизонта.** «Все понедельники» — потенциально бесконечное множество дат.
   Материализация требует выбрать горизонт и до-генерировать строки по мере его сдвига (cron/
   startup-хук). В проекте нет ни одного startup-джоба (`MigrationExtensions.MigrateDatabase`
   не вызывается — см. `backend-stage3-architecture.md` §3.1.1); вводить его ради этого — новая
   инфраструктура на пустом месте.
2. **Редактируемость.** Отменить recurring-правило = удалить одну строку. При материализации
   пришлось бы удалять сотни строк и отличать «сгенерировано правилом» от «поставлено вручную».
3. **Размер данных.** Календарь всё равно строится помесячно и на лету (агрегация заказов
   в SQL + резолв закрытий в памяти на 28-31 день). Материализация не ускоряет этот путь,
   а раздувает таблицу.
4. **Согласованность с проектом.** Проект уже отказался от материализации производных данных
   в БД в пользу вычисления в слое Service: `SiteSetting` хранит только значение, метаданные
   резолвятся из каталога в коде (ADR 002); `Region.TourCount` считается проекцией, а не
   колонкой (§3.2.6). Резолвер закрытий — тот же принцип.

## Цена решения

- Резолвер — единственный источник правды о precedence; его нельзя обойти прямым SQL-фильтром
  «дата закрыта». Все три потребителя (валидация заказа, публичный `GetClosedDates`, админ-
  календарь) обязаны грузить применимые правила и звать резолвер. Это осознанно: правило
  precedence — бизнес-логика, ей место в Service, а не в репозитории (граница слоёв).
- Публичный `GetClosedDates(tourId, from, to)` материализует закрытые даты диапазона **в
  ответе** (не в БД) — фронтовому booking-card нужен плоский список дат для гашения дней.
  Диапазон ограничен (окно бронирования ~3 месяца), стоимость мала.

## Дата как `DateOnly`, не `DateTime`

`ClosureRule.Date/EffectiveFrom/EffectiveTo` и `Order.TourDate` — календарные дни, не моменты
времени. Тип — `DateOnly` (EF Core 10 → SQL `date`). Причина: глобальный
`UtcDateTimeConverter` (`ATToursContext.ConfigureConventions`) применяется только к
`DateTime`/`DateTime?` и породил класс багов «Kind gap» (см. комментарий в `ATToursContext`).
`DateOnly` этого конвертера не касается и не имеет часового пояса вовсе — для календарного дня
это корректнее. `DateTime` остаётся только у настоящих моментов (`Order.CreatedAtUtc`).

## Обновление 2026-08-29 — третья область «тип продукта», рангов стало 6

Батч «Трансферы + формат продукта» (решение 0.27, `docs/checklists/checklist-transfers-format-2026-08-29.txt`)
добавил `ClosureRule.TourType` (`TourType?`) — область «все продукты этого типа», рядом с уже
существующими «весь сайт» (оба поля `null`) и «один продукт» (`TourId`). Поводом было требование
закрывать день **только для трансферов**, не трогая туры и экскурсии.

Решение ADR не отменяется, а расширяется тем же принципом: тип продукта — это **правило**, а не
выборка, поэтому он хранится как правило. Альтернатива (фронтовый пресет, раскладывающий выбор в N
tour-scope правил — ровно так `BulkClosurePanel` раньше делал для «Туры»/«Экскурсии») отвергнута по
той же причине, по которой в ADR отвергнута материализация: материализованный список id замораживает
состав каталога на момент нажатия, и продукт, заведённый завтра, в такое закрытие уже не попадёт.
Эти пресеты убраны из панели массового закрытия — два способа сделать «закрыть все экскурсии» с
разным результатом это ловушка, а не удобство.

`TourId` и `TourType` **взаимоисключимы** (`ClosureRuleValidationService`): правило либо про один
продукт, либо про целый тип.

Список приоритетов из раздела «Решение» (4 ранга) **устарел** — рангов стало 6, новая область
вставлена между туром и глобальной, порядок «SpecificDate > Weekly» внутри каждой области сохранён:

1. Tour-scope `SpecificDate` (ранг 6)
2. TourType-scope `SpecificDate` (ранг 5)
3. Global `SpecificDate` (ранг 4)
4. Tour-scope `Weekly` (ранг 3)
5. TourType-scope `Weekly` (ранг 2)
6. Global `Weekly` (ранг 1)

Сигнатура резолвера — `ClosureRuleResolver.IsClosed/Resolve(rules, date, tourId, tourType)`;
`tourType == null` означает «тип неизвестен/не важен», и правила типовой области тогда не
применяются (глобальные и tour-scope работают как раньше). У кастомной заявки на трансфер продукта
нет вовсе: `tourId == null`, `tourType == Transfer`. Тай-брейк по `Id` при равной специфичности не
изменился.

Публичный `GetClosedDates` получил nullable `tourId` и необязательный `tourType` — см.
`backend-api.md`. Клиентская копия резолвера (ADR 015,
`features/admin/calendar/lib/closureResolver.ts`) обновлена теми же шестью рангами и остаётся
зеркалом серверной.
