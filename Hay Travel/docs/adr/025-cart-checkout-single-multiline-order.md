# ADR 025 — Чекаут корзины: одна заявка = один мультистрочный заказ (атомарно)

- Дата: 2026-08-22
- Статус: Принято
- Связанные: ADR 019 (Order стал мультистрочным), ADR 020 (журнал событий вне транзакции
  мутации), ADR 022 (корзина — клиентский накопитель), спецификации
  `docs/specs/008-cart-frontend.md`, `docs/specs/013-cart-checkout-backend.md`
- Отменяет часть решения ADR 022: пункт «последовательный мульти-чекаут = N отдельных
  заказов по одному на позицию» и зафиксированное там «бэкенд не меняется». ADR 022/spec 008
  правит фронт-архитектор после этого ADR (клиентская часть стора корзины не трогается).

## Контекст

ADR 022 выбрал компромисс «корзина копит позиции на клиенте, а на отправке фронт дёргает
`POST api/Order/Create` по одной позиции» — чтобы не менять бэкенд (`OrderCreateModel` принимал
ровно один `{ TourId, TourDate, GuestCount }` и создавал `Order` с ровно одной `OrderLine`,
ADR 019/020).

Прямое решение Давида (подтверждено дважды) разворачивает этот компромисс:

> «всё, что in cart, в out становится одним order — то есть 4 тура → 1 order».

И отдельно про атомарность:

> если хотя бы у одной позиции дата занята (или другая валидационная ошибка) — заказ не
> создаётся целиком, ни одна строка не пишется в БД. Клиент видит, какая позиция(и)
> отклонена и почему, чинит её и пробует снова. Частично созданных заказов быть не должно.

То есть чекаут корзины на N позиций должен создавать один `Order` с N `OrderLine` одним
HTTP-запросом, атомарно, с пер-строчным отчётом об ошибке.

## Развилка

### Р1. Новый эндпоинт vs расширение существующего

- **A. Отдельный маршрут** (`Order/CreateFromCart`), старый `Create` оставить одно-строчным.
- **B. Расширить `Order/Create` до списка строк, переписать `CreateAsync`.** ← выбрано.

После фичи одно-строчный контракт публичной брони не используется никем: фронт уходит на
корзину полностью, даже для одного тура (позиция корзины с одним элементом — это заказ с одной
строкой). Держать два публичных маршрута создания заказа — это мёртвый код и второй путь,
который придётся сопровождать. Админский `AddLine` (добавление строки в уже существующий
заказ, `[Authorize(Roles = Admin)]`) — это другой сценарий и остаётся как есть.

Итог: `OrderCreateModel` меняет форму на `{ List<OrderCreateLineModel> Lines }`, маршрут и
глагол (`POST api/Order/Create`, `[Authorize]`, владелец из токена) сохраняются, ответ успеха
остаётся `OrderInfoModel` (в нём уже есть `Lines`).

### Р2. Один агрегат vs несколько сущностей + внешняя транзакция

- **A. Строить один `Order` с N `OrderLine` в коллекции и сохранять одним `SaveChanges`.**
  ← выбрано.
- B. Создавать N чего-либо и оборачивать во внешнюю `IDbContextTransaction`.

Транзакционность в этом проекте уже даётся даром при варианте A. Цепочка сохранения
(`EntityActionServiceBase.SaveEntityChangesAsync`): `ExecuteEntityChangesFactoryAsync()`
(обогащение → валидация → `AddRangeAsync`, всё это только в трекере контекста, без записи в БД)
и затем ровно один `SaveChangesAsync()`. Один агрегат `Order` со всеми `Lines` в коллекции
уезжает в БД одним `SaveChanges` = одна неявная транзакция EF, строки вставляются каскадом.
Валидация бросает исключение ДО `SaveChanges`, поэтому при любой ошибке в БД не попадает
ничего.

Явная транзакция (вариант B) здесь избыточна и вводит второй способ писать заказ мимо
`CreateVerifiableEntityBase`. Категорически нельзя реализовывать чекаут как «цикл по позициям
с созданием N `OrderCreationService` / N `SaveChanges`» — это ломает атомарность (частично
записанные заказы) и разворачивает решение Давида (N заказов вместо одного).

### Р3. Пер-строчный отчёт об ошибке vs первый-упавший

Текущий `OrderValidationService` бросает `ErrorModelException` на первой плохой строке — один
плоский `errorCode` на весь ответ. Давид требует, чтобы клиент видел **все** отклонённые
позиции и причину каждой. Значит валидация должна собрать ошибки по всем строкам и вернуть
список, а не падать на первой.

- A. Оставить `ErrorModelException` с первой ошибкой. ← отклонено (противоречит требованию).
- **B. Новый тип исключения `OrderLinesValidationException : ErrorModelException`, несущий
  список пер-строчных ошибок, + отдельный `IExceptionHandler`/цепочка, сериализующие
  расширенную error-модель.** ← выбрано.

Почему через цепочку обработчиков, а не try/catch в контроллере: это действующий паттерн
проекта (`ExceptionHandlerChainBase`/`IExceptionHandler`, ADR-стиль обработки ошибок), любой
новый формат ответа об ошибке проходит через него. `OrderLinesValidationException` наследует
`ErrorModelException`, поэтому:
- несёт плоский верхнеуровневый `ErrorCode = OrderHasInvalidLines` (2031) — для клиентов,
  читающих только общий код (существующий `ErrorModel.ErrorCode`, стиль всего фронта);
- дополнительно несёт `Lines: [{ index, tourId, tourDate, errorCode }]` — чтобы фронт
  сопоставил каждую ошибку с позицией корзины и показал причину именно у неё.

Так как новый тип — подтип `ErrorModelException`, его цепочка обязана стоять В ЦЕПОЧКЕ РАНЬШЕ
`ErrorModelExceptionHandlerChain` (более специфичный обработчик первым), иначе базовая цепочка
перехватит его и потеряет пер-строчный список.

## Последствия

- `OrderValidationService` перестаёт бросать на первой строке: собирает ошибки по всем
  строкам, и если список непуст — бросает `OrderLinesValidationException`. Пер-строчные коды
  (`TourNotFound` 2004, `TourDateUnavailable` 2014, `InvalidGuestCount` 2015, `OrderDateInPast`
  2016) не меняются — меняется только упаковка: теперь они внутри `Lines[i].errorCode`, а не
  как плоский код всего ответа. Фронтовый чекаут читает `Lines`, старый `BookingCard`-маппинг
  плоского кода фронт-архитектор адаптирует отдельно.
- Обогащение (`OrderCreationService.EnrichAsync`) становится пер-строчным циклом; правило
  снапшота цены/скидки НА ДАТУ ПОЕЗДКИ каждой строки и групповой тариф `ResolveTotalAmount`
  сохраняются без изменений. Агрегатное правило статуса (`Open`/`PendingPayment` по
  `Lines.Any(RequiresPrepayment)`) уже написано «по факту строк» и работает как есть.
- Уведомление админу о новой брони (`SendOrderCreatedAsync`) перестаёт показывать только
  первую строку: добавляется HTML-плейсхолдер `OrderLines`, рендерящий все строки заказа
  (по образцу существующего `AssignmentDetails`). Плоские `TourTitle/TourDate/GuestCount`
  остаются привязанными к первой строке для обратной совместимости уже существующих шаблонов.
- Журнал события `LogOrderCreatedAsync` и письмо вызываются один раз на заказ (заказ один) —
  логика не меняется (ADR 020: журнал вне транзакции мутации).
- Защита от абьюза: бэкенд дополнительно ограничивает число строк (1..10, зеркало клиентского
  капа корзины из spec 008) — пустой список = `OrderMustHaveAtLeastOneLine` (2028, переиспользуется),
  >10 = новый `OrderTooManyLines` (2032). Это плоские ошибки формы запроса (обычный
  `ErrorModelException`), не пер-строчные.

## Новые коды ошибок (`GlobalErrorCode`)

- `OrderHasInvalidLines = 2031` — верхнеуровневый код ответа `OrderLinesValidationException`
  (детали в `Lines`).
- `OrderTooManyLines = 2032` — в заявке больше 10 строк.
