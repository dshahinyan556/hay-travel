# ADR 003. Слияние `Restriction` + `OrganizationalDetail`: новая таблица `TourNote`, а не переименование

- **Дата:** 2026-07-29
- **Статус:** Accepted (форма перехода). Вопрос о ломке контракта API — отдельная
  развилка D-3 в `../backend-stage3-architecture.md`, статус Proposed
- **Контекст этапа:** 3.3

## Контекст

`Restriction` и `OrganizationalDetail` структурно идентичны (`TourId` + `SortOrder` +
таблица переводов). Замороженное решение — слить в одну сущность с полем `Type`,
до появления справочников (3.4). В БД сейчас 4 таблицы: две сущности и две таблицы
переводов.

## Варианты

1. Переименовать `Restriction` → `TourNote`, добавить `Type`, влить в неё
   `OrganizationalDetail`, удалить две оставшиеся таблицы.
2. Создать чистые `TourNote` / `TourNoteTranslation`, перелить обе стороны, удалить
   все четыре старых таблицы.

## Решение

Вариант 2.

Перенос выполняется одной миграцией через временные колонки `LegacyId` / `LegacySource`
на `TourNote`: сначала переливаются заметки с сохранением старых ключей, затем переводы
джойнятся по этой паре, затем временные колонки удаляются, затем дропаются старые таблицы.

## Обоснование

- Вариант 1 требует переименовать 4 объекта: две таблицы, FK-колонку
  `RestrictionTranslation.RestrictionId` → `TourNoteTranslation.TourNoteId`, а также
  индексы и constraint'ы. Это сценарий, в котором EF-скаффолдер регулярно генерирует
  `Drop` + `Create` вместо `Rename` — то есть молча теряет данные.
- Вариант 1 даёт асимметричный результат: `Id` ограничений выживают, `Id` орг. деталей
  переназначаются.
- Объём данных — единицы строк на тур. Читаемость и проверяемость миграции важнее
  экономии на переливке.
- Временные колонки вместо `OUTPUT`/`MERGE` — чтобы миграция читалась глазами и
  выполнялась одним батчем.

## Последствия

- `Id` всех заметок переназначаются. Открытая в момент миграции форма тура в админке
  отправит устаревшие `id` и получит 400 — допустимо на стадии разработки.
- `Down()` возможен (обратная раскладка по `Type`), но `Id` не восстанавливает: откат
  безопасен только до первого сохранения тура на новой схеме. Тестировать слияние
  следует на копии БД.
- `SortOrder` переносится как есть, отдельно для каждого типа: у тура получаются два
  независимых диапазона `0..n-1`. Правило чтения — всегда
  `Where(Type == X).OrderBy(SortOrder)`, никогда сортировка по всем заметкам сразу.
  Индекс — `(TourId, Type)`.
