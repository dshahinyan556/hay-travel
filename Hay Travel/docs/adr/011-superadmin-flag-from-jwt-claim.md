# ADR 011. `isSuperAdmin` на фронте — только из claim access-токена, живёт в `AuthUser`

- **Дата:** 2026-08-09
- **Статус:** Accepted
- **Контекст этапа:** SuperAdmin (блок D чек-листа `profile-account-checklist-2026-08-09.txt`)

## Контекст

Бэкенд (спека backend-architect, 2026-08-09) отдаёт признак SuperAdmin **только** claim'ом
`is_super_admin` в access-токене текущего пользователя, и только если он `true`. В
`UserInfoModel`/`UserDetailInfoModel` (список и карточка ЧУЖОГО пользователя) он не появляется
никогда — по дизайну из панели нельзя узнать, кто ещё SuperAdmin (D6). Реальный гард на
бэкенде читает флаг из БД, не из claim'а, поэтому подделанный payload на клиенте не даёт
ничего, кроме нарисованной кнопки, которая ответит 403 — та же логика, что уже описана в
ADR 007 про роль.

Фронту флаг нужен, чтобы решить три вещи в собственной сессии актёра: показывать ли опцию
«Администратор» в `RoleSelect`, разблокировать ли смену роли у чужой Admin-строки, и
разблокировать ли удаление чужого Admin-аккаунта.

## Решение 1: поле `isSuperAdmin?: boolean` в `AuthUser`, а не в `AuthState`

Это свойство того, **кто вошёл**, ровно как `role`. В `AuthState` оно завело бы второе место,
которое обязано чиститься при `logout` и обязано быть синхронно с `user` — тот же класс
рассинхрона, который ADR 007 уже отверг для варианта «Provider + модульный кэш».

Опциональность (`?`) — по существующей конвенции `AuthUser`: «поле может отсутствовать».
Отсутствие и `false` трактуются одинаково; сравнение всегда строгое (`=== true`), никогда
truthy-проверка.

## Решение 2: единственный источник — токен, и его читают ТРИ пути записи

`UserInfoModel` не несёт флаг, поэтому `toAuthUser()` его дать не может в принципе. Значит
`login()` не имеет права строить пользователя одним `toAuthUser(result.user)` — он обязан
дополнительно декодировать `result.accessToken`. Все места в `authStore.ts`:

1. **`login()`** — `{ ...toAuthUser(result.user), isSuperAdmin: superAdminFromToken(result.accessToken) }`.
2. **`refreshAccessToken()`, холодная загрузка** — путь `decodeAccessToken(token)`, флаг
   читается там же, где `role`.
3. **`refreshAccessToken()`, silent refresh в середине сессии** — сейчас код делает
   `state.user ?? decode(...)`, то есть при живом пользователе новый токен вообще не читается.
   Токен переиздаётся каждые ~15 минут, и **только** он знает актуальное значение флага
   (перечитать его больше неоткуда — эндпоинта нет, в DTO его нет). Поэтому существующий,
   более богатый объект пользователя сохраняется, но `isSuperAdmin` переприсваивается из
   свежего токена. Осознанно узко: `role` и остальные поля этот путь по-прежнему НЕ трогает —
   менять их поведение здесь значило бы чинить не ту проблему.
4. **`applyUser()`** — вызывается с объектом, собранным из `UserInfoModel`, который флага не
   содержит. Функция обязана переносить `state.user.isSuperAdmin` в новый объект, иначе
   редактирование собственного профиля молча разжаловало бы SuperAdmin до конца сессии.

Инвариант формулируется одной фразой и выносится в док-комментарий `authStore.ts`:
*`isSuperAdmin` пишется только из декода токена; ни один путь, идущий от `UserInfoModel`, не
имеет права его затирать.*

## Решение 3: парсинг claim'а — строго-толерантный к строкам

Ловушка, из-за которой это отдельным пунктом: в ASP.NET значение `Claim` — **всегда строка**.
Булев claim сериализуется как `"true"`, поэтому `payload.is_super_admin === true` в JS почти
наверняка вернёт `false` и вся фича молча не заработает. Предикат принимает
`true | "true" | "True" | 1 | "1"` и всё остальное считает `false`. Отсутствие ключа — `false`,
это штатное состояние (claim добавляется только когда флаг поднят).

## Решение 4: вопрос задаётся через `permissions.ts`, а не сравнением поля на местах

`permissions.ts` — единственное место в проекте, где сравниваются права. SuperAdmin формально
не роль, а флаг, но правило то же: когда матрица прав поменяется, меняется ровно один файл.

```ts
export const canManageAdmins = (user: AuthUser | null | undefined): boolean =>
  user?.isSuperAdmin === true && user.role === RoleType.Admin
```

Проверка роли добавлена намеренно: SuperAdmin, которого по какой-то причине понизили в БД,
не должен видеть admin-only управление. `AuthUser` импортируется из `./types`, который ничего
не импортирует, — цикла не возникает.

Компоненты получают **capability, а не личность**: `UsersTable`/`RoleSelect`/`UserDangerZone`
принимают булев проп (`canManageAdmins`, `allowAdminOption`, `canDelete`), а не объект
пользователя. Это уже действующая конвенция этого экрана (`UserDangerZone.canDelete`) и она
оставляет компоненты презентационными.

## Последствия

- `UsersPage`/`UserDetailPage` читают актёра через `getAuthState()` один раз за рендер — как и
  сегодня для `id`. Флаг, изменившийся в БД, доедет до UI на следующей навигации (лоадеры
  перевычисляются), а не мгновенно. Это принято: настоящая проверка всё равно на бэкенде.
- Правило D6 (нельзя узнать чужой SuperAdmin-статус) на фронте выполняется автоматически —
  читать его просто неоткуда, кроме собственного токена.
