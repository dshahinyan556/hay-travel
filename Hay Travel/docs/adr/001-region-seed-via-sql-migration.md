# ADR 001. Сид 11 регионов — raw SQL в миграции, а не `HasData`

- **Дата:** 2026-07-29
- **Статус:** Accepted
- **Контекст этапа:** 3.2 (Region), см. `../backend-stage3-architecture.md`

## Контекст

Нужно засидить 11 регионов Армении + 22 перевода (RU/EN). В решении ATTours
**нет ни одного `HasData`** — сид-данных не существует вообще, миграции накатываются
вручную. Прецедент рукописного SQL в миграции есть: `20260720184149_AddRoutePoint`
содержит `DELETE FROM TourDayInfoTranslation WHERE Type = 5`.

## Варианты

1. `HasData` в `RegionConfiguration` + сгенерированные INSERT'ы.
2. `migrationBuilder.Sql(...)` в отдельной data-миграции.
3. Runtime-сид на старте приложения.

## Решение

Вариант 2 — raw SQL в отдельной миграции `SeedArmenianRegions`, идущей следом за
схемной `AddRegionAndTourRegion`.

Регионы вставляются без явных `Id`; переводы — `SELECT`-ом из `Region` с сопоставлением
по `Slug`, поэтому `SET IDENTITY_INSERT` и хардкод идентификаторов не нужны.

## Обоснование

- `HasData` вшивает конкретные `Id` в model snapshot и делает данные частью модели.
  Названия регионов редактируемы (это обычные строки в `RegionTranslation`), и после
  первой же правки снимок разойдётся с БД, а следующая миграция начнёт возвращать
  строки к «эталону».
- Вариант 3 требует startup-хука, которого в проекте нет: `MigrationExtensions.MigrateDatabase`
  существует, но не вызывается нигде — автоприменение на старте пришлось бы вводить
  с нуля, что выходит за рамки задачи.
- Разделение схемной и data-миграции даёт независимый откат и не блокирует схему,
  если сид упал.

## Последствия

- В проект **не** вводится паттерн `HasData` — новые справочники (3.4) должны
  сидиться так же.
- `Down()` удаляет строки по списку слагов; если админ переименует регион, откат всё
  равно сработает (удаление идёт по `Slug`, а не по тексту названия).
- Слаги обязаны совпадать с `RegionSlug` из `Frontend/src/shared/data/armeniaRegions.ts`;
  расхождение проявится молча (фильтр перестанет находить туры).
