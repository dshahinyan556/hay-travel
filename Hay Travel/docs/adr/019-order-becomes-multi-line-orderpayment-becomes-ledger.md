# ADR 019 — `Order` становится шапкой с несколькими `OrderLine`, `OrderPayment` из 1:1-снапшота становится журналом проводок

Автор: главный агент (без субагентов, по просьбе Давида). Дата: 2026-08-16.
Статус: принято. Супersедит [ADR 014](014-order-money-in-separate-orderpayment-entity.md).

## Контекст

Давид прислал два скетча (мокап заказа/платежей) и по итогам вопросов подтвердил: заказ
должен стать мульти-строчным (несколько туров/дат в одном заказе, каждая строка — свой
исполнитель), статусы расширяются с 3 до 7, появляется грид "платежи" с типом
(предоплата/оплата), автономером (`PP0000000001`) и привязкой к конкретной строке заказа.
Бронь с публичного сайта остаётся как есть — создаёт заказ с ОДНОЙ строкой; несколько строк
на одном заказе добавляет вручную админ (checklist-orders-redesign.txt, Фаза 1) — редкий
случай.

Это прямо конфликтует с ADR 014: там `OrderPayment` — сущность 1:1 со своим `Id`, хранящая
СНАПШОТ денег заказа на момент бронирования (`TourPriceSnapshot`/`DiscountPercent`/
`TotalAmount`/`PrepaidAmount`), а `Order` — плоская запись «один тур, одна дата, одно число
гостей».

## Развилка

**A. Оставить `OrderPayment` как снапшот, завести отдельную сущность под журнал проводок**
(например `OrderPaymentTransaction`). Два разных смысла — два разных имени.

**B. Переиспользовать `OrderPayment` под журнал проводок, снапшоты (цена/скидка/итог) увезти
на `OrderLine` — выбрано.**

## Решение — B

- `Order` теряет `TourId`/`TourDate`/`GuestCount`, приобретает `Number` (человеческий номер),
  `RejectReason`, `Currency`, коллекцию `Lines`.
- Новая сущность `OrderLine`: `TourId`/`TourDate`/`GuestCount`/`RequiresPrepayment`/
  `PrepaymentAmount`/`PriceSnapshot`/`DiscountPercent`/`LineTotal`/`EmployeeId`/
  `PickupDetails`/`NavigatorLink` — то есть именно то, что раньше жило пополам на `Order` и
  `OrderPayment`, плюс новые поля мокапа.
- `OrderPayment` теряет все снапшот-поля, приобретает `OrderLineId`, `Type`
  (`Prepayment`/`Payment`), `Number` (автономер), `Amount`, `CreatedAtUtc`. Список, не 1:1.

## Почему B, а не A

ADR 014 само называет причину своего существования: «точка расширения под шлюз» —
провайдер/транзакции/статус оплаты добавятся, не трогая `Order`. Журнал проводок мокапа
(тип/автономер/сумма/строка) — это ровно ТА ЖЕ точка расширения, только пришедшая раньше
платёжного шлюза и оформленная по конкретному UI, а не абстрактно. Заводить `OrderPayment`
как снапшот И `OrderPaymentTransaction` как проводки означало бы две денежные сущности на
один заказ без чёткой границы, кому что писать — источник путаницы при следующей фиче.
Снапшот цены/скидки логичнее живёт на `OrderLine` (он там, где и остальные атрибуты конкретной
брони — тур/дата/гости), а не в отдельной таблице.

## Цена решения

- Любой существующий код, читавший `order.Payment` (единственную запись), должен переписаться
  на `order.Lines.SelectMany(l => l.Payments)` либо на агрегат по `OrderLine`
  (`PriceSnapshot`/`DiscountPercent`/`LineTotal`) — задевает `OrderInfo`, `OrderCreationService`,
  `OrderUpdateService`, `OrderCalendarInfo`, DTO, маппер, весь `OrderDetailPage` фронта.
- Требуется миграция данных (не только схемы): для каждого существующего `Order` создать
  ровно один `OrderLine` из его текущих `TourId`/`TourDate`/`GuestCount` +
  `OrderPayment.TourPriceSnapshot`/`DiscountPercent`/`TotalAmount`, и решить, что делать с
  `PrepaidAmount` (сейчас всегда 0 — ADR 014 сам это фиксирует, так что переносить в проводку
  нечего, реальных денег ещё не было). Миграция пишется руками, не доверяется скаффолдеру
  (см. историческую ловушку EF в `[[project-big-update-july-2026]]` — сгенерированный `Up()`
  один раз уже начинался с `DropTable` до `CreateTable`).

## Что сознательно НЕ делаем сейчас

- Не проектируем реальный платёжный шлюз — `OrderPayment` как проводка всё ещё просто число,
  без провайдера/статуса/ретраев. Это будущий шаг поверх уже готовой формы.
- Не восстанавливаем историю `PrepaidAmount` при миграции данных — предоплаты не было ни разу
  (глобальная константа `ResolvePrepayment` всегда возвращала 0).
