# ADR 020 — Журнал заказа пишется вне транзакции мутации и читается отдельным эндпоинтом

Дата: 2026-08-21. Статус: принято.
Спецификация реализации: [spec 007](../specs/007-order-event-log-backend.md).

## Контекст
Админской странице заказа нужен read-only таб «История»: кто и что сделал с заказом. Мутаций
девять (`OrderController`: create/update/status/add-line/remove-line/update-line/assign/
send-to-client/add-payment), каждая живёт в своём сервисе со своим `DbContext`
(`RepositoryCoreBase` + `new` в контроллере — стиль проекта, не DI).

## Решения

### 1. Запись — из контроллера через один статический фасад, не внутри сервисов мутации
Альтернативы: (а) писать событие внутри каждого сервиса тем же `SaveChanges`, что и мутацию;
(б) дублировать код записи в каждом сервисе; (в) единая точка, вызываемая из контроллера.

Выбрано (в), потому что:
- **Сбой журнала не должен ронять операцию.** Если событие пишется тем же `SaveChanges`, любая
  ошибка вставки в `OrderEvent` откатывает саму мутацию — заказ не сменит статус из-за
  сломавшегося лога. Это ровно тот же принцип, по которому письма
  (`SendNewOrderNotificationAsync`, `SendAssignmentAsync`) не бросают наружу и не откатывают
  уже сохранённое действие. Плата за это — журнал теоретически может «потерять» строку при
  сбое; для внутреннего лога это дешевле, чем упавшая бизнес-операция.
- **Автор действия известен только в контроллере.** `User.GetUserId()` — из `ClaimsPrincipal`;
  протаскивать актора в конструкторы семи сервисов ради лога — размазывание сквозной заботы.
- **Одна точка вместо девяти копий.** Формулировки текста, словарь русских названий статусов и
  форматирование дат/сумм живут в одном классе `OrderEventLog` в слое `Service`, а не в
  контроллере: контроллер передаёт данные, текст собирает бизнес-слой.

Следствие: в `OrderEventLog` разрешён `catch (Exception)` с молчаливым проглатыванием — это
единственное место такого рода, и оно осознанное. Логгера у `new`-сервисов нет (в отличие от
`IEmailSender`, который приходит из DI с `ILogger`); заводить его ради журнала — отдельная
задача, здесь не делаем.

### 2. Текст события — денормализованная русская строка, без структурированного payload
Журнал — внутренний админский, не контент сайта: `ITranslatableModel`/`TranslatableInfoModel`
не реализуем, `LanguageCode` не заводим. Структурированные old/new-значения (JSON или колонки)
дали бы фильтры и «откат», но ни того, ни другого в задаче нет — YAGNI. `OrderEventType`
всё же храним отдельным enum: фронту нужна иконка/цвет на событие, парсить текст он не должен.

### 3. Автор хранится снапшотом (`ActorUserId` + `ActorFullName`), без FK на `User`
Имя пользователя изменяемо, а история обязана показывать состояние на момент события — поэтому
имя денормализовано, как `UserFullName`/`TourTitle` в `OrderInfoModel`. FK не ставим (в отличие
от `LoginHistory.UserId`): журнал не читается графом пользователя, join не нужен, а
независимость от жизненного цикла учётки для аудита ценнее ссылочной целостности.

### 4. Читается отдельным `GET api/Order/{id}/Events`, а не полем `Events` в `OrderInfoModel`
`OrderInfo` — один общий граф на все пути чтения заказа: публичное «Мои заказы», админский
список, `GetAssignedToMe`, PDF и письма. Добавление коллекции журнала туда означало бы:
неограниченно растущую коллекцию в каждом ответе публичного сайта; ещё одну коллекцию в
`AsSplitQuery`-графе, где картезианские взрывы уже отмечены в `tech-debt.md`; лишние строки при
каждом перечитывании заказа после мутации. Таб «История» открывается по клику и только
админом — ленивый отдельный запрос точно соответствует нагрузке.

### 5. Удаление заказа не логируется
Cascade сносит журнал вместе с заказом, положить событие «удалён» некуда. Системного аудита
уровня приложения (переживающего удаление сущности) в проекте нет; заводить его ради одной
операции — несоразмерно текущему масштабу.
