# ADR 007. Фронтовый auth-store — модульный (вне React); юзер после перезагрузки восстанавливается декодом access-JWT

- **Дата:** 2026-08-05
- **Статус:** Accepted
- **Контекст этапа:** аутентификация/авторизация, фронтенд (бэкенд уже готов, см. ADR 005/006)

## Контекст

Бэкенд отдаёт access-токен (15 мин) в теле ответа `Login`, а refresh-токен (14 дней) — только
httpOnly-cookie (`Path=/api/Auth`, `Secure`, `SameSite=Lax`). Фронту нужно:

1. хранить access-токен и текущего пользователя;
2. читать это состояние **в React Router data-лоадерах** (`adminRootLoader`, `catalogLoader`,
   `settingsLoader`, `usersLoader`) — гард панели обязан отработать **до** рендера;
3. переживать F5: access-токен живёт только в памяти и после перезагрузки его нет, но cookie
   осталась, значит сессия формально жива.

Два ограничения, которые задают решение:

- **Лоадеры React Router выполняются вне дерева компонентов.** У них нет доступа к React Context,
  и хуки в них вызывать нельзя. Это не деталь реализации, а свойство data-режима роутера.
- **На бэкенде нет эндпоинта `GET api/Auth/Me`.** `RefreshToken` возвращает только
  `{ accessToken, expiresInSeconds }` — без модели пользователя (см. `AccessTokenModel`).

## Решение 1: стор — модуль, а не Context

`src/shared/auth/authStore.ts` — module-level состояние + `Set` слушателей, публичный API из
обычных функций (`ensureAuthReady`, `login`, `logout`, `refreshAccessToken`, `getAuthState`,
`subscribeAuth`). React подключается к нему одним хуком `useAuth` через `useSyncExternalStore`.
`AuthProvider` **не заводим**.

### Варианты

1. `AuthProvider` + `useContext` (обычный React-путь).
2. Provider **и** дублирующий модульный кэш для лоадеров.
3. Только модульный стор + `useSyncExternalStore` (выбрано).

### Обоснование

- Вариант 1 физически не решает задачу: `adminRootLoader` не может прочитать контекст, гард
  пришлось бы переносить в компонент — то есть после рендера, с миганием панели у того, кому в
  неё нельзя.
- Вариант 2 даёт два источника правды, которые обязаны быть синхронны; рассинхрон здесь — это
  «разлогинен в UI, но залогинен в лоадере». Худший из возможных багов в этой области.
- `useSyncExternalStore` — штатный React-примитив ровно для внешнего стора: подписка происходит
  во время рендера, снапшот не может «протухнуть» между mount и первым paint, и это корректно при
  конкурентном рендеринге.

### Следствие: access-токен НЕ входит в `AuthState`

Токен лежит в приватной переменной модуля и выдаётся только через `getAccessToken()` (его
единственный потребитель — `authFetch`). Если положить токен в снапшот, каждый silent refresh
(раз в ~15 минут и на каждом 401-retry) перерисовывал бы всё подписанное дерево ради значения,
которое ни один компонент не отображает.

Токены **не пишутся** в `localStorage`. Там лежит только «session hint» — флаг `att.session`,
означающий «у этого браузера, вероятно, есть refresh-cookie». Это не секрет и не граница
безопасности (реальная проверка — httpOnly-cookie на сервере), а оптимизация: без него анонимный
посетитель делал бы заведомо провальный `POST RefreshToken` → 401 на каждой загрузке страницы.

## Решение 2: пользователь после холодной перезагрузки — из клеймов access-токена

После F5 состояние такое: пользователя нет, токена нет, cookie есть. `refreshAccessToken()`
меняет cookie на новый access-токен, но пользователя в ответе нет. Пользователь собирается
функцией `decodeAccessToken()` — base64url-разбор payload JWT.

### Варианты

1. Добавить на бэкенд `GET api/Auth/Me` и дёргать его после каждого refresh.
2. Расширить ответ `RefreshToken` до `LoginResultModel` (с `User`).
3. Декодировать payload уже полученного токена на клиенте (выбрано).

### Обоснование

- Варианты 1 и 2 — правки бэкенда, который на момент задачи уже готов, собран и протестирован;
  трогать его ради того, что полностью решается на клиенте, — лишний риск и лишний round-trip на
  каждой загрузке страницы.
- В токене уже есть всё, что нужно UI: `sub` (id), `unique_name` (логин), `email`, роль.

### Проверено вживую (2026-08-05), не предположение

Реальный payload от локального бэкенда:

```json
{ "sub": "6", "jti": "…", "unique_name": "fedevtest2",
  "email": "fedevtest2@haytravel.local",
  "http://schemas.microsoft.com/ws/2008/06/identity/claims/role": "Admin",
  "nbf": …, "exp": …, "iss": "ATTours", "aud": "ATTours.Client" }
```

Роль приходит под **длинным WS-\*-URI**, а не под коротким `role`: `JwtSecurityTokenHandler`
сокращает по `DefaultOutboundClaimTypeMap` только те типы, которые в нём есть, и `ClaimTypes.Role`
в исходящей мапе не сработал. Поэтому `decodeAccessToken` ищет роль по обоим именам, а id и логин —
по парам кандидатов (`sub`/`nameid`, `unique_name`/`name`): это делает клиент устойчивым к смене
маппинга на сервере, а не завязанным на текущее поведение библиотеки.

### Что это НЕ даёт

Подпись токена на клиенте **не проверяется** — ключ серверный, проверить её в браузере
невозможно и не нужно. Декод используется исключительно для отрисовки (имя в шапке, набор пунктов
меню). Любое реальное право перепроверяется бэкендом по тому же токену, поэтому подделанный
payload не даёт ничего, кроме нарисованной кнопки, которая ответит 403.

## Последствия

- `permissions.ts` — единственное место сравнения ролей; и лоадеры, и компоненты спрашивают его
  одинаково, потому что это чистые функции, а не хуки.
- Порядок зависимостей внутри `shared/auth` жёсткий и односторонний:
  `shared/lib/http ← authApi ← authStore ← authFetch ← всё остальное`. Поэтому единственный
  authenticated-эндпоинт auth-вертикали, `ChangePassword`, живёт не в `shared/auth/authApi.ts`,
  а рядом со своим экраном (`features/auth/api/changePassword.ts`) — иначе получился бы цикл
  `authApi → authFetch → authStore → authApi`.
- После холодной перезагрузки объект пользователя беднее, чем после `Login`: в нём только
  id/логин/email/роль (полей `firstName`, `phoneNumber`, `isEmailVerified` нет — их нет в
  токене). Поэтому в `AuthUser` они опциональны, и ни один экран не имеет права считать их
  обязательными. Если когда-нибудь понадобится полный профиль на любой загрузке — это и будет
  момент, когда `Me` (вариант 1) станет оправдан.
