# Спецификация 012. Требования к бэкенду для rich-text редактора (картинки в письмах, свободный цвет)

- **Дата:** 2026-08-22
- **Автор:** frontend-architect (постановка задачи, не реализация)
- **Исполнитель:** `backend-architect` → `backend-developer`
- **Заказчик решения:** Давид, 2026-08-22 («картинки в письмах — да», «свободный цвет — да»)
- **Фронтовая часть:** [спека 011](011-rich-text-editor.md), решение — [ADR 023](../adr/023-rich-text-editor-on-tiptap.md)
- **Меняемый контракт:** [architecture-role-notifications.md §E.5](../architecture-role-notifications.md)

> Это постановка от фронтенд-архитектора: **что** должен уметь бэкенд и **какой контракт**
> гарантировать. Как именно это разложить по слоям (`Service`/`Common`/`Helper`), где завести
> общий сервис и как назвать классы — решает `backend-architect`; ниже конкретные механизмы
> названы только там, где от них зависит поведение фронта.

---

## Зачем

Редактор в админке получает три новые возможности (спека 011): картинки внутри текста письма,
заголовки/выравнивание и свободный выбор цвета. Заголовки и выравнивание текущий allow-list
уже разрешает — **бэкенду по ним делать нечего**. Две другие без бэкенда работать не могут:

| Что | Что происходит сегодня |
| --- | --- |
| Картинка в письме | `img` нет в `AllowedTags`, `src` нет в `AllowedAttributes`/`UriAttributes` → при сохранении шаблона картинка **исчезает молча**, владелец узнаёт об этом постфактум. Плюс аплоад отдаёт относительный `/uploads/...`, который не откроется ни в одном почтовом клиенте |
| Свободный hex-цвет | Значение CSS-свойства `color` не валидируется вообще. Пока цветов было пять фиксированных, это было неважно; давая пользователю свободный ввод, мы сами расширяем поверхность атаки |

**Срочность:** фронтовая часть (спека 011) не должна выкатываться в прод раньше этой. Если
выкатится — получим ровно тот сценарий тихой потери данных, ради предотвращения которого
картинки изначально были отложены.

## А. Allow-list: два профиля вместо одного

Сейчас конфигурация санитайзера живёт внутри
`ATTours.Service/Services/ValidationServices/EmailTemplateValidationService.cs`
(`AllowedTags`/`AllowedAttributes`/`AllowedCssProperties`/`AllowedSchemes`/`UriAttributes`,
`AllowDataAttributes = false`, `CreateBodySanitizer()`).

Требуется вынести её в общий сервис санитизации с **двумя именованными профилями** — потому что
в фазе 2 (описания туров, спека 011 §7) тот же санитайзер понадобится второму потребителю, а
размазывать allow-list по фичам §E.5 прямо запрещает.

### Профиль `EmailBody` (тело письма) — изменения

Всё, что есть сейчас, сохраняется. Добавляется:

- **Теги:** `+ img`
- **Атрибуты:** `+ src`, `+ alt`, `+ width`
- **URI-атрибуты** (те, что проверяются как ссылки): `+ src` (сейчас там только `href`)
- **Схемы:** без изменений — `http`, `https`, `mailto`

### Профиль `RichContent` (описания туров, фаза 2)

Тот же набор, что `EmailBody`, минус `mailto` не нужен, но и не мешает. Отдельный профиль
заводится сейчас, применяется — в фазе 2. Если `backend-architect` считает, что плодить второй
идентичный профиль преждевременно, допустимо начать с одного и разделить в фазе 2 — но точка
конфигурации обязана быть одна и общая уже сейчас.

### Что НЕ добавлять (осознанные запреты)

- `style` у `img` — размер задаётся HTML-атрибутом `width`, CSS почтовые клиенты режут.
- `srcset`, `loading`, `class`, `id`, `data-*` (`AllowDataAttributes` остаётся `false`).
- Схемы `data:`, `javascript:`, `vbscript:`, `file:`, protocol-relative `//host/...`.
- `figure`, `figcaption`, `picture`, `source`, `table` — фронт их не генерит.

### Валидация значения `src`

Пропускать ровно два вида значений, остальное — **атрибут удаляется целиком** (не «ссылка
чинится»):

1. Абсолютный `http://…` / `https://…`.
2. Путь, начинающийся с `/uploads/` (`UploadSettings.PublicUrlPrefix`) — это то, что отдаёт
   собственный аплоад `POST api/Upload/Image`
   (`ImageUploadService`: `"{PublicUrlPrefix}/{relativeDir}/{baseName}.{extension}"`).

Любые `../`, `//evil.com/x.png`, `data:image/svg+xml;base64,…` (SVG — это исполняемый документ),
`javascript:` — отсекаются.

> **Проверить отдельно, это тихая ловушка:** `HtmlSanitizer.Sanitize(html, baseUrl)` умеет
> резолвить относительные URL относительно `baseUrl`, а в некоторых конфигурациях — выбрасывать
> относительные URL как невалидные. Нужен тест, что `/uploads/2026/08/x.webp` **доживает до БД
> относительным и неизменённым**. Абсолютизировать на сохранении нельзя: тот же контент в фазе 2
> будет отдаваться публичному сайту, где относительный путь корректен, а вшитый домен сломается
> при его смене.

### Валидация `width`

Целое число без единиц, `1..1200`. Не число / вне диапазона / с `px` — атрибут удаляется,
картинка остаётся (без ширины она отрисуется в натуральную величину — это некрасиво, но не
сломано). Фронт присылает `Math.min(naturalWidth, 600)`.

## Б. Абсолютные URL картинок в письме

**Проблема:** в БД `bodyHtml` хранит `<img src="/uploads/2026/08/x.webp">`. В админке это
работает (тот же origin), в письме — нет: у почтового клиента нет никакого «нашего origin».

**Решение — абсолютизировать при ОТПРАВКЕ, а не при сохранении.** Хранимый HTML остаётся
портируемым (админка, публичный сайт в фазе 2, будущий предпросмотр), абсолютный адрес
появляется только в исходящем письме.

### Где

`ATTours.Service/Notifications/OrderNotificationService.cs`, после `Render(...)` тела и до
`emailSender.SendTransactionalAsync(...)` (сейчас это строки ~146–149). Тема (`subject`) —
plaintext, её не трогать.

### Что делать

Любой `src`, начинающийся с `/`, префиксовать базовым URL. Значения, уже начинающиеся с
`http://`/`https://`, не трогать (владелец мог вставить внешнюю ссылку). Реализация — по
усмотрению `backend-architect`; регуляркой по строке или разбором через AngleSharp, но
**только для атрибута `src` тега `img`**, а не «заменить все `/` в HTML».

Заодно стоит рассмотреть тот же приём для `href`, начинающихся с `/` (сегодня фронт такие не
генерит — `normalizeLinkHref` всегда даёт абсолютную ссылку, — но пользователь может вставить
относительную вручную, и в письме она будет битой).

### Откуда брать базовый URL

Отдельного «адреса сайта» в конфиге сейчас нет: в секции `Email` лежат три готовых полных URL
(`VerifyUrlBase`, `ResetUrlBase`, `EmailChangeConfirmUrlBase`), а `UploadSettings.PublicUrlPrefix`
принципиально не конфигурируется («и nginx в проде, и `UseStaticFiles` в dev читают ровно
`/uploads`»).

Предлагаемый контракт (окончательное имя ключа — за `backend-architect`):

- Новый ключ `Email:PublicMediaBaseUrl` — origin без хвостового слэша, например
  `https://haytravel.duckdns.org`. Именно **media**, а не «сайт»: важно, кто реально отдаёт
  `/uploads` (в текущем проде — тот же nginx на VPS, что и сайт; если это когда-нибудь разъедется
  с origin'ом фронта, ключ останется корректным).
- Если ключ не задан — не падать и не отправлять битую картинку молча: взять `scheme + host` из
  `VerifyUrlBase` (он по смыслу всегда указывает на публичный сайт) и записать warning в лог.
  Никакой ручной настройки от владельца при деплое это не требует — что и есть требование
  корневого `CLAUDE.md`.

> **Отдельно проверить (похоже на существующий баг, не относящийся к этой задаче):** в
> `ATTours.ClientAPI/appsettings.json` прод-значение `VerifyUrlBase` — `https://haytravel.netlify.app/verify-email`,
> хотя прод с 2026-08-16 живёт на netcup VPS (`haytravel.duckdns.org`). Если это действительно
> протухшее значение, оно уже ломает письма подтверждения почты, и на него нельзя опираться как
> на фолбэк, пока не поправлено.

### Что ещё проверить

- `/uploads/**` должен отдаваться **публично, без авторизации** (почтовый клиент придёт без
  токена) — проверить `Startup.cs` (`UseStaticFiles` с `RequestPath = UploadSettings.PublicUrlPrefix`,
  строка ~68) и конфиг nginx в проде.
- Картинка не должна требовать `Referer`/CORS — это обычный `<img>` из чужого клиента.

## В. Валидация значений CSS-свойств

Сегодня список свойств ограничен (`color`, `font-size`, `font-weight`, `text-decoration`,
`text-align`), а их **значения** — нет. С появлением свободного color picker'а это надо закрыть.

Контракт: невалидное значение → **объявление удаляется, текст сохраняется**. Никогда не удалять
элемент вместе с содержимым из-за плохого цвета.

| Свойство | Допустимое значение |
| --- | --- |
| `color` | `^#[0-9a-fA-F]{6}$` **или** `rgb(r, g, b)` с компонентами `0..255` |
| `font-size` | `^\d{1,3}px$`, значение `1..96` |
| `font-weight` | `normal`, `bold`, либо `100`…`900` кратно 100 |
| `text-decoration` | `none`, `underline`, `line-through` |
| `text-align` | `left`, `center`, `right`, `justify` |

Всё остальное режем: `var(...)`, `calc(...)`, `color-mix(...)`, `url(...)`, `expression(...)`,
`attr(...)`, `!important`, именованные цвета, `currentColor`, любые единицы кроме `px` у размера.

**Почему `color` разрешён в двух формах.** Фронт всегда отправляет `#rrggbb` (нормализует и
нативный color picker, и hex-поле). Но браузер, читая уже сохранённый HTML, отдаёт
`el.style.color` как `rgb(185, 28, 28)`, и AngleSharp внутри `HtmlSanitizer` тоже может
нормализовать значение при пересборке. Фронт умеет читать обе формы обратно в hex
(`toHexColor`, спека 011 §3.10), поэтому обе безопасны — но принимать надо именно обе, иначе
цвет будет молча пропадать на втором сохранении шаблона.

Механизм (событие `RemovingStyle`, пост-проверка через AngleSharp, собственная проверка до
`Sanitize` — что угодно) — на усмотрение `backend-architect`. Важен только результат.

- Синтаксис и рендер плейсхолдеров `{{Token}}` (§E.4): фронт по-прежнему хранит их обычным

- `POST api/Upload/Image` и `ImageUploadService` — без изменений; фронт переиспользует их как

- Момент санитизации — по-прежнему на сохранении (§E.5), не на рендере.

## Д. Приёмка (конкретные проверки)

Сохраняем шаблон через `PUT`, читаем обратно, сравниваем:

| Вход в `bodyHtml` | Ожидаемый результат в БД |
| --- | --- |
| `<p><img src="/uploads/2026/08/a.webp" alt="Схема" width="600"></p>` | Сохранено без изменений, включая относительный путь |
| `<img src="https://example.com/a.jpg" alt="">` | Сохранено |
| `<img src="data:image/svg+xml;base64,PHN2Zw==">` | `src` удалён (или узел вырезан) — SVG-data ни в каком виде не проходит |
| `<img src="javascript:alert(1)">` | `src` удалён |
| `<img src="//evil.com/a.png">` | `src` удалён |
| `<img src="/uploads/a.webp" width="99999">` | `width` удалён, `img` и `src` на месте |
| `<span style="color:#1d4ed8">т</span>` | Сохранено (в hex или в `rgb(...)` — обе формы допустимы) |
| `<span style="color:red">т</span>` | Объявление `color` удалено, текст «т» на месте |
| `<span style="color:var(--x)">т</span>` | Объявление удалено, текст на месте |
| `<span style="font-size:2000px">т</span>` | Объявление удалено, текст на месте |
| `<p style="text-align:center">т</p>` | Сохранено |
| `<img src="/uploads/a.webp" onerror="alert(1)">` | `onerror` удалён |

Отправка письма (эта проверка ловит пункт Б целиком):

1. Вставить картинку в шаблон через админку → сохранить → перезагрузить страницу: картинка на
   месте, `src` относительный.
2. Инициировать письмо этого типа → в исходящем HTML `src` абсолютный
   (`https://<origin>/uploads/...`).
3. Открыть письмо в реальном клиенте (Gmail web + мобильный) → картинка грузится, ширина не
   ломает вёрстку.
4. Письмо без картинок отправляется ровно как раньше (регрессия §E.4/E.5).

## Е. Открытый вопрос к `backend-architect`

Нужно ли ограничивать **количество и суммарный вес** картинок в одном шаблоне? Сейчас ничто не
мешает вставить 30 фотографий; письмо распухнет, часть клиентов обрежет его (Gmail — на ~102 КБ
HTML, дальше «Показать полностью»), а `/uploads` будет расти. Фронт со своей стороны ограничение
не ставит. Если ограничение нужно — это правило валидации шаблона на бэкенде
(`EmailTemplateValidationService`) плюс понятный текст ошибки, и его надо вернуть фронту, чтобы
он показал его в карточке шаблона.
