# Админ-панель

Самодостаточный инструмент под роутом `/admin` (свой каркас, без публичного Header/Footer). Авторизации пока нет, но точка врезки заложена (`adminRootLoader`).

## Роуты (`src/app/router.tsx`)
| Путь | Экран |
| --- | --- |
| `/admin` | Дашборд (обзор) |
| `/admin/products` | Продукты (управление) |
| `/admin/catalog` | Справочники (Точки маршрута / Доп. расходы / Заметки / Регионы) |
| `/admin/settings` | Настройки сайта |
| `/admin/calendar` | Календарь занятости + бронирования |
| `/admin/orders` | Заказы (список, с фильтрами) |
| `/admin/orders/:id` | Деталь заказа (вкладки Обзор/Оплата/Клиент) |
| `/admin/tours/new` | Создание продукта |
| `/admin/tours/:id/edit` | Редактирование продукта |
| `/admin/users` | Пользователи (список) |
| `/admin/users/:id` | Карточка пользователя |
| `/admin/roles` | Роли и права (список, только Admin) |
| `/admin/roles/:id` | Роль — матрица прав (`:id` = `new` для создания) |
| `/admin/notifications` | Настройки уведомлений — список из 4 событий |
| `/admin/notifications/:eventKey` | Событие: платформы, получатели, билингвальный шаблон письма |

Весь admin код-сплитом за одним lazy-импортом (включая `AdminErrorBoundary` как `ErrorBoundary`, не статичный `errorElement` — иначе весь admin утянется в main-бандл).

## Каркас и адаптивность (`AdminLayout` + `AdminSidebar`)
- **Десктоп (`md+`)**: слева фиксированный тёмный рельс `w-60` (`AdminSidebar`), справа рабочая область.
- **Мобилка**: тонкий топ-бар с кнопкой-гамбургером (3 полоски) → выдвижной drawer-оверлей с той же навигацией. Закрывается по backdrop-клику, по клику на пункт и при смене роута (`location.key`); фон заблокирован от прокрутки. `sticky top-0 z-30` (добавлено 2026-08-02 — раньше топ-бар не прилипал и уезжал при скролле, хотя рядом в том же файле десктопный рельс уже был `sticky`; несогласованность, не осознанное решение).
- `AdminSidebar` переиспользуемый (проп `onNavigate`), рендерится и в рельсе, и в drawer.
- Навигация плоская: **Дашборд** → **Продукты** → **Справочники** → **Настройки**, без групп-заголовков (порядок «ежедневное → редкое»).

> ⚠️ Анимация сдвига drawer сделана через inline `style={{transform:…}}`, а не Tailwind `translate-x-*` — в Tailwind v4 `translate-x-*` пишет CSS-свойство `translate`, и связка с `transition-transform` залипала. См. CHANGELOG.

## Дашборд (`/admin`)
Только обзор (переделается позже): карточки-счётчики (`StatCards`: всего/туров/экскурсий/без EN-перевода) + короткий список «Недавние продукты» (топ-5 по id, read-only ссылки на редактирование, «Все продукты →»). **Кнопки создания и управления тут нет** — они на странице «Продукты».

## Продукты (`/admin/products`)
Полноценное управление. Loader грузит активные и архивные списки параллельно (`getAllTours` + `getArchivedTours`); список «Избранных» отдельным запросом не грузится — вычисляется на клиенте фильтром `active.filter(t => t.isFeatured)` (не более 6 штук, лишний round-trip не нужен).
- **Тулбар** (`ProductsToolbar`): переключатель **Активные | Избранные | Архив** со счётчиками, поиск по заголовку (RU/EN), фильтры по типу и по публикации (последний — только в «Активных»). Фильтрация чистая — `lib/filterProducts.ts`.
- **Таблица** (`ProductsTable`): клик по строке (или по заголовку) открывает редактирование. Колонки зависят от вкладки: Активные — фото/заголовок/тип/дней/публикация/действия; Избранные — вместо «Публикация» колонка «Порядок» (▲▼); Архив — без публикации и порядка.
- **Действия**: активные — тумблер публикации + сердечко ♥/♡ (избранное, дизейблится при достижении лимита 6 у ещё не отмеченных туров) + «🗄 В архив»; избранные — ▲▼ реордер (`PATCH ReorderFeatured`, шлёт весь набор Id) + «✕ Убрать»; архив — «↩ Восстановить» + «Удалить» (окончательно, с модалкой подтверждения).
- Сердечко — не своя SVG-иконка, а `♥`/`♡` текстом: в админке иконки уже эмодзи-стиля (🗄/↩/🔍/⚠️/🧳/⚙), это сознательно отдельный язык от line-иконок публичного сайта (`shared/ui/icons.tsx`).
- Ошибка «уже 6 избранных» (код 2011) показывается отдельным читаемым текстом, а не сырым «сервер вернул 400» — см. `errorText`/`errorCodeOf` в `ProductsPage.tsx`, тот же паттерн, что у `SITE_SETTING_KEY_UNKNOWN` в форме настроек.
- Кнопка «Создать продукт» — в шапке страницы.
- Все мутации → соответствующий вызов API + `useRevalidator` (списки и счётчики обновляются сами).

Архив и избранное как модель — см. [product-model.md](product-model.md#архив) и [product-model.md](product-model.md#избранное-2026-08-02).

## Help-кнопка вместо инлайн-хинтов (2026-08-14)
Раньше каждое поле формы (`shared/ui/Field`, `TranslationGroup`) показывало пояснение (`hint`) ВСЕГДА видимым текстом под контролом — на экране с десятком полей (Настройки, форма тура) это превращалось в стену мелкого серого текста. `Field`/`TranslationGroup` теперь рендерят `hint` через `HelpButton` (`shared/ui/HelpButton`, введён 2026-08-06 для F14, до этого использовался только на паре экранов) — кружок «?» рядом с заголовком поля, попап по клику. Правило-исключение: **предупреждение о подозрительном значении** (`warning`, напр. «похоже на неполную ссылку») осталось ВСЕГДА видимым текстом под полем — это не объяснение, а активный сигнал, прятать его за клик было бы неправильно; `Field` теперь принимает `hint` и `warning` раздельно. `DayClosureControls` получил свой первый `HelpButton` (у секции «Доступность») — объясняет правило «ничего не выбрано = весь день» (см. ниже).

## Настройки (`/admin/settings`)
Одна форма из 22 ключей `SiteSetting` (hero-блок, контакты/соцсети, логотип, SEO, тексты сайта), сгруппированных в 6 карточек по `SiteSettingGroup`. Раскладка и группировка приходят с сервера (`GetAll` — сплошной каталог, `id: 0` у ещё не сохранённого ключа) — фронт не хардкодит список ключей. Новая карточка **«Тексты сайта»** (`SiteSettingGroup.Content`, 2026-08-02) появилась без единой правки `SettingsForm.tsx`/`SettingsPage.tsx` — секции строятся из ответа сервера, фронту хватило добавить заголовок/описание карточки и лейблы 4 новых полей в `settingsCopy.ts`. Осознанно НЕ сделаны кликабельными табами (были бы табы — просил Давид, но в `SettingsForm.tsx` уже задокументирована причина отказа: табы прячут поля за общей кнопкой «Сохранить всё», и админ не видит, что реально сохранится) — карточка-на-группу и так разбивает форму по смысловым частям.
- Одна кнопка «Сохранить» внизу, payload — только изменённые (dirty) ключи; `Update` возвращает тот же слитый список, который становится новым baseline (повторный `GetAll` не нужен).
- У переводимых ключей (`hero.title`, `contacts.address`, `seo.siteTitle` и т.п.) RU и EN обязательны — блокирующая валидация (`lib/validation.ts`): пустой EN на бэке не откатывается на RU, значит был бы пустым для англоязычного посетителя.
- Предупреждение при уходе со страницы с несохранёнными изменениями (`useUnsavedChangesGuard`, теперь `shared/hooks/` — этим же хуком пользуется и форма тура, см. ниже).
- Нет бейджа «не заполнено» у ещё-не-сохранённых ключей и нет текста «Нет изменений.» в статус-баре (убраны 2026-08-01, по просьбе Давида — статус-строка молчит, пока нечего сказать, показывает только «Изменено N полей»/«Сохранено в HH:MM»/ошибку).
- `ImageUrl`-поля (`hero.imageUrl`, `branding.logoUrl`, `seo.ogImageUrl`) — текстовый URL с живым превью (`ImageUrlField`), с 2026-08-15 рядом с ним есть загрузка файла (см. ниже) — URL остаётся альтернативой, не заменён.
- Архитектура подробно — `docs/admin-stage4-architecture.md`.

## Загрузка файлов изображений (2026-08-15)
До этой даты `ImageUrl`-поля принимали только вручную вставленный URL (см. `admin-stage4-architecture.md §6`, тогда это было сознательным решением — загрузки не было нигде в проекте). Теперь есть второй способ заполнить то же самое поле: кнопка загрузки рядом с полем URL (`ImageUploadButton.tsx`, `features/admin/ui/`) — открывает системный файловый пикер, шлёт файл на `POST api/Upload/Image` (см. `backend-api.md`), и по успеху подставляет вернувшийся URL тем же `onChange`, каким работает ручной ввод. И `ImageUrlField` (одиночная картинка — тур, настройки), и `ImageListEditor` (репитер — фото точки маршрута, галерея дня) используют одну и ту же кнопку/хук (`useImageUpload.ts`) — в `ImageListEditor` она компактная (иконка), по одной на строку.

Клиентская валидация до отправки (тип файла — JPEG/PNG/WebP, размер — до 8 МБ) дублирует дефолты бэкенда (`UploadSettings`) только ради быстрой обратной связи; окончательное решение всегда на бэке.

Хранение — локальный диск сервера (не Azure Blob/S3), см. `server-ops.md`. На сервере, где бэкенд ещё не переехал на постоянный диск (был на Azure App Service), эта фича ненадёжна — файлы теряются при рестарте инстанса; на netcup VPS (с 2026-08-15) хранение постоянное.

Публичный сайт показывает загруженные фото по-разному в зависимости от соединения посетителя — см. `client-site.md`.

## Справочники (`/admin/catalog`)
Пять вкладок, один loader грузит все пять списков параллельно (`catalogLoader`). Четыре вкладки — полноценный CRUD, пятая (Регионы) — просмотр:
- **Точки маршрута** (Place): название RU/EN, слаг (уникальный), регион (обязательный `Select`-комбобокс из уже загруженных регионов), широта/долгота (необязательно), обложка — URL (legacy-поле, читается, пока у точки нет фотографий), **и список «Фотографии»** (2026-08-06, F12) — произвольное число картинок (`ImageListEditor.tsx`, `features/admin/ui/`): добавление/удаление/drag-and-drop реордер, `sortOrder` — индекс массива. Reconcile на Update — по `id` (та же by-id конвенция, что у GalleryImages в форме тура): `id: serverId ?? 0`, `0` читается сервером как «новая строка». Бэкенд-контракт `Place.Images: PlaceImageInfoModel[]` — B10 (`admin-fixes-checklist-2026-08-06.txt`). `ImageListEditor`/`RepeaterControls` вынесены из `tour-form/components/` в `features/admin/ui/`, т.к. теперь используются и формой тура (галерея дня), и формой точки маршрута — переименование без изменения поведения (`GalleryImagesEditor` → `ImageListEditor`), существующие вызовы в форме тура обновлены на новый путь импорта.
- **Доп. расходы** (ExpenseTemplate): название RU/EN — самый простой справочник.
- **Заметки** (TourNoteTemplate): название RU/EN, тип (`TourNoteType` — Организационная деталь / Ограничение).
- **Теги** (Tag, 2026-08-16) — название RU/EN, тип (Обычный/Скидка — сегмент-переключатель), цвет (5 preset-свотчей палитры сайта, `TAG_COLOR_HEX`), для типа «Скидка» — процент (0–100). **Процент — чисто серверное поле для расчёта цены, в текст тега НЕ подставляется** (уточнено Давидом 2026-08-16 после живой проверки — до этого процент дублировался, если админ сам вписывал его в название); подсказка под полем прямо об этом предупреждает. Подробности домена — `product-model.md#теги-продукта-2026-08-16`, контракт — `backend-api.md#теги-apitag-и-скидка-в-заказе--2026-08-16`.
- **Регионы** — название RU/EN/слаг/число туров read-only (зафиксированы миграцией, `Create`/`Update`/`Delete` для региона как сущности нет). Единственное исключение (2026-08-02) — **тизер** (короткое описание под названием на карте/в панели региона публичного сайта): `RegionsTab` рендерит карточку на регион с двумя текстовыми полями (RU/EN) и кнопкой «Сохранить», активной только когда поле реально отличается от сохранённого значения. `PUT api/Region/UpdateBlurb {Id, BlurbRu, BlurbEn}`, `onMutated` → `revalidator.revalidate()` того же `catalogLoader`. Раньше тизер был захардкожен в `Frontend/src/shared/data/armeniaRegions.ts` — миграция `SeedRegionBlurbs` перенесла тот же текст в БД, так что подключение ничего не изменило на сайте день в день.

**Порядок строк — drag-and-drop, не число (убрано 2026-08-01, распространено на Теги 2026-08-16):** поле «Порядок сортировки» убрано из всех четырёх редактируемых форм и из таблиц. Строки таскаются мышью/тачем/клавиатурой за ручку слева (`DragHandle`, общий примитив `shared/ui/SortableList.tsx` на `@dnd-kit/core`+`sortable`) — хук `catalog/lib/useCatalogReorder.ts` на `onReorder` пересчитывает плотную нумерацию `0..n-1` и рассылает `Update` только по строкам, чья позиция реально изменилась (`Promise.all`, оптимистичный порядок на экране, откат при ошибке). Bulk-эндпоинта для реордера на бэкенде нет — каждая изменившаяся строка уходит отдельным `PUT`. Новая запись получает `sortOrder` «в конец списка» (`nextSortOrder`), это поле для неё больше не вводится руками. У «Заметок» (два `TourNoteType` в одной таблице) `sortOrder` **плоский** — единого индекса `(Type, SortOrder)` на бэке нет, `GetAll` просто сортирует по `SortOrder`, так что типы можно перемешивать местами свободно, форма тура (фильтрующая шаблоны по типу) видит их в том же относительном порядке.

Добавление/редактирование каждой записи открывается в `admin/ui/SidePanel.tsx` — панель, выезжающая справа поверх списка (без ухода со страницы; на узких экранах — на всю ширину). Тот же интерфейс, что у `Modal` (Escape, backdrop-клик, focus trap, блокировка скролла фона), но пристыкован к правому краю и остаётся смонтированным на время exit-анимации.

Удаление подтверждается через `Modal` (как в «Продуктах»). Бэкенд защищает целостность: `Restrict`-связь у всех четырёх каталогов + сервис-уровневая проверка `CatalogEntryInUse` (код 2010) — если запись используется в туре, `Delete` отвечает 400 с понятным кодом, а не сырой ошибкой FK; фронт показывает это отдельным текстом («используется в турах — сначала уберите оттуда»), см. `catalog/lib/catalogErrors.ts`.

RU+EN обязательны у названия во всех четырёх редактируемых каталогах — та же логика, что у настроек (публичный сайт резолвит `own(lang) ?? template(lang)`, пустой EN-шаблон означает пустое место на сайте для англоязычного посетителя).

**Важная ловушка, найденная при живой проверке:** у `Create`-эндпоинтов (`PlaceCreateModel` и аналоги) нет поля `id` на переводах — строгий JSON-биндинг бэкенда 400-ит **весь запрос**, если оно присутствует (`Could not find member 'id'...`), а не только конкретное поле. Поэтому `catalog/lib/catalogMapper.ts` держит два раздельных билдера: `writeLocalized` (без `id`, для Create) и `writeLocalizedForUpdate` (`id: 0` на каждой строке, для Update — сервер реконсилит переводы по id, `id: 0` читается как «заменить»). Не путать их местами при добавлении нового справочника по этому же образцу.

**Поиск по названию** (добавлено 2026-08-01, распространено на Теги 2026-08-16) — во всех четырёх редактируемых вкладках (Точки маршрута/Доп. расходы/Заметки/Теги), не в «Регионах». Клиентская фильтрация уже загруженного списка (`catalog/lib/useCatalogSearch.ts`), без похода на сервер — справочники маленькие. Точки маршрута ищутся ещё и по слагу и по региону. **Пока строка поиска не пуста, drag-and-drop отключается** и таблица рендерится плоским списком без ручек: `useCatalogReorder`'s индексы драга адресуют позиции в ПОЛНОМ списке, и если отдать `SortableList` отфильтрованный подсписок, индексы `fromIndex`/`toIndex` окажутся позициями в подсписке — `sortOrder` уйдёт не той строке.

## Регионы в форме тура (4.3, 4.4)

Выбор варианта: 1) заполняет RU+EN точки из названия Place и ставит `placeId`, дальше текст остаётся редактируемым, ссылка не рвётся от правки текста; 2) **сразу, в браузере, без сохранения** подставляет фото выбранного Place в галерею дня — см. следующий раздел. «Без привязки — свободный текст» возвращает точку к досамому свободному тексту (4.3-стиль), `placeId: null`.

### Живой автофилл фото по привязке к Place (2026-08-16)
Раньше фото Place попадали в галерею дня только на бэкенде (`RoutePointGalleryImageCopier`, B11) и только для НОВОЙ точки маршрута при сохранении — сменить Place у уже существующей точки ничего не подставляло, это был реальный техдолг (F13). Теперь подстановка живёт целиком на фронте и происходит сразу при выборе, без сохранения:
- **Откуда фото** — `PlaceOption.images` (`tourMapper.placesToOptions`): список Place `images`, а если у Place их нет — fallback на одну картинку из legacy `imageUrl` (то же правило, что было у бэкендного копира).
- **Замена, не накопление.** Если точка маршрута уже подставляла картинки в этой сессии (известно по `TourDayFormState.autofilledImageKeys`, `routePointKey -> gallery item keys`), при смене Place эти картинки убираются, а новые встают НА ИХ МЕСТО (не в конец списка); картинки, добавленные админом вручную, никогда не трогаются. Логика — `tourFormReducer.ts`, `setRoutePointPlace`/`removeLinkedImages`.
- **Известное ограничение (осознанное, обсуждено с Давидом):** бэкенд не хранит, какая картинка галереи пришла от какого Place — эта связь только в состоянии формы текущей сессии. Точка, у которой привязка уже стояла ДО открытия формы редактирования, при первой смене Place в этой сессии только ДОБАВЛЯЕТ картинки нового места; старые (от прежней привязки) не удаляются — программа не может знать, какие из них чьи. Дальнейшие смены той же точки в той же сессии удаляют/заменяют уже корректно.
- **«Заполнить из другого продукта»** тоже задействует этот автофилл: копируемые точки маршрута приносят с собой `placeId`, и если он есть — их фото подставляются в целевую галерею тем же способом (весь список точек дня меняется разом, поэтому весь известный автофилл прежнего списка точек убирается и пересобирается для нового). `FillDayFromProductModal`'s текст подтверждения обновлён — раньше говорил «галерея не меняется», это больше не так для точек с привязкой.
- **Кнопка «Заполнить из другого продукта» перенесена наверх** тела дня в `TourDayFields.tsx` (было — после «Длительности», перед точками маршрута) — по решению Давида 2026-08-16, чтобы сразу бросаться в глаза при открытии дня. Для экскурсии (`TourForm.tsx`, плоский макет одного дня) кнопка и так уже была первой — не двигалась.
- **Поиск в `RoutePointPlaceSelect`** — `searchable` включён (был выключен, список Place мог быть длинным без фильтра); заодно исправлен пропущенный `surface="admin"` (компонент рендерился в публичной палитре внутри админки — на этом Select это было незаметно, но неверно).
- **Бэкенд:** `RoutePointGalleryImageCopier.cs` и оба вызова (`TourCreationService`, `TourUpdateService.ReconcileTourDays`) удалены целиком — фронт теперь единственный источник подстановки, и оставлять бэкендный копир означало бы задваивать фото при сохранении НОВОЙ точки с привязкой (фронт уже отправляет её актуальную галерею в payload). Живая проверка: выбор Place в браузере, смена на другое место (замена на месте, ручная картинка не тронута), очистка привязки (авто-картинки убраны), «Заполнить из другого продукта» на сохранённой точке с привязкой (фото добавились). Бэкенд `dotnet build` и фронтенд `tsc -b` чистые.

**4.4 — регионы тура** (реализовано 2026-08-01). Чекбокс-набор на все 11 регионов (`tour-form/components/RegionPicker.tsx`) в шапке формы тура, между текстовыми полями и блоком «Публикация». Простой multi-select без порядка/поиска — регионов всего 11, драг не нужен. Регион у тура необязателен (бэкенд не требует ни одного — решение D-2), можно оставить пустым.

Контракт `UpdateTour`: поле `regions` теперь **всегда** уходит на сервер (даже пустым списком) — раньше (до 4.4) админка вообще не умела прислать этот список, и бэкенд трактовал отсутствие поля как «не трогать регионы» специально ради защиты от стирания (см. `backend-stage3-architecture.md` §3.2.9). Теперь эта защита больше не нужна практически (форма всегда шлёт реальный список), но сам бэкендный код не менялся — осознанно, чтобы не трогать работающий контракт ради чистки, которая ничего не меняет функционально.

Проверено вживую сквозным round-trip: отметить регион → «Сохранить» → `PUT UpdateTour` (200) → перезайти в тур → `GET InitUpdate` возвращает тот же регион. 375px — 2 колонки чекбоксов, без горизонтального переполнения.

## Теги в форме тура (2026-08-16)
Чекбокс-набор (`tour-form/components/TagPicker.tsx`), тот же UI-идиом, что `RegionPicker`, сразу под ним в шапке формы — но с правилом, которого у регионов нет: **максимум 3 тега, максимум 1 типа «Скидка»**. Отличие от `RegionPicker`: клик по тегу, который нарушил бы правило, НЕ снимает предыдущий выбор молча — **блокируется**, и рядом с пикером показывается пояснение (по прямому решению Давида 2026-08-16: «блокировать сказав что уже есть — меняйте существующий или удаляйте», а не тихо заменять). Второй скидочный тег или 4-й тег вообще — не отмечается, пока админ сам не снимет что-то из уже выбранного.

Это UX-подсказка, не единственная защита — то же правило продублировано на сервере (`TourValidationService`, `backend-api.md`), так что даже если бы фронт пропустил недопустимое состояние, `UpdateTour`/`CreateTour` его всё равно отклонят.

Контракт `UpdateTour`/`CreateTour`: `tags` — та же логика null/`[]`, что у `regions` (см. выше), форма всегда шлёт реальный список. Плоская проекция `TourTagInfoModel { id, tagId }` — без вложенного тега, каталог (имя/цвет/тип/процент) уже загружен в лоадере (`getTags()`, параллельно с `getRegions()`).

## Оплата (`OrderDetailPage`) — скидка видна в деталях заказа (2026-08-16)
Когда у брони `payment.discountPercent` не `null`: карточка «Цена тура на момент заказа» получает бейдж «Скидка N%» и зачёркивает саму цену; заголовок карточки «Итого» меняется на «Итого со скидкой». `OrderPaymentTab` рендерит ровно то, что вернул сервер (`OrderCreationService`, `backend-api.md`) — фронт ничего не пересчитывает, только показывает снапшот.

## Предупреждение о несохранённых изменениях в форме тура (2026-08-02)
Раньше форма тура (create и edit, общий `TourForm`/`useTourForm`) не предупреждала о потере
несохранённых изменений вообще — ни при уходе со страницы, ни при смене вкладки. По прямому
запросу Давида добавлено два независимых механизма поверх нового `useTourForm().isDirty`
(структурное сравнение текущего `state` с снапшотом, снятым один раз при монтировании —
`JSON.stringify`, у формы нет узкого diff-маппера как у настроек):
- **Уход со страницы** (сайдбар/кнопка назад/закрытие вкладки браузера) — `TourEditPage`/
  `TourCreatePage` подключают тот же `useUnsavedChangesGuard(isDirty && !isSubmitting)`, что и
  `SettingsPage`. Хук и общая модалка (`shared/ui/UnsavedChangesModal`) вынесены в `shared/`,
  чтобы не дублировать между тремя экранами.
- **Смена вкладки внутри формы** (`TourForm.tsx`) — отдельный локальный перехват клика по табу
  (`requestTabChange`), НЕ через `useUnsavedChangesGuard` (это не роутинг, `useBlocker` тут не
  сработал бы). Важная оговорка: технически смена вкладки ничего не удаляет — все вкладки читают
  один и тот же `state` формы, данные никуда не деваются. Модалка тут — осознанная UX-подстраховка
  по решению Давида, а не защита от реальной потери данных, поэтому текст другой («перейти» вместо
  «уйти», без утверждения, что изменения потеряются).

`UnsavedChangesModal` принимает `title`/`message`/`confirmLabel`, чтобы копирайт можно было
адаптировать под конкретный сценарий подтверждения без нового компонента.

## Календарь (`/admin/calendar`) — 2026-08-13
Спецификация — `docs/specs/003-calendar-frontend.md` (+ `docs/adr/015`, `016`), бэкенд — `backend-api.md#заказы-apiorder-и-доступность-apiavailability--2026-08-13`. Admin-only (`canManageCalendar`).

- **Сетка месяца**, навигация на год вперёд. В каждой клетке — компактный индикатор (кол-во заказов + отметка закрытия). Клик по дню открывает панель (`SidePanel`) с деталями: список заказов по турам на этот день + управление закрытием (открыть/закрыть день — глобально или для конкретного тура).
- **Массовые операции** («Массовые операции» в тулбаре): создание `ClosureRule` — диапазон дат ИЛИ повторение по дню недели, область — «Все туры» либо мультивыбор конкретных туров (тегов у туров в системе нет, поэтому «по тегу» реализовано как чипы-пресеты «Все · Туры · Экскурсии» по `TourType`). Жёсткий клиентский кап `MAX_BULK_RULES = 300` — диапазон × туры может дать тысячи правил за один запрос.
- **Данные месяца** владеет не route loader, а хук `useCalendarMonth` (кэш по `'YYYY-MM'`, дедупликация, `AbortController`, префетч следующего месяца через `requestIdleCallback`) — ADR 016.
- **Клиентское зеркало `ClosureRuleResolver`** нужно только для планирования мутации при клике «Открыть/Закрыть день» (что именно создать/удалить), не для отображения — оно всегда идёт с сервера (ADR 015).
- Таблица правил на мобильном — `overflow-x-auto` (тот же приём, что у `UsersTable`), карточной раскладки нет.

### Редизайн сетки (B12, 2026-08-13)
Сетка была без верхней границы ширины: `grid-cols-7` + `aspect-square` растягивал клетки вместе с шириной контейнера — на широком десктопе клетка доходила до 100+px, и весь месяц (6 строк + тулбар/легенда) переставал помещаться на экран без прокрутки. `CalendarMonthGrid` теперь обёрнут в `mx-auto max-w-[440px]` — ниже этой ширины ничего не меняется (телефон как раньше), выше клетка держится ~55–60px. `CalendarDayCell` заодно избавлена от лишнего дублирования: у закрытого дня раньше были ОДНОВРЕМЕННО штриховка фона, приглушённый текст И крестик в углу — крестик убран (штриховки+текста достаточно), у частично закрытого дня остался только янтарный кружок (у него своего фона нет). Из карточки заказов в клетке убрано число гостей (`· N`) — оставлен только счётчик заказов, при 55–60px клетке вторая цифра в пилюле начинала обрезаться.

### Правки календаря (B12, 2026-08-13)
- **Бэкдейтинг запрещён везде** — раньше массовая операция намеренно разрешала прошедшие даты, одиночный клик по прошедшему дню вообще не проверялся. Теперь оба пути (`BulkClosurePanel`'s `DatePicker`, `DayClosureControls`) заблокированы и на клиенте, и на сервере (`ClosureDateInPast=2022`). Прошедший день по-прежнему открывается (история заказов читается), но все actions в нём задизейблены с поясняющей подписью.
- **Причина закрытия видна в карточке дня** (`CalendarDayModel.closureReason`, только для глобального SpecificDate-закрытия) — раньше терялась между `ClosureRuleResolver` и DTO.
- **Одиночное закрытие дня** теперь тоже собирает `reason` (`Textarea`, тот же лимит `MAX_REASON_LENGTH`, что у массовой операции) — раньше поле было только у bulk.
- **Мультивыбор туров** при закрытии одного дня (поиск + список чекбоксов, тот же паттерн, что у `BulkClosurePanel`) — раньше можно было закрыть только один тур за раз.
- **Hover/selected-подсветка строк списка (2026-08-13)** — обе версии этого списка (`DayClosureControls`, `BulkClosurePanel`) раньше были голыми чекбоксами без обратной связи при наведении/выборе. `shared/ui/Checkbox` получил необязательный `containerClassName` (аддитивно — красит внешний `<label>`-строку, а не сам `<input>`; остальные вызовы не затронуты), обе строки теперь красятся по конвенции `Select.tsx` (admin surface): `hover:bg-neutral-100` в покое, `bg-brand-50 font-semibold` на выбранной.

### Вкладка «Блокировки» (переименована из «Правила», 2026-08-14)
Слово «правило» в UI заменено на «блокировка» везде на этой вкладке (тексты `calendarCopy.ts`, ошибки) — по просьбе Давида, само слово он оставил выбрать агенту. Сущность в коде осталась `ClosureRule`, переименование чисто в отображаемой копии.

- **Группировка** (`ClosureRulesTable`, backend `ClosureRule.BatchId` — см. `backend-api.md`): все правила одного вызова `CreateRules` (массовая операция ИЛИ одиночный toggle из `DayClosureControls` — оба идут через один эндпоинт) делят один `BatchId` и рендерятся ОДНОЙ строкой-группой с раскрытием (`groupClosureRules`/`compareClosureRules`, `calendar/lib/calendarModel.ts`), а не N визуально неотличимых строк. Группа-сводка показывает общую область (тур/«Все туры»/«N туров» при разных турах в одном батче), тип, диапазон дат или список дней недели, действие, причину — все три последних поля берутся с первого правила группы: тип/действие/причина гарантированно одинаковы внутри одного батча (оба создающих пути шлют по одному значению на весь вызов), это НЕ пересчитывается по всем строкам заново. Правило с `BatchId = null` (данные до миграции) или батч из одного правила рендерится как раньше — плоской строкой без шеврона.
- **Массовое удаление вместо кнопки на каждой строке**: чекбокс на группу (выделяет все дочерние id разом, tri-state при частичном выборе) и на отдельное правило внутри развёрнутой группы; одна кнопка «Удалить выбранное» над таблицей с подтверждением. Новый эндпоинт — `DELETE api/Availability/DeleteRules` (список id), `adminAvailability.deleteClosureRules`.

### Единая кнопка Закрыть/Открыть (`DayClosureControls`, 2026-08-14)
Раньше было три отдельных контрола: чекбокс «Закрыть весь день», список чекбоксов «закрыть тур», список кнопок «Открыть» по одной на закрытый тур. Теперь оба направления — выбор тура через кнопки-переключатели (`ToggleChip`, не чекбоксы) + ОДНА кнопка на направление: ничего не выбрано → действие применяется к целому дню (закрыть) или ко всему закрытому (открыть); выбраны туры → только к ним. Когда день уже закрыт целиком, секция открытия — просто кнопка «Открыть весь день» без пикера (нечего выбирать по отдельности). Правило объяснено через `HelpButton` у заголовка «Доступность», не инлайн-текстом.

### Фильтр по региону + сброс (`BulkClosurePanel`, 2026-08-14)
Рядом с существующими пресетами «Все/Туры/Экскурсии» — ряд кнопок по регионам (`shared/data/armeniaRegions`, только регионы, где реально есть хотя бы один тур). Кнопка «Сбросить» рядом со строкой поиска — очищает только фильтр выбора туров (поиск + отмеченные), не трогая действие/тип/даты выше.

### Десктопная ширина сетки (2026-08-14)
Решение B12 (2026-08-13) капало сетку в `max-w-[440px]` на ВСЕХ экранах, чтобы месяц помещался без прокрутки — на широком мониторе клетки оставались телефонного размера. Теперь кап расширяется в два шага: `lg:max-w-[720px]`, `xl:max-w-[960px]` (сама клетка/цифра/бейдж заказов масштабируются вместе с шириной), мобильная раскладка не тронута.

Изначально список показывал всё (платёж, обе метки времени, кнопки) прямо в строке — по просьбе Давида переделано в список/деталь: строка (`OrderRow`) теперь только тур+дата, клиент, статус, Итого, целиком кликабельна на `/admin/orders/:id`. Никаких мутаций на этом экране больше нет — `ordersLoader` не ревалидируется.

- **Фильтры** (`OrderFilters`, полностью клиентские — датасет маленький, лишний запрос не нужен): статус (вкладки, дефолт «Ждут подтверждения»), тур (`Select`, из того же `getAllTours()`, что грузит `ordersLoader`), клиент (текст по имени/email), № заказа, диапазон даты выезда. Логика фильтрации — `orders/lib/ordersModel.ts` (`matchesOrderFilters`), там же локальная копия `tourTitleResolver` (та же, что в `calendar/lib/calendarModel.ts` — фича фичу не импортирует, дублирование сознательное).
- Заказ с 7+ гостей показывает «Цена по запросу» вместо Итого (см. ниже) — счёт по `resolveTier(guestCount) === 'hidden'` из `shared/currency/pricing.ts`.

### Деталь (`OrderDetailPage`, `/admin/orders/:id`)
Три вкладки (`Tabs`, тот же компонент, что у `CalendarPage`):
- **Обзор** (`OrderOverviewTab`) — тур/дата/гости, «Создан»/«Подтверждён» (`confirmedAtUtc`, `null` → «ещё нет» — см. `backend-api.md`), и — только пока `PendingConfirmation` — Подтвердить/Изменить/Отменить. Логика 1:1 перенесена из старой инлайн-версии `OrderRow`.
- **Оплата** (`OrderPaymentTab`) — цена тура на момент заказа / Итого, и предоплата новым визуалом: полоса-прогресс (`role="progressbar"`) вместо старой плоской строки «не внесена», которую Давид забраковал. Для 7+ гостей вместо Итого/предоплаты — карточка «Цена по запросу» с пояснением (тариф скрыт и на публичном сайте тоже).
- **Клиент** (`OrderClientTab`) — имя/email + кнопка-ссылка на `/admin/users/:id` (`UserDetailPage`), и список других заказов этого же клиента (переиспользует `OrderRow` как есть — компонент уже «один заказ, минимум полей, ссылка на деталь»). Источник — `orderDetailLoader` грузит `getOrders()` целиком и фильтрует по `userId` (отдельного эндпоинта «заказы по пользователю» нет, как и с фильтрами списка).

Мутации (`confirmOrder`/`cancelOrder`/`updateOrder`) теперь живут в `OrderDetailPage`, не в `OrdersPage` — тот же паттерн run→revalidate, что был в старой `OrdersPage`.

### Цена (B12, 2026-08-13 — см. `backend-api.md`)

Баг обнаружился именно когда `order.payment` стало видно в новой детали заказа. Исправлено на бэкенде; старые заказы намеренно не пересчитаны (см. `backend-api.md`).

### Acumatica-style тулбар, сводка, contextual-действия и История заказа (2026-08-21)
Чек-лист — `checklists/order-toolbar-summary-checklist-2026-08-21.txt`. Референс — 2 скрина
Acumatica ERP (Sales Order — тулбар + summary-панель + сгруппированное меню «…») + запрос Давида
сделать тот же уровень функционала в своей ч/б стилистике.

- **Новые переиспользуемые примитивы** в `shared/ui` (строго `neutral-*`, без `brand-*`, без
  анимаций кроме `translate-y-px` на нажатии — билд-язык описан в самих файлах):
  `AdminActionButton` (варианты `primary`/`secondary`/`ghost`/`destructive`), `AdminToolbar`
  (Cancel → Save → Add → Delete, именно в этом порядке — Prev/Next из референса Давид явно
  отменил), `AdminSummaryPanel` (лейбл слева/значение справа, итоговая строка отбита жирной
  чертой), `OrderStatusBadge` (read-only пилюля — статус НЕ редактируется напрямую нигде в UI),
  `AdminActionsMenu` (сгруппированное меню-колонки поверх `Popover`, триггер живёт внутри самого
  `AdminToolbar` через его проп `actionsMenu`).
- **`OrderDetailPage` переведён на модель черновика.** `requiresPrepayment`/`prepaymentAmount`
  (грид строк) и `pickupDetails`/`navigatorLink` (таб «Детали для выполнения») и причина отказа
  больше не сохраняются по `onBlur` — правки копятся в локальном `OrderDraft`
  (`{ rejectReason?, lines: Record<lineId, patch> }`), `AdminToolbar`'s Save коммитит его одним
  батчем запросов (`SetStatus` — если менялась причина, `UpdateLine` — по одному на изменённую
  строку), Cancel откатывает МГНОВЕННО, без сетевого запроса (просто сбрасывает черновик — все
  компоненты рендерят `order`, "просвеченный" черновиком через `applyDraft`, ничего не хранят сами).
  Всё, что и раньше было отдельным действием с побочным эффектом (Assign, AddPayment, AddLine/
  RemoveLine, SendToClient) в черновик не уходит — сохраняется как и раньше, сразу.
- **Contextual-кнопки** (`OrderContextActions`, рядом с `AdminToolbar`, НЕ в выпадающем меню) —
  тонкие обёртки над `SetStatus`: «Одобрить»/«Отклонить», видны, только пока заказ ещё не
  `Approved`/`Rejected` (компонент рендерит `null`, когда решение уже принято).
- **«…» `AdminActionsMenu`** (в самом `AdminToolbar`, после Delete) — 2 группы-колонки:
  «Назначение» → «Назначить исполнителя» (попап, см. ниже); «Отправка» → «Отправить заказ клиенту»
  (существующий `SendToClient`) и «Отправить заказ исполнителям» (повторно шлёт письмо+PDF ТЕМ, кто
  уже назначен — перебирает строки с `employeeId != null`, тот же `AssignEmployee` на каждую, «на
  всякий случай» если оригинальная отправка не дошла; задизейблен, если ни одна строка ещё не
  назначена). Эти 3 действия раньше были отдельными контекстными кнопками — перенесены в меню
  2026-08-21, чтобы не растягивать мобильный тулбар в 3+ отдельные строки. Обе «отправить»-опции НЕ
  сохраняют черновик сами — если в черновике есть правки, сперва спрашивают («Сохранить перед
  отправкой?» — модалка, «Сохранить и отправить» либо «Отмена»), чтобы письмо ушло с актуальными
  данными.
- **Попап «Назначить исполнителя»** — 3 кнопки: «Отмена», «Назначить» (тихо, без письма) и
  «Назначить и отправить письмо». Рендерится через `shared/ui/Modal`'s `size="lg"` (`max-w-xl`,
  576px вместо дефолтных 448px) — на десктопе форма+3 кнопки иначе выглядели тесно. Бэкенд получил
  для этого `OrderAssignEmployeeModel.SendEmail` (default `true`) — см. `backend-api.md`.
  **2026-08-23: `AssignAllModal.tsx` → `AssignEmployeesModal.tsx`, мультивыбор** — см. «Мульти-
  исполнители на строке заказа» ниже (несколько исполнителей на одну строку теперь поддержаны).
- **Мобильный тулбар — видимость Cancel.** `AdminActionButton`'s `ghost`-вариант (используется
  только Cancel'ом) был `border-transparent` — на мобилке, где кнопка схлопывается в 44×44 иконку
  без подписи, это читалось как ничего не отображающий "плавающий" крестик (особенно в disabled-
  состоянии). Добавлена постоянная `border-neutral-200` (на ступень легче, чем у `secondary`) —
  форма кнопки видна всегда, не только на hover.
- **Таб «История»** (`OrderHistoryTab`, четвёртый после «Детали для выполнения») — чистый readonly
  таймлайн событий заказа (`GET Order/{id}/Events`, см. `backend-api.md`): дата/автор/готовый
  русский текст события/мелкая пилюля-тип. Ни кнопок, ни фильтров, ни разворачивания строк.
- **Кнопка Add — только визуальный «новый черновик».** Открывает страницу в пустом клиентском
  состоянии (`blankDraftOrder`, ничего не уходит на сервер), Save в этом режиме задизейблен.
  Реальное создание (пикер клиента + расширение `POST Order/Create`, который сейчас всегда берёт
  владельца из токена и делает ровно 1 строку) — отдельная будущая задача.
- **Сознательно НЕ сделано в этой задаче**: Prev/Next по тулбару, полноценное создание заказа
  через Add, весь остальной guarded workflow (Assigned/Готов к выполнению/В процессе/background
  jobs), acceptable starting time на продукте — всё это зафиксировано как будущие задачи в самом
  чек-листе. (Множественные исполнители с ролями — реализовано позже, см. ниже.)

  несохранённые правки» сразу после успешного PUT. Исправлено: патч черновика — no-op, если ничего

- **Убрана предупреждающая подсказка** под тумблером «Новая бронь с сайта» («выключать не
  рекомендуется…») вместе с удалением старого `EmailTemplateCard.tsx` — по прямому решению
  Давида: патерналистские советующие плашки в интерфейсе не нужны. Других плашек этого класса

## Пользователи (`/admin/users`)

Список (`UsersPage`) + карточка (`UserDetailPage`), `[Authorize(Roles="Admin")]`. Полный контракт (SuperAdmin, LoginHistory, email/телефон) — `user-management.md`, здесь только то, что видно в самой админке.

- **Список**: таблица (`UsersTable`) с ролью (`RoleSelect`), кнопками сброса пароля/блокировки. Смена роли на **Admin** теперь требует подтверждения (`PromoteToAdminModal`, единственная модалка на страницу, не на строку) — раньше `RoleSelect` менял роль сразу по `onChange` без единого подтверждения. Опция «Admin» в дропдауне вообще не показывается обычному админу (`allowAdminOption`) — видна только SuperAdmin.
- **Карточка пользователя** (2026-08-09/10): новая секция **История входов** (`LoginHistoryList`) — стек карточек-строк (IP, страна/город с флагом, устройство/браузер, время), не таблица. Грузится в `userDetailLoader` через `Promise.all` с `.catch(() => null)` — падение истории не роняет саму карточку профиля.
- **«Опасная зона»** (`UserDangerZone`) — удалить/понизить пользователя с ролью Admin теперь может только SuperAdmin (`canDelete` учитывает `canManageAdmins(actor)`), обычный админ по-прежнему не может тронуть ни одного другого админа. Текст подтверждения жёстче, если цель — админ (`deleteAdminBody`).
- Кто из админов SuperAdmin — **не видно нигде в интерфейсе**: осознанное решение, `IsSuperAdmin` не приходит ни в списке, ни в карточке чужого пользователя (см. `user-management.md`).

## Гибкая система ролей и прав (`/admin/roles`, 2026-08-22)

Замена фиксированной модели `RoleType` (Regular/TourManager/Admin/Employee, жёстко зашитой в
`[Authorize(Roles=...)]`) на роли, редактируемые из UI. Полная архитектура —
`architecture-flexible-roles.md` (бэкенд) и `architecture-flexible-roles-frontend.md` (фронтенд),
чек-лист со статусами по этапам — `docs/checklists/checklist-flexible-roles.txt`.

- **Единица прав — «экран»**, не таблица: 13 фиксированных ключей (`dashboard`, `products`,
  `calendar`, `orders`, `catalog.places/expense-templates/note-templates/regions/tags`, `users`,
  `roles`, `notifications`, `settings`), каждый с **одним уровнем доступа** (см. ниже — правка
  2026-08-23 заменила 4 независимых флага одним `AccessLevel`). Реестр — `AdminScreens.cs`
  (бэкенд) / `shared/auth/screens.ts` (фронт) — единственное место, которое трогают при
  добавлении нового экрана.
- **Права = роль + персональный override** на пользователя. Override — `AccessLevel | null` на
  экран (`null` = наследовать от роли), редактируется в `UserPermissionsCard` на карточке
  пользователя (`/admin/users/:id`, свёрнута по умолчанию — теперь по-настоящему анимированно,
  см. `Accordion` ниже — видна тем, у кого есть `users.Update`).
- **`/admin/roles`** — список ролей + создание/переименование/удаление; **`/admin/roles/:id`**
  (`:id = new` для создания) — форма с `PermissionMatrix` (переиспользуемая таблица
  экраны×уровень, компонент/карточки на мобильном, без горизонтального скролла). **Ни одна роль
  не защищена от редактирования или удаления** (правка 22.08.2026, по прямому требованию Давида):
  4 сидовые роли — просто стартовые данные, их можно переименовать, урезать матрицу до нуля (в
  т.ч. отобрать у «Администратора» доступ к самому экрану «Роли») или удалить, если на них никто
  не назначен. Два флага в форме роли меняются только SuperAdmin: `CanManageAdmins` (право
  трогать других носителей этой же способности) и **`CanImpersonate`** (право входить в аккаунты
  пользователей, новое 2026-08-23 — см. ниже).
- `/admin/roles` и `/admin/notifications` — обычные экраны матрицы (ключи `roles`/
  `notifications`), а не жёстко зашитые Admin-only мета-экраны: любая роль получает или теряет
  доступ к ним так же, как к любому другому экрану.
- **Резолвинг** — права печём в JWT при логине/рефреше; `GET api/Auth/MyPermissions` отдаёт
  всегда свежий из БД набор для немедленной перерисовки гардов (задержка применения на бэкенде —
  не больше одного TTL access-токена, ≤15 мин, либо мгновенно — remember me теперь форсирует
  переролгин всей базы в течение часа после деплоя, см. ниже).
- `shared/auth/permissions.ts` переписан целиком на универсальные `can/canView/canCreate/
  canUpdate/canDelete(screen, action)` — именованные предикаты (`canManageTours` и т.п.) не
  сохранены тонкими обёртками: они гейтили разные наборы экранов и склеили бы обратно то, что
  матрица специально разделила.
- Живая браузерная проверка (создание тестовой роли, override, регрессия по 4 старым ролям) —
  на Давиде; статическая (build/typecheck/lint) прогнана и чиста.

### Единый уровень доступа, Sign in as user, Remember me (2026-08-22/23)
Контракт — `backend-api.md#единый-уровень-доступа-вместо-4-независимых-флагов--impersonation--remember-me-20260822-23`,
спека `docs/specs/014-permission-levels-impersonation-sessions.md`, ADR 027-030.

- **`AccessLevelSelect`** (`shared/ui/`) заменил 4 чекбокса одним дропдауном (None/View/Create/
  Update/Delete, каждый включает нижестоящие). В `PermissionMatrix`/`PermissionCell` — обычный
  выбор; в `UserPermissionsCard` (override) — вариант с `value: AccessLevel | null`, где `null`
  показывает реальный уровень роли призрачным текстом («По роли: Удаление») вместо пустой ячейки.
  Уровень, которого экран не поддерживает (напр. Delete у «Регионов»), не предлагается —
  компонент принимает `levels?: readonly AccessLevel[]`, иначе бэкенд отклонил бы выбор 400-м
  (`InvalidPermissionLevel`).
- **«Войти как пользователь»** (`UserImpersonateModal`, кнопка на `/admin/users/:id`) — видна
  только при `can_impersonate` claim и не на себе, задизейблена с подсказкой на цели с
  `CanManageAdmins`/`CanImpersonate`/SuperAdmin, если сам актёр не SuperAdmin. Модал явно
  предупреждает: своя сессия завершается безвозвратно, обратной кнопки нет — это факт бэкенда
  (`POST api/Users/{id}/Impersonate` отзывает все refresh-токены и мгновенно убивает ещё живой
  access-токен импersonator'а), не UI-ограничение. После успеха — редирект в `/admin`, если у
  цели есть доступ хоть к одному admin-экрану, иначе на публичный сайт `/` (решение зафиксировано
  как открытое для ревизии, не согласовано явно с Давидом). **Живой клик не проверен** — в
  локальной БД на момент реализации был только один пользователь (admin); проверено сборкой/
  тайпчеком и тем, что кнопка корректно скрыта на себе.
- **Логин** — чекбокс «Запомнить меня» (`rememberMe`, выключен по умолчанию). Влияет только на
  срок refresh-токена (1 час / 14 дней), см. `backend-api.md`.
- **Живая браузерная проверка (2026-08-23, Клод)**: dev-логин, чекбокс remember me на форме
  логина, дропдаун уровня на карточке роли + новые галочки `CanManageAdmins`/`CanImpersonate`,
  анимированный разворот `UserPermissionsCard` (аккордеон реально анимируется, не мгновенный
  показ/скрытие), retrofit-экраны (см. ниже) без ошибок в консоли, 375px без переполнения.

### Формат и групповой тариф (`TourFormatFields.tsx`)
Сегментированное радио «индивидуальный / групповой / оба» — **только у тура/экскурсии**; у трансфера
блок не рендерится вовсе (а не дизейблится). Два групповых поля — «цена за человека» и «мест на
выезд» — появляются только при `Групповой`/`Оба`: при индивидуальном они бессмысленны, маппер шлёт
их как `null`, и серые неактивные поля намекали бы, что числа где-то хранятся.

**Решение 0.26**: при формате «Групповой» (именно чисто групповом, не «оба») «Цена за группу»
в шапке **прячется**, а вместе с ней и цены дней, которые её составляют (`TourFormHeader.tsx`,
`TourForm.tsx`, `TourDayFields.tsx` — флаг `isGroupOnly`). Данные при этом целы: `Tour.TotalPrice`
остаётся суммой цен дней, ничего не обнуляется. У формата «Оба» цена за группу нужна — там она
на месте.

На форме одновременно живут две цены, которые **не выводятся друг из друга**: «цена за группу» —
фикс с тирной наценкой, «цена за человека» — умножается на число гостей без наценки. Каждая
объясняется за своей иконкой «?» (`HelpButton`), не инлайн-прозой — правило проекта.

### Редактор времён старта (`TourStartTimesEditor.tsx`)
Список `HH:mm` с добавлением/удалением; минимум одно время обязательно, дубли запрещены — обе
проверки дублируют бэковую `InvalidTourStartTimes`/2052, чтобы ошибка встала у поля, а не прилетела
400-кой. Ввод — нативный `<input type="time">` (тот же контрол, что в `JobScheduleCard`), без своей
маски и без парсера; общий примитив в `shared/ui` намеренно не выносится — публичному сайту нужен
свой, со своей палитрой. **Сортировка по `onBlur`, а не по `onChange`**: нативный time-input
докладывает и промежуточные состояния, и перестановка строк прямо под курсором увела бы поле
из-под ввода. Ошибки, как и везде в форме, показываются после первой попытки сохранения.

### Ветка трансфера в форме

остаются: главная картинка, маршрут, таблица цен, чекбокс предоплаты, публикация — всё остальное

- Пояснения к новым полям — за иконкой «?» (`HelpButton`), не инлайн-текстом.

### Экран заказа — статус «Заявка» и детали кастомного трансфера
- Статус `Request` = **«Заявка»** в бейджах (тон `neutral` — такое же «в работе», как Open/
  PendingPayment) и в фильтрах списка. В `STATUS_ORDER` он стоит **первым**: это единственный
  статус, который ничего не стоит, пока за него не взялись, поэтому попадаться на глаза должен
  раньше всех.
- Заказ-заявка намеренно **не попадает** ни в `frozen`, ни в `preDecision` (`OrderDetailPage.tsx`,
  `isRequestOrder`): править её нужно ДО решения — иначе одобрять было бы нечего, цены у неё нет.
  Флаг управляет только пояснением сверху, редактирование не ограничивает.
- `OrderRequestDetails.tsx` — блок деталей заявки: маршрут «откуда → стопы → куда» ровно в том виде,
  в каком его ввёл клиент (одноязычный), багаж, пожелания по классу авто, комментарий, и **поле
  согласованной цены**. Цена правится тем же эндпоинтом, что предоплата (`UpdateLine`), пишется в
  черновик страницы и коммитится общим Save — сеть до нажатия Save не трогается.
- `OrderLineMeta.tsx` — параметры строки, появившиеся с батчем (время старта/подачи, формат, класс
  авто по снапшоту названия, обратный рейс), показаны **чипами под названием продукта, а не
  четырьмя новыми колонками грида**: таблица строк уже 960px минимум, а любая из этих величин у
  половины строк пуста — колонка ради пустоты растянула бы горизонтальную прокрутку на всех экранах.
  Чип рисуется только когда значение есть; у старой строки и у обычного тура блок либо пуст
  (`null`), либо в одну пилюлю.

### Календарь — настоящая область правила вместо пресетов
`BulkClosurePanel` теперь предлагает три **взаимоисключающих** варианта области, которые понимает
бэк: «Все продукты» (одно глобальное правило), «Тип продукта» (правило на категорию — действует и
на продукты, заведённые позже) и «Выбранные продукты» (мультивыбор).

Прежние кнопки-пресеты «Туры»/«Экскурсии» **убраны**: они лишь набивали мультивыбор идентификаторами
из текущего каталога, то есть замораживали состав каталога на момент нажатия. Два способа сделать
«закрыть все экскурсии» с разным результатом — ловушка, а не удобство. Фильтр по региону остался
пресетом сознательно: области «регион» на бэке нет и не планируется, там это честный помощник
выбора, а не имитация правила.

Форма по-прежнему компилируется через `compileBulkForm` на каждое изменение, поэтому строка
«будет создано N правил» и отправляемый payload не могут разойтись — это один и тот же вызов.
