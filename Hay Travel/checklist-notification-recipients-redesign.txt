=====================================================================
ВСЕ ПРИНЯТЫЕ РЕШЕНИЯ (сводка)
=====================================================================

1. Hint-боксы. Убрать `createdOnlyHint` (плашка «не рекомендуется выключать») и
   аналогичные патерналистские советующие плашки по всей админке. НЕ трогать
   функциональные плашки (readOnlyHint про права; короткие field-hints в
   SettingsPage — это описания полей, не советы).

2. Мульти-исполнители на строке заказа (OrderLine) — ФУНДАМЕНТ, делаем ПОЛНОСТЬЮ,
   не только модель:
   - Один OrderLine может иметь НЕСКОЛЬКО исполнителей одновременно.
   - У КАЖДОГО исполнителя на строке — СВОЯ роль (EmployeeJobRole), т.е. водитель +
     гид одновременно на одной строке — валидный случай.
   - Меняются: модель данных, assign/unassign-сервисы, попап назначения в админке
     (мультивыбор), PDF, `GetAssignedToMe` (кабинет сотрудника), резолвинг
     получателя в уведомлениях — ВСЁ сразу, одной задачей.

3. Fulfillment details (сейчас `PickupDetails`/`NavigatorLink` на уровне
   OrderLine) переезжают на уровень КАЖДОГО исполнителя строки (т.е. на новую
   сущность line+employee, не на line целиком) — у каждого исполнителя своя
   карточка деталей в fulfillment-попапе.
   - Добавить новое поле `Comment` (+ `CommentEn`, см. п.5).
   - Правило null-скрытия: если поле (Pickup/Navigator/Comment) не заполнено —
     оно НИГДЕ не появляется — ни в PDF, ни в письме. PDF это уже умеет
     (`OrderPdfService` — условный `if (!string.IsNullOrWhiteSpace(...))`).
     Email — НЕ умеет: `OrderNotificationService.BuildAssignmentDetailsHtml`
     сейчас подставляет заглушки «не указано»/«не указан» вместо пропуска поля —
     это баг относительно нового правила, чинить.

4. Билингвальность писем — ПОЛНАЯ, для ВСЕХ 4 писем (OrderCreated /
   OrderAssignEmployee / OrderUnassignEmployee / OrderSendToClient), не только
   для письма-назначения:
   - `EmailTemplate`: к существующим `Subject`/`BodyHtml` добавляются
     `SubjectEn`/`BodyHtmlEn`. Обе версии редактируются в одной админ-карточке.
   - На `User` — новое поле `PreferredLanguage` (RU/EN, дефолт RU). Именно оно
     решает, какая версия письма уйдёт этому конкретному получателю.
   - Получатель без `User` (см. п.7 — «Custom email») языка не имеет: ПРИНИМАЮ
     дефолт — уходит RU-версия (низкий риск, если Давиду нужно иначе — сказать,
     поправим). Дальше не переспрашиваю, чтобы не растягивать раунды вопросов.
   - `Comment`/`CommentEn` в fulfillment details — та же логика: у Comment есть
     обе языковые версии, подставляется та, что соответствует языку получателя
     этого конкретного письма.

5. Настройки уведомлений — редизайн экрана (изначальный скоуп задачи):
   - Список = грид с ЕДИНСТВЕННОЙ колонкой «Событие» (текущие 4 action-key,
     набор закрытый — без create/delete строки, как сейчас).
   - Клик по строке → Details: шапка + вкладки.
   - Вкладка «Платформы»: грид [чекбокс Active] + [Название платформы]. Клик по
     чекбоксу платформы → появляется её вкладка настроек. Платформы: Email
     (рабочая), Telegram (см. п.6 — только каркас).
   - Вкладка «Email Settings»:
     (a) грид получателей — [Active] [Type: To/CC/BCC] [Получатель: Users-select
         / «Клиент заказа» / «Исполнитель заказа» / Custom email — свободный
         ввод];
     (b) ниже — Subject/SubjectEn + BodyHtml/BodyHtmlEn (RichTextEditor,
         п.4) — переезжает из текущей карточки как есть, только добавляются
         EN-поля.
   - Вкладка «Telegram Settings» (см. п.6): тот же грид получателей БЕЗ колонки
     Type (нет CC/BCC у Telegram) — [Active] [Получатель].
   - Грид получателей = ЕДИНСТВЕННЫЙ источник правды. Зашитая в код логика
     получателей (Admin/Employee/Client) удаляется. 0 активных строк у события —
     письмо не уходит вообще (осознанное поведение, не баг).
   - «Привязан к заказу» — закрытый список из 2 вариантов: Клиент заказа,
     Исполнитель заказа (при мульти-исполнителях — уходит КАЖДОМУ активному
     исполнителю строки/заказа отдельно, по аналогии с текущим
     `UnassignedEmployee`-списком). Админ как «привязанный к заказу» НЕ заводим —
     админ выбирается обычным Users-получателем.

6. Telegram: сейчас ТОЛЬКО каркас — модель в БД (`NotificationPlatform` enum,
   строка платформы в гриде п.5) + вкладка/грид в UI. Реальная отправка через
   Telegram-бота — отдельная будущая задача, вне этого скоупа.

architecture-role-notifications.md):
  [ ] Модель `OrderLineEmployee` (join line+employee): EmployeeId, EmployeeRole,

      `OrderLine.EmployeeId/EmployeeRole/PickupDetails/NavigatorLink` — удалить
      после переноса данных миграцией (по одной строке на существующую
      непустую связку).

  [ ] `EmailTemplate` + `SubjectEn`/`BodyHtmlEn`; правило выбора языка при
      рендере (по `PreferredLanguage` получателя; дефолт RU для получателей без
      User — п.4).
  [ ] Модель получателей: `NotificationPlatform` (Email/Telegram),
      `NotificationRecipient` (EventKey, Platform, Active, Type — nullable,
      только для Email, RecipientSource: User(FK)/OrderLinkedRole(Client|
      Employee)/CustomEmail(string)).
  [ ] Резолвинг «Исполнитель заказа» при множественных исполнителях — уход

      `EmailTemplateInfoModel`/`EmailTemplateUpdateModel`,
